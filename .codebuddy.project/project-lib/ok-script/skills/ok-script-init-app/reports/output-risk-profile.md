# 输出风险画像（ok-script-init-app）

## 风险矩阵

| 风险类别 | 严重度 | 概率 | 影响 | 缓解措施 |
|---|---|---|---|---|
| 编造可执行名/包名/仓库地址 | 高 | 中 | 应用启动后找不到目标进程，或打包指向不存在的仓库 | 需求清单明确「不知道就说不知道」，保留模板默认或运行期探测；不得凭空填写 |
| 中英文文档只改一侧 | 中 | 高 | 两语言读者看到的事实不一致，英文读者仍看到模板信息 | 工作流第 7 步与清单第七节都要求两侧同步；`mkdocs build --strict` 拦断链 |
| 更新仓库策略混用（半套配置） | 高 | 中 | 白名单过滤形同虚设，或更新库永远停在旧代码 | 清单第四节把两种策略写成互斥表格，并列出「混用的后果」 |
| 图标改名后漏改引用 | 中 | 低 | 界面与安装包图标缺失 | 明确要求文件名保持不变；确需改名时同步 `pyappify.yml`、`src/config.py` 与文档 |
| 任务类建好但未注册 | 中 | 中 | 任务永远不出现在列表，**不报错** | 清单第六节把「注册」列为独立检查点；注册方式交 `ok-script-tasks` |
| `ok_templates` 仍被忽略 | 高 | 中 | 协作者无法重新导出特征，标注知识丢失 | SKILL.md 单列「模板资源」一节；清单第五节给出三条校验命令 |
| 入库后未配发布过滤 | 高 | 中 | 数百 MB 源图进安装包，用户下载量激增 | 说明 PyAppify 不读 `.gitignore`；要求 `deploy.txt` 不含该目录并打测试 tag 核验 |
| 用 Git LFS 存截图 | 高 | 低 | 用户侧拿到指针文本，特征全部匹配失败，**构建期不报错** | SKILL.md 明确禁止并说明 libgit2 不执行 smudge filter |

## 与其他技能的边界风险

| 越界形态 | 表现 | 处置 |
|---|---|---|
| 顺手生成 `.codebuddy.project/` 骨架 | 与 `core-init` 冲突，两套骨架互相覆盖 | 初始化引擎配置一律交 `core-init`；本技能只改应用业务层 |
| 把首个任务的完整 `run()` 动作序列写进骨架 | 与 `ok-script-codegen` 产出重复，改一处漏一处 | 骨架只留任务类结构与注册，动作交 codegen |
| 顺手改 `.po` 条目 | 与 `ok-script-i18n` 的编译步骤脱节，改了不生效 | 只提示「需要翻译」，不要动翻译目录 |
| 顺手打 tag 触发发布 | 与 `ok-script-deploy` 的版本号规则冲突 | 用户未明确要求时不建、不推 tag |

## 输出质量维度

### 配置一致性

- 三处应用名必须同源：`src/config.py` 的 `gui_title`、`pyappify.yml` 的 `name`、`mkdocs.yml` 的 `site_name`。
- 运行目标至少保留一个，用户要支持的全部保留。
- 图标文件名与 `pyappify.yml` 的 `icon` 字段保持一致。

### 说明与操作分离

- 用户只要结果时直接改文件并展示 diff，不附长篇解释。
- 需要用户决策的地方（更新策略、MirrorChyan 接不接）用明确的是/否提问，不替用户选。

## 已知局限性

1. **无法验证目标程序标识**：可执行名、窗口类名、包名是否真的匹配，只能在真机或模拟器上跑一次 `main_debug.py` 才能确认。本技能只保证配置被正确写入。
2. **首个任务只建骨架**：行为实现依赖 `ok-script-codegen` 对截图或描述的解读质量，本技能不校验识别准确率。
3. **secrets 无法代建**：更新仓库与 MirrorChyan 需要的 token 必须由用户在仓库设置里手工创建，技能只能列出清单。
4. **无自动化脚本**：全部结论靠读文件与项目约定，因此「漏改项」依赖清单逐项核对，没有机械兜底。
5. **模板来源会演进**：上游 `.agents/skills/initialize-ok-script-app` 更新时需按 `CHANGELOG.md` 的同步策略手工比对，不能直接覆盖。
