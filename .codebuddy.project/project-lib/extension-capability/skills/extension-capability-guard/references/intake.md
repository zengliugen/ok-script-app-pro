# 调用后的第一步：意图确认

> 本文件是 `SKILL.md` 的**强制前置**：技能被唤起后**不得直接执行 `audit`**，
> 先问清这次属于哪一类意图，再按去向表走。执行模式本身的判定细节仍看 `SKILL.md`。

## 为什么必须先分流

同一声「扩展能力」可能落在四类完全不同的动作上，而它们的前置条件互不兼容：

| 直接照字面执行 | 后果 |
|---|---|
| 听到「扩展能力」就 `audit` | 用户其实要新增能力时，拿到的是一份体检报告；真正该走的 `explore → new` 被跳过，而体检照样全绿，没有任何报错 |
| 听到「改一下某能力」就改活跃文档 | 改动可能暴露新行为面，本该立新能力；旧文档被改写后，当初的推理永久消失 |
| 把本技能当文档生成器 | 本技能不提供 `new`，用户以为技能坏了，转而手工建文档——绕过了 `devflow-guard` 的强制校验 |
| 一律先 `audit` | 体检只查契约，查不出「这次改动该不该立项」；报全绿反而给了错误结论 |

分流是一次提问的成本，换掉的是一次错误产出。

## 第一问：这次要做什么

**先问，再动手。** 选项按可能性排序，第一个标推荐。用户已在消息里说明意图的，
仍要问一次，把「按你刚才说的执行」放第一项——分诊结论必须由用户确认，不由执行者推定。

| 选项 | 含义 | 紧接着做什么 |
|---|---|---|
| 只跑体检 / 查契约缺口 | 文档契约或代码落位有没有缺口、某能力是否已登记 | 本技能 `audit`；需要推进状态时再转 `devflow-guard status` |
| 新增扩展能力 | 从无到有做一件向用户或框架暴露新行为面的事 | 转 `devflow-guard` 的 explore → new 全链路（见下节） |
| 改动现有能力 | 已有能力要改方案、改行为、改范围 | 先判「算不算暴露新行为面」，再决定立新能力还是只记偏差 |
| 维护文档结构 | 改状态、归档、写决策记录 | 转 `devflow-guard` 的 `status` / `archive` / `adr` |

**不要一次问四件事**。第一问只定类别；类别确定后，缺的参数（能力名、状态值、主题名、slug）
在第二轮一并问齐，避免连续弹窗。

## 为什么没有第二问（域）

`devflow-guard` 需要确认「项目域还是引擎域」，因为它的两棵文档树相互独立。本技能不需要：
扩展能力代码只存在于本项目的 `extensions/`，对应文档固定落项目域，文档根由 devflow 配置声明
（本仓库为 `extensions_docs`）。凭空问一次域，只会诱导用户选到引擎域那个不存在的落点。

## 各去向的完整判据

### 只跑体检

```bash
D=.codebuddy.project/project-lib/extension-capability/skills/extension-capability-guard
python $D/scripts/extension_capability_guard.py audit
```

退出码 3 表示环境不可用（委托目标缺失或 devflow 配置不可用），此时其余结论都不可采信。

### 新增扩展能力

**不在本技能执行**。按 `devflow-guard` 的链路，一步不得跳：

1. `explore <主题名>` 建需求探索记录；
2. 查既有方案（联网检索、上游/框架文档、本地依赖与既有代码），把候选与来源写进「既有方案调研」；
3. 填写「要解决的问题」「未定项」「已排除」「结论」「已确认的决定」；
4. 经用户确认结论；
5. `new <能力名> --from-explore <主题名>` 生成骨架并登记总览表；
6. 实施、记偏差、验收；
7. 完成后再回来跑本技能 `audit`。

### 改动现有能力

先用 `.codebuddy/lib/devflow/rules/devflow/design-spec.mdc` 的判定表确认这次改动
**是否暴露新行为面**：

| 判定 | 去向 |
|---|---|
| 暴露新行为面 | 立新能力，用与旧名不同的名字；旧能力已归档用 `--rework-from <旧名>` |
| 不暴露新行为面（修 bug、调参数、改文案、内部重构） | 不走链路，按普通改动处理；完成后再 `audit` |

旧能力已归档时先读 `.codebuddy/lib/devflow/skills/devflow-guard/references/guide.md` 的
「已归档的能力怎么改」——「修 bug」在归档场景下有两义：实现缺陷仍按普通改动处理，
推翻了归档文档判据的属设计失效，须立新能力 + `--rework-from`。

### 维护文档结构

全部转 `devflow-guard`：

```bash
D=.codebuddy/lib/devflow/skills/devflow-guard/scripts/devflow_guard.py
python $D status <能力名> <状态>
python $D archive <能力名>
python $D adr <slug> --capability <能力名>
```

## 分诊之外的两条硬约束

1. **只读请求也不豁免第一问**。「这个能力登记了吗」同样先问类别——答案可能引出补登记
   （`new`）、补状态（`status`）或只是查表（`audit`），三者的写操作范围不同。
2. **用户回答模糊时追问一轮，不要猜**。「改一下那个东西」不足以判定类别；猜错会产出
   一份用不上的文档。

## 与其它技能的边界

本技能只承接**扩展能力的流程守卫与代码落位体检**。下列请求在分诊时直接告知用户去向，
不代为执行：

| 请求 | 去向 |
|---|---|
| 决定用哪条扩展路径 | 规则 `extension-capability/methods.mdc` |
| 修 bug、调参数、内部重构、补测试 | 无需走流程；完成后再 `audit` |
| 提交代码 | 版本控制路由技能 |
| 登记上游改动、校验差异清单 | `upstream-compat-guard` 技能 |
| 执行测试 | `run_tests.ps1` |
