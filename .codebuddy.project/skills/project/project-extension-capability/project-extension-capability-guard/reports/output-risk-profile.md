# 输出风险画像

> 本文件由人工撰写（非工具生成）。当前技能**没有脚本单元测试**，本文件是主要的自我约束记录。

## 职责范围已收窄（2026-10-29）

本技能原先把文档契约（文件头、生成器、总览表、ADR 编号、计划与偏差配对）与代码落位一起体检。
引擎侧 `devflow-guard` 补齐同名能力后，文档契约改由它承担，本技能只保留它查不了的部分：
需要读懂 `extensions/` 源码结构才能判断的落位约束。`new` / `deviation` / `adr` 三个命令随之删除。

**风险性质因此改变**：原先「两处判定逻辑各自演化」的风险消失，换成「委托失败时表面通过」的新风险，
见下表第一条。

## 风险矩阵

| 风险 | 触发场景 | 表现 | 缓解 |
|---|---|---|---|
| **委托失败被当成通过** | `devflow` 包未安装、配置不可用、脚本执行异常 | 文档契约段落打印一行错误，但整体结论可能被误读为「部分检查通过」 | 委托失败固定返回 3，且 3 优先于一切；结论行显式说明「有检查未能执行」 |
| **静默通过** | 代码落位检查的正则或 ast 判定失效 | 输出「无缺口」，退出码 0——看起来一切正常 | 输出必须含「项目根」与两段分节标题；零缺口时人工抽查一个已知约束 |
| 误报堆积 | 上游/项目结构演进后检查判据未同步 | 每次 audit 都报同一条不存在的问题 | 出现重复误报时先查判据是否落后，而不是加豁免 |

## 输出的三类质量问题

### 1. 结论与明细不一致

退出码由最高档决定（有错误即 2），但输出可能同时含错误与警告。
**读者容易只看最后一行「结论」，忽略上面的错误明细**——尤其当错误只有一条时。

缓解：错误分组始终排在警告与提示之前，且每组带计数；两段（委托 / 本技能）各自单独成节。

### 2. 「提示」被当成「没问题」

提示级（如「代码变了但总览表未变」）不改变退出码，容易被忽略。
但它往往正是「新能力未登记」的唯一信号。

缓解：提示单独成组输出，不隐藏在通过分支里。

### 3. 委托段的输出被当成自己的输出

委托段的输出原样转发，缩进两格并加节标题。不加区分会让读者以为
「文档契约也对齐了本项目的某些约定」，实际上它只按 `devflow` 配置判。

缓解：节标题写明「委托 devflow-guard」，且委托段的结论行本身带「开发流程文档体检」抬头。

### 4. 路径信息不足以定位

缺口消息必须带**相对项目根的完整路径**（如 `extensions/patches/foo.py`），
不能只说「foo.py 缺断言」——后者在读代码时无法判断是哪个目录。

## 自查清单（改动脚本后必看）

| 项 | 检查方式 |
|---|---|
| 能正常跑 | `python <脚本> audit` 无 traceback |
| 全绿时输出干净 | 无缺口时两段各自只打印标题与结论 |
| 委托目标缺失返回 3 | 临时改名 `.codebuddy/lib/devflow`，整体退出码应为 3 且结论行提示「有检查未能执行」 |
| 缺 `__init__.py` 能识别 | 在 `extensions/` 下建空目录，audit 报错 |
| patch 无断言能识别 | 建一个无 `raise` 的 `apply()`，audit 报错 |
| `sys.path` 污染能识别 | 在 `extensions/` 里写一行 `sys.path.insert(0, "extensions")`，audit 报错 |

## 已知盲区

| 盲区 | 影响 | 为什么不修 |
|---|---|---|
| 不检查文档契约 | 文档缺字段、未登记、ADR 断号由引擎侧脚本判，本技能看不见 | 判定逻辑只应有一处事实来源；本技能委托它 |
| 不检查文档**内容**质量 | 写了但写的是废话，体检判通过 | 内容质量无法机械判定 |
| 不检查 ADR 正文是否被改写 | 已提交的 ADR 被修改不会被发现 | 需要 git 历史基线 |
| 不检查 plan 与代码的一致性 | 计划写 A 实现成 B 不报错 | 需要语义理解 |
| 不校验能力名与实际代码的对应 | 登记了能力名之后再没写任何代码也不报错 | 无法判断「代码里哪部分是某个能力」 |

## 免责声明

本技能的退出码**只能证明「机械检查通过」，不能证明「文档合格」**。
零缺口意味着没有违反结构约束，不意味着设计写得对、取舍有依据。
