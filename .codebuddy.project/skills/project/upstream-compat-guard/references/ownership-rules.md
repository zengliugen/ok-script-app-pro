# 归属判定：哪些改动根本不该进 divergence.yaml

## 为什么单独成篇

本项目工作区里至少有三个"看起来像上游、其实不是"的路径。把它们当成上游文件，会产生两种后果，
都很难自查出来：

1. **误登记**：把引擎仓库的改动写进 `divergence.yaml`，条目永远无法失效（引擎改动不会出现在
   上游 diff 里），校验会一直报 `[不一致]` 或莫名通过，最终没人再信这份清单。
2. **误以为已处理**：改完引擎后跑一次校验，脚本什么都没提示，于是认为「引擎属于上游、
   本次改动已被覆盖」——实际是「这条路径根本不在本技能的职责内」。

## 三类路径与归属

| 路径 | 真实归属 | 该在哪提交 | 是否登记上游差异 |
|---|---|---|---|
| `.codebuddy/**` | **引擎仓库**（submodule，独立 Git 仓库） | 引擎根（`.codebuddy/`）内 | **否** |
| `.codebuddy.project/**` | **项目仓库**（本项目自有目录） | 项目根内 | **否** |
| `src/**`、`pyproject.toml` 等 | **项目仓库**，但文件来自上游 | 项目根内 | **是** |

判定顺序不能反。正确顺序是：**先判 submodule → 再判项目自有目录 → 最后才问「锚点里有没有」**。

反例：若某个项目历史上把引擎当普通目录提交过一次，锚点里就会留下 `.codebuddy` 的 tree。
此时只靠「锚点中存在」判定，整棵引擎树都会被认成上游文件，而它其实是 submodule。
脚本的 `classify()` 先查 `.gitmodules` 正是为了挡掉这种情况。

## 为什么用 `.gitmodules` 而不是硬编码 `.codebuddy`

submodule 路径由项目自行配置，可能不叫 `.codebuddy`，也可能一个项目挂多个 submodule。
脚本用 `git config --file .gitmodules --get-regexp '^submodule[.].*[.]path$'` 读取声明，
不假设任何固定名字。项目若没有 `.gitmodules`，该列表为空，判定自然退化为「只按锚点判」。

## 脚本如何表现

| 场景 | 表现 | 退出码 |
|---|---|---|
| 引擎有未提交改动，跑全量校验 | 顶部提示「以下目录是独立仓库…应在该仓库内提交」，引擎改动不进入登记判定 | 0（登记本身无问题） |
| `--add .codebuddy/xxx` | `[拒绝] … 属于独立仓库（submodule）`，并指出应在 `.codebuddy` 内提交 | 4 |
| `--add .codebuddy.project/xxx` | `[拒绝] … 是本项目自有目录` | 4 |
| `--add src/xxx`（上游文件） | 正常输出登记骨架 | 0 |

「不属于上游来源」统一用退出码 4，与「有问题（1）」区分开——前者是调用方式错了，
后者是清单需要补登记，两者处置完全不同。

## 自查：我改的到底算不算上游

在动手登记之前，先回答一个问题：**这个文件在 `git merge upstream/master` 时会不会产生冲突？**

- 会 → 它是上游文件，改了就登记。
- 不会（引擎、`.codebuddy.project/`、`extensions/` 新增文件、`tests/` 新增测试）→ 不登记。

第二种情况下如果仍想记录「我做了什么」，该写的是 `extensions_docs/README.md` 的能力总览表（记能力、文档与状态），
不是 `divergence.yaml`（记与上游的差异）。两份清单的职责见 `divergence-registry.mdc` 与 `rules/project/extension-capability/docs.mdc`。

## 与相邻规则的边界

本文件只回答「这条路径归哪个仓库、要不要登记」。**怎么在各自仓库提交**（先子后父的顺序、
两仓库混提交的后果、判定当前目录属于哪个仓库的命令）由
`.codebuddy/rules/vcs/vcs-engine-commit/` 管辖，那里是权威来源，本文件不复述。
