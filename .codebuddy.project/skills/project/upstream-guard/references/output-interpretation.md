# 输出标记与退出码解读

脚本每次运行都会先打印两行头部，告诉人「这次拿什么当基准、比了多大范围」：

```
校验基准：f134d07ce064c49060068c0511b5592b0e78a081
检查范围：锚点到 HEAD 全部差异
```

头部之后是明细。明细只有四种标记，没有第五种——出现别的字样说明脚本被改过，需要核对。

## 四种标记

| 标记 | 判定条件 | 含义 | 处置 |
|---|---|---|---|
| `[未登记]` | 文件在锚点中存在（属上游来源），状态为 `M` 或 `D`，但 `divergence.yaml` 里没有该 path 条目 | 改了上游文件却没登记 | 补登记，**与改动同一次提交** |
| `[已失效]` | `divergence.yaml` 有条目，但锚点到 HEAD 的差异里已无该文件 | 条目指向的差异不存在了（多半是上游合并后差异被吸收） | 删除该条目；需要历史请查 git |
| `[不一致]` | 有条目且文件有差异，但实际状态与登记的 `kind` 不同 | 例如实际 `D`（删除）却登记为 `M`（修改） | 修正条目 `kind` |
| `[告警]` | 状态为 `A`（新增），且路径落在上游专属代码目录 | 新代码写进了上游目录，未来上游改动会冲突 | 按扩展优先原则移到 `extensions/` |

## 三条判定细节

**新增文件不进 `[未登记]`。** 上游没有这个文件，新增不构成冲突源，所以不要求登记。
只有落进上游专属目录才告警——告警不是「未登记」，两者语义不同，不要混谈。

**重命名归并为修改。** git 把重命名报为 `R`，脚本取首个字母前先归一：`R` → `M`。
否则重命名会被当成新增而漏掉删除侧的问题。

**`--changed` 模式不做失效判定。** 工作区只包含部分改动，拿它判定「条目已无差异」必然误报。
失效判定只在全量模式下有意义。

## 上游专属目录清单

判定 `[告警]` 用的目录在脚本常量 `UPSTREAM_ONLY_DIRS` 中，当前为：

- `src/tasks/`
- `src/ui/`
- `src/globals.py`

`docs/` 与 `tests/` **故意不在列表内**：新增文档页与新增 `Test*.py` 是正常落点，
且新增测试需要被 `run_tests.ps1` 捡到。改动这两个目录的既有文件仍按 `[未登记]` 处理。

## 退出码

| 码 | 含义 | 调用方该做什么 |
|---|---|---|
| 0 | 通过：所有上游改动都已登记且一致 | 可以提交 |
| 1 | 存在问题：有未登记 / 已失效 / 不一致 / 告警 | 按明细逐条处置后重跑 |
| 2 | git 操作失败：锚点不可解析、`git diff` 失败等 | 检查仓库状态与锚点，不要当成「校验通过」 |
| 3 | 配置缺失或损坏：清单不存在、YAML 坏、缺必填字段 | 修配置；脚本不会回退默认值 |
| 4 | `--add` 目标不属上游来源（引擎 submodule / 项目自有目录 / 锚点中不存在） | 不是错误：按提示去对应仓库处理，或本就无需登记 |

退出码 2 与 3 都**不是**「没问题」。CI 里只判 `!= 0` 时务必把 2/3 与 1 区分呈现，
否则会出现在「根本没跑起来」的情况下报「有未登记改动」的误导。
