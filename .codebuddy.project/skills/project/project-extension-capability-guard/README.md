# 扩展能力守卫

## 解决什么问题

扩展能力的**代码**能说明「做了什么」，但说明不了「为什么这么做、放弃了什么、在什么前提下会失效」。
这些判断一旦丢失，后来者只能重新推演——而重新推演往往会得出相反结论，于是同一件事被反复推翻。

本技能把这件事变成可执行的流程：新建能力时生成文档骨架并在总览表登记，改动后机械体检文档契约与
代码落位，把缺口按三档报出来。

## 怎么用

```bash
S=.codebuddy.project/skills/project/project-extension-capability-guard/scripts/extension_capability_guard.py

python $S new config-overrides   # 生成三份骨架 + 登记总览表
python $S audit                  # 体检
```

`new` 之后需要人填内容：design 写方案与取舍，plan 写分批任务，testing 写策略与验收结论。
技能只给骨架，不给内容——设计判断不能由脚本代劳。

## 两个模式的分工

| 模式 | 何时用 | 产物 |
|---|---|---|
| `new` | 决定要做一个新能力、方案还没定 | 三份空骨架 + 总览表一行 |
| `audit` | 提交前、同步后、或怀疑文档与磁盘不一致时 | 缺口报告 + 退出码 |

## `audit` 报出来的东西怎么读

| 档位 | 你该做什么 |
|---|---|
| 错误（退出码 2）| 必须修。缺文件、缺文件头字段表、字段缺失、状态值非法、**生成器字段缺失或取值非法**、表头被改、ADR 编号重复、patch 无断言、包结构缺 `__init__.py` |
| 警告（退出码 1）| 逐条判断。文档存在但未在总览表登记、状态已定/已实施但缺计划或偏差记录、ADR 编号跳号 |
| 提示（退出码 0）| 看一眼即可。`extensions/` 有改动但总览表未变 |

**不设豁免机制**：缺口一直报，直到修掉。这条是刻意的——豁免清单一旦存在就会无限扩张，
最后没人再看输出。

## 边界（不做什么）

| 不做 | 理由 | 该谁做 |
|---|---|---|
| 判断用哪条扩展路径 | 需要读框架能力，脚本判断不了 | 规则 `project-extension-capability/methods.mdc` |
| 修改文档内容 | 设计与措辞是人的判断 | 人写 |
| 覆盖已存在的文件 | design 文档往往是唯一副本，覆盖不可逆 | 人手工处理 |
| 检查上游文件改动 | 属另一族 | 技能 `project-upstream-compat-guard` |
| 跑测试 | 职责分离 | `run_tests.ps1` |
| 自动接 CI | 先观察误报率，确认稳定后再考虑 | 后续决定 |

## 已知局限

**没有脚本单元测试**。九项检查的判定逻辑靠实际运行验证，这意味着逻辑错误可能**静默通过**
（表现是「零缺口」，而非报错）。使用时不应只看退出码，还要看输出内容是否合理。

已验证过的场景（手工构造）：非法状态值、表指向不存在的文件、表头被改、缺 `__init__.py` 目录、
非法能力名、重名能力、缺参数、未知命令——均能正确报错并返回预期退出码。
