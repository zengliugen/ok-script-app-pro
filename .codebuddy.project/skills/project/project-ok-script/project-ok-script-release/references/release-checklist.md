# 发布检查清单

## 一、发布前

| 项 | 检查方式 | 不通过时 |
|---|---|---|
| 工作区改动都在预期内 | `git status --short --branch` + `git diff` | 先确认范围，无关改动不得混入 |
| 验证通过 | `.\run_tests.ps1` | 停止发布，除非用户明确接受带失败发布 |
| 版本号未与他人撞车 | `next_tag.py <渠道> --remote origin` | 远端查询失败即停止，不得凭本地 tag 猜 |
| 没有未登记的上游改动 | 走 `project-upstream-compat-guard` | 补登记后再发 |
| `src/config.py` 的 `version` 仍是 `dev` | 人工核对 | 它由打包流程改写，不要手改 |

## 二、tag 与 CI 的触发关系

`.github/workflows/build.yml` 的触发条件是 `push` 的 tag 匹配 `v*`。因此：

- **只打本地 tag 不会触发构建**，必须推上去；
- tag 名不符合 `v*` 时构建根本不启动，也不会报错——只是什么也没发生；
- 构建产物、Release 与更新源的地址由 `pyappify.yml` 决定，与 tag 号无关。

推论：**「本地有 tag」与「发布完成」是两件事**。汇报时必须分开说推送是否成功、
CI 是否已开始构建。

## 三、三条号段互不影响

| 渠道 | 递增依据 | 会不会影响另外两条 |
|---|---|---|
| 稳定版 | 最新稳定版 patch + 1 | 会**关闭**版本号小于等于它的预发布基线 |
| beta | 同渠道最新预发布 + 1，或下一个 patch 的 `.1` | 不影响 alpha，也不改稳定版 |
| alpha | 同渠道最新预发布 + 1，或下一个 patch 的 `.1` | 不影响 beta，也不改稳定版 |

「关闭」的含义：稳定版 `v3.3.55` 发布后，`v3.3.55-beta.*` 与 `v3.3.55-alpha.*` 都不再继续，
新的预发布从 `v3.3.56-*` 起。这条规则避免出现「正式版之后还有同基线预发布」的乱序状态。

## 四、失败处置

| 现象 | 处置 |
|---|---|
| `next_tag.py` 报「没有任何稳定版 tag」 | 首发版本要人工指定（如 `v0.1.0`），脚本不做无基线的推断 |
| `ls-remote` 失败（网络 / 权限） | 停止，不要退回只用本地 tag |
| 提交链路判定摘要不合规 | 按项目配置的 pattern 改写摘要后重走链路，不要绕过 |
| tag 已创建但推送失败 | 保留本地 tag，修好网络或权限后重推；**不要删 tag 重来** |
| 推送成功但 CI 未启动 | 先核对 tag 是否匹配 `v*`，再查 Actions 是否有权限问题 |
| tag 打错了版本号 | 停止并回报；删除/移动 tag 属禁止操作，需人工决策 |

## 五、不要做的事

- 不要为了「让 tag 对上代码」去 `git tag -f` 或删 tag 重建。
- 不要在验证失败时用「先发出去再说」推进。
- 不要在一次发布里同时改代码与改版本号——版本号由 tag 承载，代码里不写版本。
- 不要用 `git push --force` 解决推送冲突。
