# 输出风险画像（project-ok-script-release）

## 风险矩阵

| 风险类别 | 严重度 | 概率 | 影响 | 缓解措施 |
|---|---|---|---|---|
| 版本号算错（重复或倒退） | 高 | 中 | 同号覆盖或构建不触发，已发布版本不可追溯 | 一律用 `next_tag.py` 计算；必须带 `--remote` 纳入远端 tag；远端查询失败即停止 |
| 稳定版之后继续发同基线预发布 | 中 | 中 | 出现「正式版之后还有同基线 beta」的乱序状态 | 脚本内实现「基线已发正式版即关闭」规则，并有实测用例 |
| 只打本地 tag 就宣布发布完成 | 高 | 中 | 用户以为已发布，实际 CI 未触发 | 规则要求分别汇报「推送是否成功」与「CI 是否触发」 |
| 绕过 vcs-router 自己 commit | 高 | 中 | 跳过摘要格式校验、安全检查、互斥锁，形成第二套提交流程 | SKILL.md 单列一节说明边界；提交一律交链路 |
| 未经授权就推送 | 高 | 低 | 违反项目 `push_initiation=user_only` 约定 | 显式写明须用户指令；未授权时停在「仅本地完成」 |
| 删/移动已有 tag | 高 | 低 | 已发布版本号指向另一份代码，无法追溯 | 硬约束第一条；`security/permission_policy.json` 明确列为禁止 |
| 验证失败仍继续发布 | 中 | 中 | 带缺陷发版 | 工作流第 2 步要求停止，除非用户明确接受 |
| 混入无关改动 | 中 | 中 | 发布内容与预期不符 | 第 1 步要求确认范围，歧义时先问 |

## 与其他技能的边界风险

| 越界形态 | 表现 | 处置 |
|---|---|---|
| 本技能直接 `git commit` | 两套提交流程，摘要格式与安全检查逐步分叉 | 提交一律交 `vcs-router` 链路 |
| 本技能改代码「顺手修一下」 | 发布范围失控，验证结论失效 | 发布只做版本编排，代码改动另开步骤 |
| 本技能代为登记上游差异 | 与 `project-upstream-compat-guard` 职责重叠 | 发现未登记改动时停下，交给该技能 |

## 输出质量维度

### 结论可核验

- 汇报必须包含：提交摘要、tag、远端、推送是否成功、CI 是否触发。
- 不把「本地有 tag」表述为「已发布」。
- 版本号改动前后都要能复述依据（最新稳定版是哪个、为什么是这个号）。

### 顺序正确

固定顺序：确认范围 → 验证 → 算版本号 → 提交 → 打 tag → 推送 → 核验。
算版本号必须在提交前完成，避免与既有 tag 撞名后才发现。

## 已知局限性

1. **首发版本不由脚本推断**：仓库里没有稳定版 tag 时脚本报错退出，首个版本号需人工指定。
2. **无法判断该不该发**：验证通过不等于功能完整，发布时机属人的决策。
3. **CI 状态无法在本技能内确认**：只能确认推送成功；构建结果需要在 Actions 页面看。
4. **远端查询依赖网络与权限**：`git ls-remote` 失败时无法给出可信版本号，这是硬阻塞而非告警。
5. **不做发布说明**：tag 消息只写版本号，变更内容需另行整理。
