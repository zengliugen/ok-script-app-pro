# decisions/ —— 决策记录（ADR）

## 什么是 ADR

一份 ADR 记录**一个已经拍板的决策**及其理由，一旦定稿**不再改写**。
后续若推翻该决策，不修订原文，而是新写一份 ADR 并在其「取代」字段指向被取代者。
这样「当时为什么这么定」永远可查，不会被后续改写抹掉。

## 只记结论与判据，不记讨论反复

ADR 记录的是**最终采纳的决策**及其判据，不是讨论过程。

在设计阶段的反复推演中推翻已有结论是常见且正常的——那些被推翻的中间方案**从未成为决策**，
因此不需要进 ADR。把「曾经考虑过 A，后来改成 B，又改回 A」写进 ADR 只会让读者误以为存在历史包袱。

**只在同一决策已经定稿并落地后又被推翻时**，才新写一份 ADR 取代它（见下文「命名与编号」）。


## 记的是扩展能力的决策，不是文档体系自身的决策

这里记录**某个扩展能力**在实现过程中拍板的决策：为什么选这个方案、否决了哪些备选、边界划在哪。

**不记录**「这套文档体系为什么这样设计」——那是体系自身的建设过程，结论已经落在规则文件里
（`.codebuddy.project/rules/project/extension-capability/`），不需要在这里留档。

判断标准：这条决策以后还会被某个能力的维护者查询吗？会 → 写；只是当初建体系时的推演 → 不写。


## 放什么

- 选择类决策：在多个可行做法中选了哪个，为什么，放弃了什么
- 否决类决策：某个看似合理的做法为什么被排除（这类最有价值——防止同一提案被反复重启）
- 边界类决策：两个概念/目录/职责的分工线划在哪

## 不放什么

- 尚未拍板的方案 → `design/`
- 实施步骤 → `plans/`
- 通用编码约束 → 规则文件

## 命名与编号

`NNNN-<slug>.md`，四位数字，**只增不复用、不回收**。slug 用英文 kebab-case，简短描述决策本身。

已被取代的 ADR **保留在原处**，只在文件头状态改为「已废弃」并在「取代」字段写明新的编号。
不移入 `archive/`——决策链的连续性依赖编号顺序，移动会破坏可查性。

## 与设计文档的区别

| | design/ | decisions/ |
|---|---|---|
| 内容 | 多个候选方案的比较与推演 | 单一结论及其理由 |
| 可变性 | 可随理解加深改写 | 定稿后不可改写 |
| 读者 | 参与设计的人 | 半年后想知道「为什么」的人 |
