## 背景

> 需求已确认，探索记录见 explore/scene-manager.md（含已排除方向与重新可行的前提）。

本项目是 ok-script 模板项目，业务代码要在「进入某个画面之后才能做某事」这件事上反复手写等待与
重试。需要一套与业务解耦的场景库（画面状态 + 交互区域 + 跳转边）、一个「跳到指定场景」的
稳定接口，以及一个能把跳转边自动探出来的探索器。

## 要解决的问题

**现象**：使用者每接一个游戏，都要为每个任务各自实现「识别现在在哪 → 决定怎么走 → 点击 →
验证到没到」。同一套逻辑在多个任务里重复、互不兼容；坐标散落各处，游戏更新或换分辨率后
需要逐个改，且没有任何手段能一眼看出「当前画面属于哪个状态」。

**不做的后果**：路径知识以散装形式沉积在各任务的 `run()` 里。新增一个「要先进某个二级页面」
的需求时，作者只能重新摸索一遍点击序列；路径失效时，故障表现为「任务卡住」而非「场景识别错」，
排查成本全部转嫁到使用者。

## 候选方案

| 方案 | 做法 | 代价 | 前提 |
|---|---|---|---|
| A：纯逻辑类 + 薄壳 Task | `SceneNavigator` 承载识别/寻路/点击；`SceneGotoTask` 只做执行器集成；另有 `SceneExploreTask` 独立跑探索 | 两个任务类要注册、`visible=False` 需自行处理 | 框架的任务嵌套与提交机制可用（已核实，见实测证据 1） |
| B：单一大 Task 包办全部 | 一个 `SceneManagerTask` 内含导航、探索、页签回调 | 内部模块（流转图「试走一步」、离线回归测试）无法复用，只能开任务或复制代码 | 无 |
| C：纯函数库，不做 Task | 只暴露 `goto_scene()` 等函数，调用方自己管线程 | 不继承执行器的暂停/停止/独占语义；无法从任务列表启动探索 | 调用方都是自己写的、且都愿意处理线程 |
| 不做 | 各任务继续手写路径 | 每个任务重复实现，路径知识不可复用、不可视化 | 无 |

**否决理由与重新可行的前提**：

- **B 被否决**：流转图页的「单步走一步」与离线回归测试都需要在**没有任务上下文**的地方调用
  识别与单步点击。把逻辑锁进 `run()` 后，这两处只能复制代码，而复制出来的副本一定会与
  主路径漂移。若日后框架提供「任务内可复用的执行上下文对象」，B 的代价会下降，但收益仍不如 A。
- **C 被否决**：探索是长跑，必须能暂停、停止、被中断；导航与探索都要独占执行器以防其他任务
  抢点击。这些全部由框架的执行器提供，绕开它就要自己实现一套等价机制。
  若框架移除了 `BaseTask` / `TaskExecutor`，C 才会成为唯一选择（届时也没有别的选择）。
- **不做被否决**：需求明确要求「封装接口供外部使用」，而现状是没有任何可调用的统一入口。
  若要重新考虑「不做」，前提是本项目的任务数量长期停留在一两个、且路径不重复。

## 实现手段

按依赖深度从浅到深：显式扩展点 → 继承覆写 → 观察事件 → 侵入式替换。

- **选定哪一级：路径 1（继承 + config 注册）**。

  | 用途 | 扩展点 | 依据 |
  |---|---|---|
  | 页签注入 | `config['custom_tabs'].append([模块, 类])` | `MainWindow.py:125-135` |
  | 任务注入 | `config['onetime_tasks'].append([模块, 类])` | `config.py:122-125` 的既有形态 |
  | 识别 / 点击 | `BaseTask` 已有的 `find_feature` / `ocr` / `click` | `task.py:594` / `:742` / `:148` |
  | 取帧 | `og.device_manager.capture_method.get_frame(...)` | `TemplateTab.py:168-169` |
  | 执行器独占 | `executor.acquire_exclusive(owner)` | `TaskExecutor.py:560-585` |
  | 任务嵌套 | `BaseTask.run_task_by_class(cls)` | `task.py:1046-1056` |

- **未上升级别**，因此不写 `divergence.yaml` 条目（`pyproject.toml` 的依赖新增属既有条目
  的内容更新，不是新增差异面）。

## 模块划分

```text
extensions/capabilities/scene_manager/
├── __init__.py          装配契约：登记页签与两个任务
├── model.py             场景/特征/区域的数据类 + JSON 序列化（无 Qt、无 ok 依赖）
├── routes.py            流转路由表：场景之间怎么跳转（独立的 routes.json）
├── store.py             场景库读写：一场景一目录、草稿区、导入导出、基准分辨率、路由表
├── normalize.py         帧归一化：缩放到库基准分辨率、坐标换算、特征搜索区域换算
├── recognize.py         场景识别：必需全中 + 可选打分、缓存当前场景、短路
├── resolution.py        分辨率一致性判断：截图准入、保存前全面检查（无 Qt 依赖）
├── graph.py             流转图：networkx 建图、最短路、边来源过滤、布局坐标
├── navigate.py          SceneNavigator：逐层跳转、重试/回退/报错、结果对象
├── explore.py           探索器：BFS、白名单探测、稳定帧判定、差分提候选框、草稿产出
├── tasks.py             SceneGotoTask / SceneExploreTask（薄壳，只做执行器集成）
├── tab.py               主页签：TabStrip + QStackedWidget 四个子页签
├── pages/               四个子页签（config / flow / drafts / debug）
├── flow_canvas.py       QGraphicsView 自绘节点画布
└── i18n/                zh_CN / en_US 的 ok_ext catalog
```

**为什么 `model.py` / `normalize.py` 不导入 `ok` 与 PySide6**：它们是全部换算逻辑所在，
必须能在无 GUI、无设备的测试环境里完整验证。混入 `ok` 后，最需要精确验证的部分反而
必须装齐运行依赖才能测。这与 `screenshot_mask/geometry.py` 的取舍同源。

## 关键设计判断

### 区域不绑定「业务动作」，但探索动作必须可配

场景库里的 `Area` 只记一件业务事实：**它在哪**（`rect`）。跳转关系不在区域上——
它属于画面之间的关系，存在库根的 `routes.json`（见「路由独立成表」一节）。
**也没有业务动作字段**——单击、双击、长按由使用方自己实现，
场景管理既不解释也不记录。理由是动作种类可扩展，写进数据结构就要迁移旧库、同步识别
与寻路（它们其实都不关心动作）。

**唯一的例外是探索，而且必须有**：探索是唯一「自己动手」的使用方式，它必须知道怎么
触发区域。原先固定单击，实测踩到三类区域全都会出错：

| 区域类型 | 单击的后果 |
|---|---|
| 滑动列表、轮播、地图 | 画面不变 → 被判「无效区域」，连两次就永久跳过 |
| 需要长按蓄力的按钮 | 单击不触发 → 同上，被误杀 |
| 右键菜单 | 单击打开的是另一个功能 → 写出的边是错的 |

三种失败都**不报错**，只是探索结果悄悄缺了边或指向错误的场景。因此加了
`Area.explore_action` 与 `Area.explore_params`——**字段名带 `explore_` 前缀**，
明确它是探索专用，不参与识别与寻路。

| 动作 | 参数 |
|---|---|
| `click`（默认） | 无 |
| `double_click` | `interval`：两击间隔（秒，默认 0.08） |
| `long_press` | `duration`：按住时长（秒，默认 1.0） |
| `swipe` | `direction`（up/down/left/right，默认 up）、`distance`（帧短边比例，默认 0.3） |
| `right_click` | 无 |

**参数放在独立的 `explore_params` 字典，不给每种动作加字段**：动作种类会继续扩展
（拖拽、滚轮），每加一种就往 `Area` 上添字段会让结构无限膨胀，而它们的取值又必须
各自校验。用「动作 → 参数规格」两张表（`ACTION_NUMERIC_PARAMS` /
`ACTION_ENUM_PARAMS`），新增动作只改表。

**切换动作时丢弃旧参数**：从长按切到滑动时，`duration` 不能留在字典里——它会跟着
落盘，下次读出来看着像「滑动也有个 duration」，而实际不生效。多余键直接丢弃而不是
报错（用户在对话框里改动作不该被拦下）；已知参数**取值非法**才报错，因为那通常意味
着配置文件被手改坏了。

**滑动距离按帧短边折算而非像素**：换分辨率后手势幅度不变，否则同一份配置在 4K 上会
滑出画面。

**动作的执行方式都挑上游现成接口**：长按用 `click(down_time=...)` 而不是手动
mouse_down/mouse_up——后者在异常路径上可能留下一个没松开的按键；双击用两次 click 加
间隔，上游没有跨设备一致的双击接口。

对应的接口命名仍按这条走：导航与探索的 hook 叫 `activate_area`（让区域生效）而非
`click_area`；`TaskBridge.activate_area` 按 `explore_action` 分派，另提供
`area_center` 返回坐标而不点击——外部拿到坐标可以做任意动作。

### 界面文案用英文源串，中文只存在于译文

界面静态文案（按钮、表头、下拉选项、弹窗标题与字段标签）一律写成
`tr("Capture Frame")` 这样的**英文源串**，`msgid` 与它逐字符一致；中文只出现在
`zh_CN` 的 `msgstr` 里。

理由：gettext 的 `msgid` 是源语言那一侧，缺译时的回退结果就是它。若用中文当源串，
缺译的英文用户会看到中文而不是英文原文；且仓库里会出现两套源语言（本能力中文、
既有能力英文），翻译条目重复、术语容易分叉。

**动态文案不本地化**：状态栏提示、错误消息、日志由 f-string 拼出，没有固定 `msgid`
与之对应，保持中文原文、不进 catalog。界面上「静态文案随语言变、动态提示固定中文」
是有意为之——强行本地化动态串只会得到一串查不到的 `msgid`。

页面层没有 `CustomTab.tr()`（四个子页签与两个对话框都是普通 `QWidget`/`QDialog`），
因此有 `translate.tr()` 这一个统一入口：拿得到 `og.app` 就走它的 `tr()`（与页签同一
条链路，含 `ok_ext` 域回退），拿不到（单元测试）就返回原文。

### 特征是一块「形状」，不是矩形

原设计里特征只有一个 `region` 矩形。改成形状 + 掩码的原因是**矩形表达不了画面里的
形状**：圆形按钮的外接矩形四角是背景，不排掉会拉低置信度。实测同一张模板匹配
「四角有干扰元素」的画面，不带掩码 0.9221、圆形掩码 0.9918。

四种形状与它们各自的必要性：

| 形状 | 解决什么 | 为什么不用矩形代替 |
|---|---|---|
| `rect` | 绝大多数 UI 元素 | — |
| `circle` | 圆形按钮、头像、球形图标 | 四角背景参与相关性计算，拉低置信度 |
| `sector` | 扇形进度条、方向指示器 | 扇形是「圆的一部分」，用矩形必含无关区 |
| `polygon` | 不规则图标、贴图轮廓 | 任意形状都表达不了 |

**搜索区域由形状派生，没有独立的 `region` 字段**。另存一个 region 会与形状分叉：
改了形状忘了改 region，模板就与搜索区对不上，表现是「这个特征从来匹配不到」，
不报错且很难归因。

### 圆的半径按帧宽折算，不按两轴各自折算

点与半径存相对比例，x 基准是帧宽、y 基准是帧高。二者不等时，「相对半径 0.1 的圆」
在 1920×1080 下于 x 方向占 192px、y 方向只占 108px。若按相对包围盒裁图，圆会被
上下切掉——实测掩码覆盖率 94.4%，而真圆应是 78.5%。

因此所有几何方法都要求传 `width`/`height`，在像素空间完成旋转与包围盒计算。
修正后覆盖率 78.52%（理论 78.54%）。

### 旋转是「形状可倾斜」，不是「模板旋转匹配」

两种「旋转」的实现代价差 57 倍，必须分清：

- **形状可倾斜**（本设计）：用户给矩形或多边形设一个角度，模板按该角度下的真实
  像素裁出。匹配逻辑完全不变，零额外代价。实测同角度画面得分 1.0000。
- **模板旋转匹配**（未实现）：让同一张模板去找任意角度的画面。实测同一模板匹配
  旋转 20° 的画面只有 0.6337 分；要覆盖需 24 个角度的模板库，单次匹配从 17ms
  涨到 688ms、每个特征占 2.8MB。

游戏 UI 的元素角度是固定的，需要的是前者。

### 掩码的用途是「表达形状」，不是「排除杂物」

与上游 `ZenlessZoneZero-OneDragon` 的做法一致：它的 `TemplateInfo` 用
`template_shape` + `point_list` 描述形状，从形状生成 `mask.png`，与 `raw.png`
一起存。区别只在于它一个特征一个小目录（`config.yml` + `raw.png` + `mask.png`），
本设计把这些字段放进 `scene.json` 的 `shape` 里，模板与掩码放在 `templates/`。

### 编辑区与产物区分离

```text
ok_scenes/        # 编辑区：不入库，随时可改形状/换截图重导
assets/scenes/    # 产物区：入库，运行期只读
```

与上游 `ok_templates/` → `assets/templates/` 的分工同构。混在一起时，「哪些文件
该提交」只能靠一条条 gitignore 反选判断，而漏判的表现是本地实测数据进了发布包。

**两区都只有遮罩后的图**，没有未遮罩副本（见下一节）。

**两区之间没有自动同步**：弹窗里点「保存」写编辑区，配置页点「保存到 assets」才
导出。这是刻意的——编辑随时发生且频繁，导出是明确的一次性动作，且要能拒绝资产
不全的场景（缺掩码的场景被跳过并给出原因，而不是静默导出半成品）。

### 遮罩是「输出脱敏」，不是「输入脱敏」

框架的设计口径是：`screenshot_processor` 只在把图变成文件/推给界面时生效
（`ok/core/screenshot.py` 的 `to_pil_image`），运行期识别一律跑在原始帧上。
调查确认框架里 `screenshot_processor` 只有 3 个使用点，全部在 UI/落盘路径上，
`capture_method.get_frame()`、`TaskExecutor.next_frame()`、`base_task.frame`
没有任何一个施加遮罩。

本能力沿用这个口径，**不在取帧层涂黑**。原因是涂黑会让遮罩区内的特征永远无法
匹配，而那不是「安全换性能」，是把功能改坏：

```text
get_frame() → 原始帧 ──┬→ 识别 / 探索 / 坐标换算（原始像素 ✓）
                      └→ 落盘与展示 ─→ apply_global_mask → preview.png（已脱敏 ✓）
```

因此只有两处调 `apply_global_mask`：保存 `preview.png`、以及界面展示的预览图。
编辑弹窗里保留两帧（`_raw_frame` 裁模板、`_display_frame` 展示与落盘），模板必须
用真实像素——从遮罩图裁出的纯色块模板在 `TM_CCOEFF_NORMED` 下恒得 1.0，等于永远
命中。

**原始帧一律不落盘**。它是整帧未遮罩截图：即使目录不入库，`export_library` 这类
按目录打包的动作也会把它带出去。因此它只在弹窗内存里存在，用于当次裁模板。

重新打开已有场景时用 `preview.png` 当模板源——落在遮罩区内的特征本就会被判为无效
（裁出纯色块，`template_has_texture` 会拒绝），配置页另有重叠警告。

**已知限制**：若将来要求「运行期也拿不到 UID」，只能在框架的 `next_frame` 处统一
施加，那属改上游文件，需登记 `divergence.yaml`。本能力不自行引入该分歧。

### 特征必须有搜索区域，且是硬性要求

实测发现性能差 **18 倍**（3840×2160 下全图 0.470s vs 限定 25% 区域 0.026s；见实测证据 3）。
原探索记录把「搜索区域存相对比例」定位为**鲁棒性**措施（应对黑边/边框偏移），实测后升级为
**性能 + 鲁棒性双重硬要求**：没有搜索区域的特征不允许保存。

依据：用 30 个场景、每场景 1 个必需特征、限定 30% 区域估算，全扫一轮 0.27s（9ms/场景）；
若不限区域则约 14s，导航时每轮判断都不可接受。

### 必需特征短路顺序按「区分度」排

一个场景的必需特征之间是 AND 关系，顺序不影响结果，但影响耗时：把最容易失败的特征排前面，
不匹配时能提前中断。区分度用「历史命中率」估计——库内维护每个特征的 `hit_count` 与
`attempt_count`，比值低者先跑。首次全为 0.5，随使用自动收敛。

### 界面层碰设备必须派到执行器线程，否则界面永久卡死

界面上任何会走到 `task.ocr` / `task.click` / `task.sleep` 的动作（调试页的识别、
试走、跳转，流转页的试走），**都必须经 `TaskBridge.run_on_executor` 派到执行器
线程**，不能直接在 GUI 线程调。

**卡死链路**（实测确认，四环相扣）：

| 环节 | 事实 |
|---|---|
| 执行器初始状态 | `TaskExecutor.__init__` 里 `self.paused = True`，未点「开始」时一直如此 |
| 任务方法的前置检查 | `task.ocr` 第一行就是 `if self.blocked_by_pause(): self.executor.sleep(1)` |
| 暂停判定的线程语义 | `blocked_by_pause` 只在「执行器线程 + job 有 `ignore_pause`」时返回 False |
| `sleep` 的形态 | 暂停态下是 `while True`，只在暂停解除时退出 |

四环合起来：GUI 线程调 `task.ocr` → 判定暂停 → 进 `sleep` 的 `while True` → 等待
解除暂停 → 而解除要执行器线程推进 → 执行器线程空闲但 GUI 占住了整个应用的事件
循环 → **没有任何恢复路径，只能杀进程**。

**为什么派发能解决**：`executor.submit` 的 job 默认 `ignore_pause=True`，而
`blocked_by_pause` 对「执行器线程上的 job」放行，所以 job 在暂停态下照常执行。
上游自己的诊断页也是这么做的（`ok/ui/qt/debug/diagnosis_page.py` 的 `run_ocr`，
注释写的是「A job on the executor gets frames even while the executor is paused」）。

**为什么整段一起派发而不是逐次**：点击 → 等待 → 识别要在同一个 job 里完成。拆成
三次派发会让每一步各自排队，「点完立刻识别」的时序依赖被打断，而且中间可能插进
别的 job。

**为什么目标函数里不能碰 Qt 控件**：它是跨线程执行的。结果通过返回值带回本线程
再更新界面；在 job 里改控件会直接崩溃。

### 等待不能用 `task.sleep`，它在窗口非前台时永不返回

`TaskBridge.wait()` 用 `time.sleep`，**不调 `task.sleep`**。这与「必须走任务方法」的
直觉相反，但 `TaskExecutor.sleep` 有一个不保证退出的循环：

```python
while True:
    if not (self.blocked_by_pause() or (self.current_task is not None
            and self.current_task.paused) or self.interaction is None
            or not self.interaction.should_capture()):
        to_sleep = self.pause_end_time - time.time()
        if to_sleep <= 0:
            return              # ← 唯一正常出口
    else:
        self._wait_for_activity(0.1)
```

`should_capture()` 在 `Pynput` / `PyDirect` / `ForegroundPostMessage` 里返回
`hwnd_window.is_foreground()`。**用户点调试页的按钮时焦点在调试页上，游戏窗口不在
前台**，该判断恒为 False → 永远进不到 return → 每 0.1 秒空转一次，永不返回。实测表现
就是「点了『点击并观察』整个界面卡死」。

而 `blocked_by_pause()` 那层豁免（job 的 `ignore_pause`）只解「暂停」不解「前台」，
所以上一条的派发方案对这个问题无效——**两处都必须处理**：

| 阻塞源 | 解法 |
|---|---|
| 执行器暂停（`blocked_by_pause` 死循环） | 派发到执行器线程 + job 的 `ignore_pause` |
| 窗口非前台（`should_capture` 死循环） | `wait` 改用 `time.sleep` |

**为什么 `time.sleep` 在这里是对的**：`sleep` 原本的设计意图是「等用户把窗口切回前台
再继续」，但我们这里的等待是「点击后等画面稳定」的固定时长——卡住不动的结果比多等两秒
糟得多，且此时画面本来也没在被操作。在执行器线程上直接阻塞是安全的：该线程只跑这一个
job，不影响 GUI；GUI 在 `future.result(timeout)` 上等，超时后仍能拿回控制权。

### 识别耗时只测「归一化 + 扫描」，不含取帧与排队

`MatchResult.duration` 由 `recognize()` 内部用 `time.perf_counter()` 计时，起点在
归一化之前、终点在返回之前。界面显示成「耗时 64 ms」。

**为什么不把取帧和线程排队算进来**：界面拿这个数字要回答的是「识别本身快不快」。
把取帧（设备往返）与排队（执行器等别的 job）算进去，同一台机器上会随负载大幅抖动，
看不出任何优化效果。实测 20 场景 / 40 特征：纯扫描 64ms、归一化 23ms——两者都是
十毫秒级，合并计时才够量级判断。

**`duration == 0.0` 显示「未实际识别」**：库为空或缺基准时 `make_matcher` 返回的
兜底函数从不真正扫描，它的 `MatchResult` 也不带耗时。显示「耗时 0 ms」会被读成
「快到不需要时间」，与事实相反。

**实时刷新与按钮共用同一处展示**：两者都走 `_on_identify`，所以耗时对两者同时生效。
另有 `_identifying` 互斥——刷新间隔 800ms 可能短于一次识别，没有它会在上一次还没
返回时再发一次，两次结果各写一遍，耗时与当前画面不同步。触发被**丢弃**而不是排队：
排队会积压，放开后连跑好几次。

### OCR 裁剪要外扩 + 补齐到 32 倍数，两道缺一不可

识别 OCR 特征时，`match_text` 在裁出区域后要做两件事：向外扩 `TEXT_PAD = 8`
像素，再把图补齐到 32 的倍数。**两道各自解决一个独立成因，缺任何一道都会有场景
识别不到**，而且失败方式都很难归因。

**缺陷现象**：`ok_scenes/scene-0002` 的「靶场入口」场景识别不到，而同一张
`preview.png` 单独去做 OCR 却能清楚看到这段文字。

#### 第一道：文字离裁剪边界不足 4px 就失效（DB 的 unclip）

先确认了「不是坐标偏移、也不是框太小」——用像素阈值直接量文字墨迹的真实范围是
`(251,82)-(406,120)`，特征框是 `(248,79)-(410,125)`，四边各留 3~5px 余量，完整包裹。
但识别仍然失败。固定宽度、只改上边界看结果：

| 裁剪上边界 | 文字上方留空 | 结果 |
|---|---|---|
| y=82 | 0px | `'五'`、`'分'`（碎片） |
| y=80 | 2px | 空结果 |
| **y=79（特征框原样）** | **3px** | **`'TT'`** |
| y=78 | 4px | `'靶场入口'` 0.998 |
| y=74 | 8px | `'靶场入口'` 0.999 |

成因是 DB 检测器把检测到的文字区域 `unclip`（向外扩张）后作为识别输入，扩张后的框
一旦超出裁剪边界就会被裁掉，文字区域不完整导致检测失败。**特征框画得再准也没用。**

#### 第二道：检测器把输入尺寸吸附到 32 的倍数，且用 `round`

`resize_h = max(round(resize_h / 32) * 32, 32)`。`round` 有一半情况会**向下**取整，
把图压小：

| 原高 | 吸附后 | 变化 |
|---|---|---|
| 40 | 32 | 压缩 20% |
| 46 | 32 | **压缩 30%** |
| 47 | 32 | 压缩 32% |
| 48 | 64 | 放大 |

压缩后笔画糊在一起，识别直接失效。**这和 `pad` 是互相独立的**：原框高 49 外扩到 65，
`round(65/32) = 2` 仍会压到 64；原框高 25 外扩到 41，会压到 32（压缩 22%）。实测
`round` 在 468 个高度里有 **232 个（50%）会压缩**，靠调 `pad` 只是碰运气避开。

**解法：我们自己按 `ceil` 补齐到 32 的倍数**。补齐后检测器的吸附变成**恒等**
（已验证 1..499 全部成立，零例外），压缩从结构上不可能发生。代价是平均放大 1.18 倍、
最坏 1.94 倍——换「永不压缩」这个确定性值得。这也是用户指出的关键点：
不能用四舍五入，必须向上取整。

**补齐用 `BORDER_REPLICATE` 而不是缩放**：在右侧与下侧复制边缘像素，不改动已有像素。
若用 `cv2.resize` 拉伸到目标尺寸，文字会被拉伸变形，等于换了个新问题；横纵拉伸比
不同时字还会被拉宽或压扁。

#### 试过但否掉的做法

| 做法 | 为什么不用 |
|---|---|
| 只外扩 `pad`（不补齐） | 50% 的高度组合仍会被压缩，靠调参碰运气 |
| 把整块区域放大 2 倍 | 能同时绕过两道问题，但那是用「碰巧放大到 64 以上」实现的，且 OCR 处理面积翻 4 倍 |
| 加很大内边距（40px+） | 会把邻近文字框进来（实测识别出 `'on\tests\testb'`），还要按坐标二次筛选 |
| 整图 OCR | 每帧处理全画面，比裁小图慢一个数量级，而识别链路每轮都要跑 |

### 相似度：运行期短路，调试页全量，两套不能混用

识别结果表要按相似度排序，而相似度来自「特征置信度」。这里有一个不易察觉的陷阱：
`evaluate_scene` 为了省时间会**短路**——首个必需特征不中就直接返回，后面的特征
根本不评估。

于是「已评估特征的置信度均值」在不同场景上平均了**不同数量的样本**：一个全中的场景
平均了 5 个，一个首特征即失败的平均了 1 个。两者数值不可比，拿它排序会失真。

实测一组能让排序**完全反转**的数据：

| 场景 | 特征数 | 短路相似度 | 全量相似度 |
|---|---|---|---|
| A | 1（命中一半） | 0.617 | 0.617 |
| B | 4（首个不中，其余全中） | 0.009 | 0.752 |

按短路值排，B 掉到最后；按全量值排，B 应该排在 A 前面——B 实际上有一半以上特征很像。

**因此分两条路径**：

| 路径 | 用哪个 | 为什么 |
|---|---|---|
| 运行期识别 | `evaluate_scene`（短路） | 实测 50 场景 × 2 特征：短路 4ms、全量 189ms，差 47 倍。导航每轮都判断，慢两个数量级不可接受 |
| 调试页展示 | `diagnose_scene`（全量） | 人点一下等半秒无所谓，换来可比的相似度与可信的排序 |

`TaskBridge.diagnose_blocking` 在**同一帧**上先跑一次正式识别（保证「命中哪个场景」
与运行期一致），再对每个场景做全量评估，结果放进 `MatchResult.diagnostics`。
`details_by_similarity` 优先用 `diagnostics`，没有时才退回 `details`。

**汇总识别本身也要关掉首中即停**：`diagnose_blocking` 内那次 `recognize()` 必须传
`MatchOptions(stop_on_first=False)`。

历史缺陷：初版只把「每个场景的全量相似度」算进了 `diagnostics`，而汇总那次
`recognize()` 仍用默认 `stop_on_first=True`。后果是命中第一个场景后循环就 break，
`details` 里只有一条，表格前先渲染 `len(result.details)` 行——于是**整张表只显示
一个场景**。用户看到的是「只匹配了第一个」，实际上 `diagnostics` 是完整的，只是没用上。

运行期 `make_matcher` 仍用默认值 True：那里每轮都要判断，不能为完整性牺牲速度。

#### 场景列显示「名称（id）」，名称随明细带出

结果表第一列与状态行都显示 `靶场入口（scene-0002）`。

**名称放在明细元组里**（第 7 项，追加在末尾），不由界面另查一次库：界面查库要多一次
IO，且可能取到一个刚被删掉的场景；而 `evaluate_scene` 手上就有 `Scene` 实例。
**追加在末尾而不是插在前面**——`detail[0..5]` 的位置是既有契约，多个调用点（含测试）
按位置读取，插在中间会让 `missing` 与 `similarity` 的语义整体错位。

**名称等于 id 时不重复显示**：新建场景默认就是这个状态（`Scene.__post_init__` 在
name 为空时填 scene_id），直接拼会显示成 `scene-0002（scene-0002）`。

**列宽用「场景列 Stretch + 数值列 ResizeToContents」**：数值列内容最多三四位，不需要
弹性；反过来（场景列固定、数值列 Stretch）会让名称被截断、右侧却空出一大片留白。

**为什么结果表必须只读**：它展示的是「这一次识别算出来的东西」，编辑它没有任何落点
——写回场景库？还是改本次结果？两种解释都说不通，而可编辑的表格会让用户以为改了有用。
控件级 `NoEditTriggers` 覆盖不到 F2 与部分平台的右键菜单，所以每个 item 也去掉
`ItemIsEditable`，双重保证。

### 帧归一化只做一次

一次 `cv2.resize` 到库基准分辨率（3840×2160 → 1920×1080 实测 12ms），之后所有场景匹配
复用同一帧。模板不缩放：模板尺寸是裁剪时的真实像素，缩放模板会反复插值、失真累积。

点击时坐标乘回当前分辨率：`x_click = x_base * (frame_w / base_w)`。

### 基准分辨率三道判断：空库立基准、截图准入、保存前全面检查

基准分辨率是识别链路的唯一参照系：所有相对坐标按它换算成像素，运行帧也按它缩放。
它一旦与采集时的画面构造成不同比例，特征框在运行期就会整体错位——而错位**不报错**，
表现是「这个场景从来识别不到」。

历史缺陷：基准只在「`has_resolution()` 为假」时写入。那条分支只在库里还没有任何记录
时成立，于是第一张图的分辨率成了永久基准，之后换窗口尺寸或换采集分辨率都不会更新。
实测库里 `library.json` 是 `1918×997`（1.9238），而两张 `preview.png` 都是
`1280×720`（1.7778）。更隐蔽的是：编辑器存相对坐标与画框都用同一个基准，两个错误
互相抵消，画布上看不出异常，只有运行期会错。

因此分三道判断，判定逻辑集中在 `resolution.py`，界面只负责「问用户」：

| 时机 | 判断 | 不通过时 |
|---|---|---|
| 库里还没有场景 | 用当前帧立基准 | — |
| 已有场景，准备截图 | 宽高比与基准一致 | 弹窗说明并**拒绝**写入 |
| 点「保存」同步到产物区 | 逐个场景核对 `preview.png` 尺寸 | 弹窗列出全部问题场景并**中止导出** |

**宽高比与尺寸分开处理**：比例不同是硬错误（换算出的坐标不可信，必须拒）；比例相同
但尺寸不同只提示（识别时帧会等比缩放到基准，结果正确）。混为一谈会让「换个分辨率重拍
同一画面」这种正常操作被拦住，而那种情况本来没有问题。

**保存前的检查排在最前**（早于覆盖确认框）：导出是「入库、随包分发」的动作，把错位
数据发布出去比本地留着更糟。放在确认框之前，用户不会先点「覆盖」再被拦下。

**只读 PNG 文件头取尺寸**：`preview.png` 在 4K 下有几 MB，逐个整幅解码会明显拖慢检查。
`store.image_size` 读 IHDR 的宽高字段，并要求签名与 `IHDR` 都在场——扩展名被改成
`.png` 的其它格式会读出一对垃圾宽高，那种「看起来有尺寸」的误判比读不出来更危险。

### 返回关系由探索自己发现，不要求用户额外配置

用户给每个场景标好交互区域（含返回按钮）之后，探索应该能自己把「点哪个区域会到哪」
全部探出来——包括返回边。原始实现做不到，因为它**依赖「返回边已经存在」**才能回退：

1. 点进新场景 B；
2. 想把画面带回 A 继续探 A 的其余区域，查 `graph.return_step(B)`；
3. 查不到——B 的返回按钮还一次都没点过，路由表里没有那条边；
4. 放弃，B 与 A 的剩余区域全部跳过。

表现就是「点一次、跳转一次就结束了」。这是**代码问题而不是配置问题**：返回区域就在
那里，只是没被探出来。

现在的做法是三步：

| 阶段 | 做什么 | 为什么 |
|---|---|---|
| 正常展开 | 点当前场景的每个可探测区域，记下边 | 与原来一致 |
| **探路** | 回退失败时，在当前场景里挑一个**还没有结论**的区域点一下 | 把「返回按钮通向哪」发现出来 |
| 重新规划 | 探完回到循环顶部重判位置 | 探路可能点进了更深一层，必须重新判断 |

三个配套约束缺一不可：

- **`expanded` 的语义是「探完了」不是「开始过」**。半途因回不去而中断的场景不进
  `expanded`，重排队后还能再试。用「开始过」会把它们永久锁死。
- **重排队但不能无限重排**。真实环境可能存在配置缺失的场景（真的没有返回按钮）。
  每个场景最多重排 3 次，超了就如实报「无法回退」——这是「配置没配完」的正常表现。
- **回退阶段不再用正向路径**。正向走会把人送回刚离开的场景，形成
  「进 B → 退到 A → 又沿 A→B 走到 B」的往复，实测能烧光 20 次点击上限。

#### 区域的「结论」有三种，判据只在 `_area_resolved` 一处

判断「这个区域还要不要点」有三个来源：

| 来源 | 含义 | 为什么算结论 |
|---|---|---|
| **可寻路**路由（`manual` / `confirmed`） | 确认过「点它能到哪」 | 再点一次只会得到同一条边 |
| 本轮 `result.edges` | 这一轮已经点过 | 同一轮重探只是白烧点击 |
| `result.invalid_areas` | 点了没反应 | 再点不会得到新信息 |

**`explored` 候选边不算结论**。它是待人工确认的候选，不是最终事实；当成结论的
后果是重跑探索时起点场景一个区域都不点，摘要只有「采集 0 条边」——用户看到的
就是「点一下探索立刻结束」。产物区里历史遗留的探索边尤其容易触发：那些边既没被
应用、也不参与寻路，却会永久挡住重新探测。

`_scene_exhausted` 直接复用 `_area_resolved`，两边各写一套判据时会出现「区域都跳过
但场景不算探完」，同一个场景被反复排队重试。

一个区域都没点、也没采到任何东西时，探索会显式发一条 `warn` 说明原因（没有可探
区域 / 全部已确认），不靠摘要里的「0 条边」让用户自己猜。

#### 队列耗尽 ≠ 探索完成：`incomplete` 与目标重启恢复

**重启的目标是「重置被操作程序的状态」，不是「重跑任务」**。探索卡在一个回不去的
画面（草稿或未识别画面）时，任务不中断：重启目标让游戏回到可探索的初始状态，队列、
已展开集合、点击计数与本轮已采集的边全部保留，随后从当前队列继续。

停止原因是收尾的**事实描述**，与中途重启是两件事：

| 类别 | `stop_reason` | 是否重跑整轮 | 原因 |
|---|---|---|---|
| 正常结束 | `completed` | 否 | 所有可探区域都已有结论 |
| 未完成 | `incomplete` | 否 | 还有场景没探完；中途恢复已经尽力，重跑只会重复劳动 |
| 启动失败 | `no_start_scene` | 是（重启目标后重跑） | 尚无任何进度，重跑等价于继续 |
| 用户设定的截止 | `max_scenes` / `max_seconds` / `max_clicks_per_scene` | 否 | 用户主动设的上限 |
| 用户中止 | `cancelled` | 否 | 用户点了中断 |

异常（取帧/点击抛错）按 `no_start_scene` 同等处理：重跑一轮。

**队列空了不代表做完了**。回不去时场景会被跳过，队列照样耗尽，但那些场景的可探区域
一个结论都没有。收尾判据 `_unfinished_scenes` 与 `_scene_exhausted` 同源，避免「一个
说探完、一个说没探完」两套口径；有未探完的场景就记 `incomplete`，并发一条 `warn`
列出它们。

**中途重启的触发条件**（`_restart_for_navigation`）只有一条：**当前画面本身无法离开**
——未识别画面，或草稿。真实草稿只有图和特征、没有区域，没有返回按钮可点，
`_discover_exit` 再怎么探路也走不出去。当前是正常场景却导航失败时不重启：那是路由
缺失，杀进程补不出边，只会把进度推倒重来。

重启成功后先等目标回到**可识别**画面（启动动画/加载画面也能取到帧，立刻重试会把
加载画面当成「仍然回不去」，白烧重启次数），再重试 `_go_to` / `_ensure_at`；队列与
进度不受影响。失败或次数用尽时按原来的「跳过 + 重新排队」处理。

**重启必须锁定目标路径并重新绑定窗口**，不能沿用「当前选中设备」：

1. **优先锁定「当前已绑定窗口」的 exe**（`bound_target_path`）——那是探索实际
   在取帧与点击的应用。只有还没绑定成功时才退回 `target_status()`。选中项可能
   被框架在目标退出后回落成前台窗口，而绑定窗口不会凭空换应用。
2. 目标被 kill 后，原设备条目从窗口列表消失，框架的 `get_preferred_device()` 会
   回落到「第一个 connected 窗口」——实测回落到微信 / 输入法 / 启动器 / Unity Hub。
   因此路径在第一次重启前解析一次并锁定，后续所有重启都只认它。
3. 启动后**不能**直接 `do_refresh()`（它内部会 `do_start()` 再次走回落逻辑）。
   先刷新窗口列表，按 `full_path` / exe 名找到目标的新窗口（同 exe 有多个窗口时取
   面积最大的），显式 `set_preferred_device` + `do_start()`。
4. **`set_preferred_device` 之后必须校验选中项真的切到了候选窗口**：候选可能在
   后台刷新中消失，此时它会静默回落到首个 connected 窗口，随后 `do_start` 就把
   捕获绑到别的应用上。校验不一致时直接判失败，不继续。
5. 取帧前还要校验 `hwnd_window.exe_full_path` 仍指向目标；不一致就继续等，直到
   超时判失败——绝不在别的应用画面上继续探索。

**中断要能打断重启**：`restart_target` 在 kill 前、启动前、等待窗口与取帧的每一轮
都检查 `should_stop`；任务层在异常分支与重启前也检查，已取消时按 `cancelled` 收尾，
不再重启、也不把异常抛给执行器。`SceneExplorer` 在请求重启前与重启等待结束后同样
检查，避免用户点了「中断」还在继续点击。界面侧的中断按钮直接作用于**启动时保存的
任务实例**，不再依赖 `get_task` 反查——热重载或类对象不一致时反查可能拿不到实例，
表现就是「点了中断没反应」。

重启本身是破坏性操作（杀进程再启动），因此上限由 `max_restarts` 约束；次数写进
`ExploreResult.restarts`，摘要与结果弹窗都会带上「重启目标 N 次」。开关关闭时任务
不注入重启 hook，探索器按原逻辑跳过卡住的场景。

**草稿编号必须避开已有草稿**。原先用「本轮新场景数 + 1」取号，而上一轮落盘的
`draft-0001` 已存在、但不在本轮的 `new_scenes` 里，编号会从 1 重新开始，把同名草稿
整目录覆盖——用户确认前的画面就丢了。现在 `_next_draft_id` 取「已认识草稿（含运行时
加载的）最大编号 + 1」，本轮内不会重号。

##### 初始方案与实测证据（原 scene-target-restart，2026-11-19）

本能力最初以独立文档立项（原目录 `scene-target-restart/`），但代码、任务与测试全部
落在 `scene_manager` 内。2026-11-23 已并入本节，不再有第二个能力目录。

**要解决的问题**：场景探索依赖目标程序持续在线。目标崩溃、掉线或被关闭后，探索只能
以 `no_start_scene`（取不到画面 / 识别不到起点）或取帧、点击异常结束，当前没有恢复
手段，用户必须手动重开目标再重新点一次。

| 方案 | 做法 | 代价 | 前提 |
|---|---|---|---|
| A（选定） | 探索任务外层加重试循环：`no_start_scene` 或取帧/点击异常时，用框架接口杀目标、重启、等待并重跑一轮；默认关闭、最多 1 次 | 多一个重试层与 4 个配置项；重启后需重新识别起点 | 目标是 Windows 且能由主应用启动 |
| B | 只在探索开始前自动启动，不做中途重启 | 改动小 | 目标只在启动阶段异常；无法覆盖探索中崩溃 |
| C | 同时支持 ADB 模拟器重启 | 杀模拟器会影响多开与串口，恢复链路复杂 | 有模拟器专用重启接口且能隔离实例 |
| 不做 | 保持人工恢复 | 无新增风险 | 目标足够稳定，异常可接受 |

**否决理由**：B 解决不了探索中崩溃这一主场景；C 的风险与实现成本明显高于收益，
在「有模拟器专用重启接口」前不重新评估；不做会让无人值守探索不可用。

**实现手段**：显式扩展点——只调用框架公开能力，不改框架文件、不继承核心类。用到的
框架接口：

- `og.device_manager.stop_hwnd()`：杀已绑定窗口的目标 exe，内部 `kill_exe` 会跳过当前/父进程。
- `ok.util.process.execute(path, arguments, start_method)`：按 `windows.launch_arguments` 拉起目标。
- `og.device_manager.do_refresh(True)`：重启后重新枚举设备、重建窗口绑定。
- `og.app.start_controller.start_device()`：探索前自动启动（未连接时）。

**当时的未解问题与收敛结果**：

| 未解问题 | 收敛结果 |
|---|---|
| `stop_hwnd()` 在窗口未绑定时杀不掉目标 | 已补 `get_exe_path()` + `kill_exe()` 兜底，见偏差 #82 的子节 R1 |
| 重启后设备重连与识别轮询的超时取值 | 由 `restart_wait` 控制，默认 8 秒，可调 |
| 目标重启后停在登录 / 公告画面时无法自动通过 | 列为已知盲区；次数耗尽后保留 `no_start_scene` |

#### 界面统一读编辑区，产物区只服务运行期

两个库的分工是**界面 / 运行期**，不是「探索读两区」：

| 使用方 | 读写的库 | 原因 |
|---|---|---|
| 场景配置、场景路由、探索、草稿、调试 | 编辑区 `ok_scenes/` | 用户正在编辑的那份；刚连的边、刚建的场景必须立即可见 |
| 「保存」/ 导出 | 编辑区 → 产物区 `assets/scenes/` | 唯一一次写产物区的动作，随包分发 |
| 运行期任务（`SceneGotoTask`） | 产物区 | 游戏里实际跑的是已导出的那份 |

因此 `TaskBridge` 在界面路径（`SceneManagerTab._build_bridge`、`SceneExploreTask.explore`）
一律注入编辑区实例；`SceneGotoTask` 保持默认产物区。此前调试页桥接用的是产物区，
刚连好的边在调试页提示「没有可用路径」，就是这条边界混用导致的。

`TaskBridge._merged_routes()` 仍保留合并逻辑（编辑区覆盖产物区），但界面路径传入的
两库都是编辑区，结果就是编辑区自己的路由表；它的价值在于运行期任务若复用同一桥接时
仍能看到编辑区未导出的边。

**界面上所有面向用户的场景文本都带名称**：统一 `名称（scene-0001）` 形式，不裸
显示 id。只有两类例外：名称与 id 相同（旧库没起名）时只显示 id；场景读取失败时
只能显示 id（此时没有名称可读）。覆盖的位置：

| 位置 | 实现 |
|---|---|
| 路由页表格、提示行、下拉 | `FlowPage._label` |
| 探索页选中行、问题摘要、新草稿 | `ExplorePage._scene_label` / `_scene_name` |
| 调试页场景/区域下拉、识别结果、试走结果 | `_scene_label` |
| 导航结果（no_path / 到达 / 回退失败） | `SceneNavigator._label` |
| 导航路径描述 | `path_description(labels)` |
| 探索事件与任务日志 | `SceneExplorer._label`，日志头不再拼 id |
| 分辨率检查与导出跳过清单 | `tab.py` 内联查询名称 |
| 场景编辑器区域标签的目标 | 一次 `load_library()` 建 id→名称映射 |

#### 调试页的长结果文本必须换行

调试页三条结果标签（识别、试走、完整跳转）与状态行都开 `wordWrap`。**不换行时
`QLabel` 的最小宽度等于整段文本宽度**，而 Qt 会把子控件的最小宽度逐级并进页面的
最小宽度——完整跳转成功后写进去的是整条路径（十几段「A --区域--> B」），实测单行
宽 6600px，页面最小宽度被撑到同一量级，同一行右侧的「开始」按钮被推出可视区，
用户看到的是「按钮不见了」。开换行后最小宽度只取决于最长的不可断词，页面回到
窗口宽度内，长路径折成多行显示。

这条与「缺失特征列单行省略」相反，但理由一致：**表格行高必须恒定以便横向扫读，
而结果标签是读完整句子的地方**——路径被省略就等于看不到中间跳到了哪。

#### 探索内部的路由表要实时更新

`_remember_edge` 原先只更新规划图，没更新路由表。而「区域有没有结论」读的正是路由表
——于是刚探到的区域仍被当作没结论，下一轮重探、再跳走、再回退，循环到点击上限。

路由表由调用方传入（`SceneExplorer(..., routes=table)`）。**未传时用的是模块级共享
空表**，此时不能往里写：一次探索的边会漏到下一次甚至别的实例。用 `_owns_routes` 区分。

### 探索的「无跳转」判定复用稳定帧判据

判定「点击后离开了原场景」需要先确认画面已稳定，否则动画中的中间帧会被误判成新场景。
稳定判据直接复用框架 `patches_changed` 的阈值（单像素差 >8 计变化，`mean(diff) > 3.0` 或
变化像素占比 > 0.1 判为仍在变），叠「连续两帧都判稳定」。

不自己定阈值：「连续两次无跳转」与「连续两帧稳定」两处判据若用不同阈值，会出现
「判定为稳定了但仍在动画中」的自相矛盾，且两个数字要各自调参。同一判据只有一个来源。

### 路由独立成表：场景只描述画面，不描述跳转

场景信息只该回答**「这个画面长什么样」**：识别特征、可交互区域的定义、探索时用什么动作。
「点这个区域会到哪个场景」「点完等多久」属于**画面之间的关系**，落在库根的
`routes.json`（模块 `routes.py`），键为 `(场景 id, 区域名)`。

```json
{
  "schema_version": 1,
  "routes": [
    { "from": "scene-0001", "area": "开始按钮", "to": "scene-0002",
      "after_wait": 1.0, "source": "explored", "observations": 2 }
  ]
}
```

**为什么必须分开**：原先 `target_scene` / `after_wait` / `edge_source` 都挂在 `Area` 上，
于是同一份事实有两处落点——场景文件里一份、流转图里一份。改一处漏一处就分叉，而分叉的
表现是「流转图上有一条边，点下去到不了」，或者反过来「探索探到了，流转图上看不见」。
两者都不报错。

分开之后各自的职责是单线的：

| 数据 | 回答什么问题 | 谁来维护 |
|---|---|---|
| `scene.json` | 这个画面是什么 | 场景编辑器（人工） |
| `routes.json` | 画面之间怎么走 | 流转图页 + 自动探索 |

**场景编辑器里不再有「目标场景」「操作后等待」两项**。这两项现在只在流转图页维护：
选中一条边 → 确认 / 改目标 / 改等待 / 删除。探索跑出来的边以 `explored` 档进入表格，
人工确认后升 `confirmed` 才参与寻路。

#### 键同步是唯一纽带，四类操作必须联动

路由与场景之间只剩 `(场景 id, 区域名)` 这个键。任一处不同步，故障都是**静默的**：

| 操作 | 必须同步什么 | 漏掉的后果 |
|---|---|---|
| 区域改名 | 路由键跟着改名 | 边无故消失；用户以为只是改了名字 |
| 区域删除 | 删掉它的路由 | 留下点不到的边，建图报「不一致」 |
| 场景删除 | 清掉出边与入边 | 悬空边让整个流转图打不开 |
| 草稿转正 | 改写所有指向旧 id 的边 | 建图抛「悬空边」，界面却提示「请检查是否被手工改动」 |

最后一条最容易漏：`promote_draft` 只改草稿自己的 id 时，父场景那条指向 `draft-0001` 的
边就成了悬空引用。转正还要顺手把该场景的出边与入边一起升为 `confirmed`——用户确认
「这个画面是对的」，等于确认了「点父场景那个按钮能到这里」，不该让他再确认一次。

#### 旧库的边在加载时迁移

升级前的库把边挂在区域字段上。`Area.from_dict` 已经不读那些字段，因此
`SceneLibrary.load_library()` 首次运行时会读原始 JSON 把边搬进 `routes.json`
（`migrate_legacy_edges`）。不迁移的话，用户升级后会看到**所有手工配的边凭空消失**，
而且没有任何报错。

迁移是幂等的，且**不覆盖路由表里已有的条目**——表是新的权威来源。

### 边分三档来源，寻路只走两档

`manual`（人工配）/ `explored`（探索产出待确认）/ `confirmed`（人工确认过的探索边）。
寻路只用 `manual` 与 `confirmed`。理由：探索是无人值守跑出来的，一条误边会让**后续每一次**
导航都点错地方，而错误表现为「到了奇怪的地方」而非「报错」。

流转图页建图时传 `include_pending=True`，因此 `explored` 的边**会画出来**（用户需要看到
探索探到了什么才能决定确认还是删掉），但寻路仍然只读 `routable_routes()`。

### 探索与场景路由分两个子页签

| 子页签 | 职责 | 内容 |
|---|---|---|
| 场景路由 | 长期维护 | 画布、边表格、保存 / 还原 / 清除全部连线、右键菜单、预览路径、试走一步 |
| 探索 | 一次动作 + 回看 | 启动探索、点击识别参数与探索顺序、候选画布、应用 / 忽略 |

**库级导入导出挂在页签条最右侧**：它操作整份场景库，不属于任何单个子页签。
原先放在场景路由页，用户在配置页或探索页都找不到入口。现在作为页签条右侧的
两个按钮，所有子页签下都可见。**必须在所有页签添加完之后再追加按钮**：
`TabStrip._insert` 总是插在「倒数第一项之前」，先加按钮会让页签插到按钮前面，
顺序变成「导出、页签…、导入」；页签加完后布局是 `[页签…, stretch]`，此时追加
的按钮落在 stretch 之后，才是「页签靠左、中间空白、按钮靠右」。

原先两者同页，探索结果区会把边表格挤出可视区：用户看到「采集 12 条边」，
却找不到可选中确认的行。两者对界面的要求也相反——路由页要尽量大的画布与表格，
探索页要尽量大的文本区。

**参数为什么放探索页、不放主窗口设置**：主窗口设置属上游框架，扩展写进去会产生
上游差异，每次合并都可能冲突；而且这两个参数只服务场景探索。参数原先常驻页面上方，
两行控件会把画布压矮，现收进「参数」按钮的弹窗，改一项存一项，不设「应用」按钮。

**探索摘要为什么改成弹窗**：摘要、图例说明与「注意」原先常驻在画布上方，四行文字
长期占掉约 80px 画布高度，而它只在探索结束那一刻有用。改为探索结束弹一次
`Dialog`，点确认后关闭。弹窗用阻塞 `exec()`，**不加超时自动关闭**——自动化流程
（含全量测试）本就应该自己处理弹窗；测试在 `_page` 里把 `_show_result_dialog`
替换成文本收集器，避免 `exec()` 阻塞。摘要文本由 `_result_lines` 生成，测试直接
断言文本，不依赖弹窗是否显示。

#### 探索页是候选池，场景路由页是最终图

两个页面看到的不是同一份边：

| 页面 | 画什么 | 职责 |
|---|---|---|
| 探索 | 已生效边作底图，叠加历史待确认（紫色虚线）与本次新发现（橙色加粗虚线） | 启动探索、审核候选、应用 / 忽略 |
| 场景路由 | **只画 **`manual` / `confirmed` 的边 | 最终结果，改目标、设等待、删除 |

探索页的画布仍然保留拓扑上下文：新边接在哪个节点、与已有路径是否重叠，一眼能看出；
但它不会污染最终结果页。路由页打开时看到的就是当前真实能走的路，表格也只列可寻路由。

**画布坐标只有两种单位，不能混用**：`graph.layout()` 给的是布局单位，要乘
`NODE_GAP` 才是画布坐标；`remember_positions()` 返回的已经是画布坐标。刷新时把
后者再乘一次间距，节点会飞到几万像素外，视图自适应缩到极小——整块画布看起来
是空的。另一个同类坑是控件尚未拿到真实尺寸时 `fitInView` 会把缩放算成 0；
两者都表现为「画布全白、没有任何报错」，因此 `set_graph` 区分两种输入，
`_fit_scene` 在空视口上只记待办、等首次 `resizeEvent` 再补。

候选的操作在探索页完成：单击或 Ctrl+点击选中连线，**右键选中的线**弹「应用 / 忽略」
（多选时作用于集合里全部待确认边），**双击一条候选线**直接应用；画布外只保留
「应用全部 / 忽略全部」，它们作用于**全部待确认候选**（含历史），数量大时各弹一次确认。
应用只把 `explored` 升为 `confirmed`，忽略只删未生效的候选，已有 `manual` / `confirmed`
原样保留。画布空白右键提供「重置视图 / 自动布局」，与路由页一致。

**重复采到已生效路径不降级**：探索会重新走一遍已知链路，`save_edge` 若一律写
`explored`，会把已确认的边打回待确认。保存时先看已有档位，可寻路则保留原 `source`。

#### 探索进度弹窗

探索在后台线程跑，原先点完「开始探索」只有底部一行状态，用户不知道跑到哪、还要
多久，也无法中途停止。现在启动后立即弹进度窗：

| 区域 | 内容 |
|---|---|
| 统计行 | 已用秒数、访问场景数、新发现草稿数、采集边数 |
| 事件行 | 最近一条探索事件（正在展开哪个场景、哪条边、为什么跳过） |
| 底部 | 「中断」按钮 |

- **阻塞操作但不阻塞事件循环**：`Dialog` 用非阻塞 `open()` 拉开遮罩，主窗口点不到
  其他控件；`exec()` 会卡住界面，进度就无法刷新。
- **进度来源**：任务侧维护 `progress` 字典，由 `_on_explore_event` 按事件类型累加
  （`new_scene` / `edge`），访问数按出现过的场景 id 去重；界面每秒轮询读取。
- **长事件手动折行**：`QLabel` 的自动换行依赖布局给宽度，固定宽度卡片里长事件会被
  右侧裁掉（实测「返回路径未知，先探…」只显示半句）。`_wrap_event` 按 26 字折行。
- **计时器每秒走**：任务侧 `elapsed` 只在事件发生时更新，两次事件之间可能隔好几秒，
  光靠事件刷新会让计时器停住、看起来像卡死。弹窗用本地单调时钟补足（取任务值与
  本地值较大者），内部 `QTimer` 每 100ms 重绘一次；只有行数变化时才重排高度，高频刷新只更新文本。
- **消息区按行数加高**：`adjustSize` 只按单行算高度，折行后的后几行会溢出卡片。
  消息区基础高度 120px，每次刷新按 `26 × 行数 + 24` 加高并重新居中。
- **中断**：按钮置 `cancel_requested`，`TaskBridge.should_stop` 在每个检查点读它，
  探索器以 `cancelled` 结束。按钮点击后**不立即关窗**——只把按钮改成「正在中断…」，
  等任务真正退出再关闭，避免用户以为已经停下。
- **确认摘要后自动布局**：`show_explore_result` 的确认弹窗返回 True 后调用一次
  `_on_auto_layout`。新边接进来后原手工布局往往已经挤在一起，用户点确认就是想看
  结果，自动重排并写回 `layout.json`。

#### 场景路由页：工作副本 + 保存才落盘

路由页不再改一条写一条，而是加载时克隆整张路由表作为**工作副本**：

| 操作 | 行为 |
|---|---|
| 新增 / 改目标 / 改等待 | 只改副本，边画成**绿色实线** |
| 删除 | 只从副本移除，边画成**红色虚线**（可右键撤销） |
| 保存修改 | 整表写回 `routes.json`，同时保留未展示的 `explored` 候选 |
| 还原 | 丢弃副本，重新从磁盘加载 |

有未保存修改时，页签切换与其它页面的刷新**不会回读磁盘**，否则会把工作副本冲掉；
若期间别的页签改了路由，提示「路由已变化」，由用户决定保存还是还原。

**选中与「待删除」是两件事，样式必须同时表达**：普通选中是蓝色实线加粗；待删除
（ghost）选中仍是**红色虚线**，只加粗。原先选中优先级最高，选中一条待删除边后与
选中普通边完全同形（都是蓝色实线），用户分不清自己选中的是「会被删掉的那条」还是
正常边。

**槽位只按真实边分配，ghost 不参与**：平行边按槽位偏移弯曲，槽位由「同对节点的
边序号与总数」决定。标记删除的边会从「图里的边」变成追加在末尾的 ghost；若它计入
同对的总数，剩下的真实边会从居中槽移到半槽位——用户看到的是「标记删除后线自己
动了」。现在真实边之间按 `(来源, 目标, 区域名)` 稳定排序、只按真实边算总数，ghost
排在真实边束之外（第 k 条 ghost 占「真实边数 + k」号槽），既不挤动真实边，也不会与
真实边重叠成一条看不清的线。

**编辑不重排节点**：编辑路径（改目标 / 改等待 / 删边 / 撤销）重建画布时沿用画布上
的当前位置，而不是回落到自动布局。弹簧布局依赖边集，删一条边会让没保存过位置的
节点整体重算，节点与连线一起跳。

#### 节点图交互与重连

画布按主流节点图约定：左键选择 / 空白框选、Ctrl+左键增减、中键或 Alt+左键平移、
滚轮缩放、右键节点 / 连线 / 空白出菜单、Delete 删除选中连线。

**连线的两端都可拖出重连**：

| 抓住的端 | 活动端 | 落下时 |
|---|---|---|
| 靠近目标端（in） | 入端 | 只需等待时间，改这条边的目标 |
| 靠近来源端（out） | 出端 | 先选新来源节点及其**交互区域**，再设等待 |

拖出 5px 即进入重连，**旧线同时隐藏**：视觉上它已经被拿走，不再与新预览线并存。
松手就完成——落在其他节点上表示重连，落在空白处表示**删除这条边**（只改工作副本，
保存前仍是红色虚线、可右键撤销）。Esc / 右键仍是取消，旧线恢复。

**右键「更改目标」与拖拽同形，但落空语义不同**：从菜单进入时同样**立即隐藏旧边**
（与拖拽的入端重连一致），否则画面上同时有旧边与跟随鼠标的虚线预览，看起来像
「旧的没删、又新建了一条」。区别只在落空：菜单没有拖拽动作，点空白是**取消**而不是
删边——删边只由真正的「拖出后落在空白」触发（`_link_delete_on_empty` 区分两者）。

**编辑已有连线不重置视图**：改目标 / 改等待 / 删边 / 撤销删边触发的重建都保留当前
缩放与视口中心（`set_graph(keep_view=True)`）。原先每次编辑都走自适应「全部节点可见」，
用户刚放大对准的位置会丢，连改几条就要重新找。保留方式是在重建前记录**变换**与
**视口中心对应的场景点**，重建后 `setTransform` + `centerOn`；用滚动条数值恢复会因
sceneRect 大小变化而偏移。加载、切页签、保存后的刷新仍按自适应，保证首次打开能看到全图。

**连线可以多选**：Ctrl+点击在线条集合里增减；多选后 Delete 批量标记删除，右键编辑
主键那条。表格同步只写单行，跳转时用 `_refresh_guard` 挡住 `selectRow` 的
`itemSelectionChanged`，否则表格会把画布的多选集合重新压成单选。

**右键菜单的作用集合**：右键的边在选中集合里时，删除与改等待都作用于**全部选中
边**，不只删触发菜单的那一条。删除的菜单文案带数量（「删除选中的 N 条连线」），
改等待弹一次输入、统一写入每条边。「改目标」仍是单条——把多条边指向同一目标风险
太大，需要逐条确认。

**清除全部连线只改工作副本**：工具栏的「清除全部连线」把 `_working` 整体换成空表，
画布上原有边变成红色虚线（`_deleted_edges` 与 baseline 的差集），保存后才写盘；
点「还原」即可恢复。确认框写明条数与「保存生效 / 还原可恢复」，避免误以为立即落盘。

**切到探索页会重新读库**：路由页保存后 `routes.json` 已变，探索页若不刷新仍画着
上一次加载的旧拓扑，看起来像「删除没生效」。`_on_tab_changed` 在切到探索页时调用
`reload()`；路由页本身不重新读盘，避免丢掉未保存的工作副本。

**框选要自己实现**：Qt 的 `RubberBandDrag` 只选 `QGraphicsItem`，边是自绘曲线，
内置框选永远选不到线。改为 `NoDrag` + 自绘半透明矩形：按下空白记起点，移动时刷新
矩形，松手时用**曲线路径**与矩形求交选中边，同时按本地圆形 `shape()` 判定节点。
节点的命中区也从 `boundingRect` 的方形换成圆形——方形四角（尤其左侧空白）会让
「只框到圆外」的节点被选中。框选后发 `selection_changed`，由页面同步表格与提示行；
Ctrl 框选在已有集合上累加。

右键节点另有「倒序连线」：先定目标（当前节点），再点来源节点并选它的区域——适合
「已经知道要去哪，反过来找入口」的场景。

**悬停、命中与绘制**：悬停时整条边高亮（预选），按下后拖出 5px 才进入重连，避免
单击被误判。命中区用**同一条贝塞尔曲线**扩 14px，而不是按直线或 1.6px 描边，标签
与箭头也带边键。只标 `来源场景 · 区域名`——箭头指向的节点本身就写着名字，再标一次
目标会让边中段挤满文字，平行边靠近时尤其明显。

**标签贴起点端并按走向对齐**：标签不再固定挂在中段 45% 处，而是取路径 5% 处的锚点，
按主导方向决定对齐方式：

| 走向 | 对齐 | 文本位置 |
|---|---|---|
| 左 → 右 | 左缘贴起点 | 线上方 |
| 右 → 左 | 右缘贴起点 | 线上方 |
| 上 → 下 | 顶边中心贴起点 | 线右侧 |
| 下 → 上 | 底边中心贴起点 | 线右侧 |

文字始终从「出发的那一端」开始排列，并且落在线外侧，不压住线条。斜线按
`|dx| >= |dy|` 归入横向或纵向。标签只画文字，不加底框——淡白底在浅色画布上
显脏，也会把短边切成一截一截。标签**仅做展示**：不写边键、不接收鼠标事件，
`_edge_at` 命中标签时直接返回空，点文字不会选中边，也不会用描边命中带兜底。

**平行边按「排序后的节点对」分槽**：弯距不是按每条边自己的方向算的，而是先取
`(min(来源, 目标), max(...))` 的法线，再按该对节点的边序号叠加槽位偏移。按各自方向
算时，A→B 与 B→A 的法线相反、弯距符号再相反，两条曲线会弯到同一侧**完全重合**，
标签也叠在一起。槽位间距 84px，中段实际分开约 42px；自环按序号逐层外扩。

**自动布局与最小间距**：场景路由页顶部「自动布局」按钮、画布空白右键、探索页顶部
按钮执行同一动作——清掉 `layout.json`、按 `spring_layout`（固定种子）重排，再做一次
确定性斥力松弛。间距分两档，并按用户要求连续收紧到「紧凑流程图」的尺度：

| 节点对 | 最小中心距 | 圆间通道 |
|---|---|---|
| 两端都有连线 | `2 × 半径 + 32`（100px） | 32px（96 → 48 → 16 → 32） |
| 任一端是孤岛 | `2 × 半径 + 16`（84px） | 16px（24 → 8 → 16） |

孤岛（度为 0）不参与拓扑阅读，通道只有连线节点的一半；`spring_layout` 的斥力
会把孤岛甩在外圈，间距既远又不均匀。布局后另做一次**孤岛归置**：孤岛按 √n 列排成
主图下方的网格，步长 `孤岛距离 × 1.05`（约 88px），同行同列间距完全一致；只移动
孤岛、不动主图节点。布局单位乘 180 得到画布坐标；自适应留白单独用 40px，不跟间距
一起放大，否则图会被缩得过小。自动布局后的自适应上限用 `ZOOM_MAX`（2.6），节点少、
内容小时会顶格放大，文字更清楚。

**布局尺度要服务「看得清」**：`NODE_GAP` 220、留白 80 时，7 节点环的内容包围盒
约 940×385，缩放只剩 0.88，节点直径约 60px；改成 180 / 40 后同样拓扑是 393×409、
缩放 0.98、节点直径约 67px。间距参数只决定「节点之间多紧」，而 `NODE_GAP` 与留白
决定「整张图占多大」，后者才是缩放的真正瓶颈。

**减少边交叉**：`spring_layout` 不保证无交叉，项目又不带 scipy，无法用
`kamada_kawai_layout`。布局后做一轮确定性**成对交换**：交换两个节点的位置，交叉数
下降才保留（`_reduce_crossings`）。交换不改变两两距离的多重集合，最小间距仍然成立；
只调整位置、不增删节点。节点超过 40 个时跳过，避免 O(n² × E²) 把界面卡住。

**布局按视口宽高比拉伸**：spring 布局是各向同性的，横向视口里可能排成竖长条，两边
大片空白。布局后按视口可用宽高比只拉伸**较窄的那个轴**（不压缩较宽轴，否则最小间距
失效），上限 1.35 倍。上限不能再大：4 倍会把 7 节点环横向拉到 940px，横向间距是纵向
的两倍多，整图又宽又扁——用户反馈「看起来好奇怪」。拉伸发生在松弛之后，拉伸轴上的
间距只会变大。

**重置视图**：自己算比例并显式居中，不用 `fitInView`——后者按 rect 适配后不保证视图
中心落在内容中心，节点少时还会放大到铺满视口。比例上限单独取 1.6（滚轮上限仍是
2.6），保证「包裹全部节点」与「内容居中」同时成立。路由页与探索页顶部各有一个
「重置视图」按钮。

**缩到最小也能自由平移**：场景矩形按内容外扩 ±100000，而不是 ±2000。缩放很小时
视口覆盖的场景范围远大于内容，旧范围会让滚动位置在内容附近被挡住，表现就是
「缩到最小后拖不动」。滚动条仍然关闭，平移只走中键 / Alt+左键。

**画布不显示滚动条**：平移靠中键 / Alt+左键，滚动条纯属遮挡，横竖一律关闭。外层
页签本身是 QScrollArea，且 `QStackedWidget` 会把所有子页的最大高度报给外层；因此
**外层 view 的最大高度在所有子页下都钉在视口高度**，页签本身永不滚动。滚动只发生在
各页自己的滚动区里（配置页的卡片列表、草稿页的表格、画布自己的缩放平移）。配置页
也必须钉住——否则卡片一多，外层先出现滚动余量，滚轮滚的就是整页，标题行与状态行
会被一起滚出视口，而卡片列表自己反而不滚。

**缩放限幅与文字阈值**：滚轮与「重置视图 / 自适应」共用 `[0.22, 2.6]` 的比例区间。
滚轮按 `angleDelta / 120` 做指数缩放，每格 8%（原为固定 15%，连续滚动累积过快、
触控板小增量也会被当成一整格）；夹取后换算成实际倍率，避免在边界附近跳变。
画布右下角常驻显示当前缩放百分比，随滚轮、自适应与自动布局同步刷新。
`fitInView` 本身不受滚轮限幅约束，两个节点时会放大到三四倍、文字撑满屏幕，因此自适应
之后也要把比例夹回区间。缩放低于 0.5 时隐藏节点文字与边标签——此时文字已缩成黑点，
只留圆圈与连线；放大回阈值以上自动恢复。

**节点位置持久化**：拖动结束写入库根 `layout.json`，下次打开恢复；「重置视图」只
缩放，「自动布局」才清掉记录并重新排列。布局文件不导出到产物区——它是编辑
视图数据，不是运行期数据。

#### 探索顺序可选：广度优先 / 深度优先

待展开场景放在一个队列里，**取出端决定顺序**：

| 顺序 | 取出方式 | 适用 |
|---|---|---|
| 广度优先（默认） | 队首 `pop(0)` | 层级关系清楚的库：先把这一层全展开，结果按层排列，容易核对漏没漏 |
| 深度优先 | 队尾 `pop()` | 链式流程（开始 → 关卡 → 战斗 → 结算）：一探到新场景就沿链路走到底 |

参数存在库元数据 `search_order`，探索页顶部下拉切换，随库走；手改坏的值退回
广度优先（只影响顺序，不值得让整库读不出来）。

**初始队列覆盖所有「还有未结论区域」的场景**，不只是起点。用户删掉部分连线后图
可能不再连通，只从起点沿边走的话其余场景永远进不了队列，表现是「当前场景探完就
直接结束」——实测日志里起点场景的区域都已有路由，于是访问 1 个场景、采集 0 条边
就 `completed`。现在起点之外、任一 `explore_probe` 区域尚无结论的场景也排进队列：
能导航过去就继续探，到不了则由 `_go_to` 失败并记 `skip`，不会整轮静默结束。
BFS 把起点放队首保证当前画面先展开，DFS 放队尾。

**「重复场景」不是顺序问题，是判据与兜底的问题**：

- `_ensure_at` 为了回到当前场景会调用 `_discover_exit`，那里可能刚好点掉当前
  待探区域；回到区域循环后必须**再判一次** `_area_resolved`，否则同一区域连点
  两次、日志出现两条相同的边。
- 回退兜底的「任意一条已知出边」必须排除「已走过」和「到不了目标」的目标。
  否则在有环的图上会一圈圈走：实测 `0003→0004→0005→0006→0003` 转了 14 次，
  白等近 30 秒才发现这条环上没有回边入口。排除后直接转去探剩余区域。

#### 探索返回标记：按区域、可多个、只服务探索

原先场景级有 `return_area`（单值），设计意图就是「回退时优先点它」，但它没有
界面入口、真实库里全空，还同时被运行期导航读取。现在改成区域级
`Area.explore_return`：

| 约束 | 做法 | 理由 |
|---|---|---|
| 可多个 | 每个区域一个布尔标记 | 关闭 / 返回 / ESC 都可能回退，硬性单选会丢路 |
| 与探测独立 | 没开「允许探索探测」也能标 | 标记是「回退时点它」，不是「展开时点它」 |
| 布尔开关 | 新建与编辑区域弹窗都用开关（放在动作参数之后） | 两个选项的下拉要先展开再选，开关一次点击就切换 |
| 只服务探索 | `graph.return_step` 不读它 | 运行期导航不该被探索标注改变落点 |
| 不标则照旧 | 候选链自动退到入边反推与已知出口 | 旧库、旧习惯零变化 |

回退候选顺序：标记里**能到达本次目标**的优先（按路径长度）→ 目标未知的标记 →
目标已知但到不了目标的标记 → 入边反推 → 已知出口。一次 `_go_to` 内记录已点过的
`(场景, 区域)`，多个标记互不相通时不会反复点同一个。

**回退也要记边**：标记了但没开探测的区域，正常展开阶段不会点；如果回退时还只
「校验画面变了」而不记录，路由图里就永远没有这条回边。回退命中后按普通探测一样
写入 `explored` 与实测等待，已生效的边不重复写。

### 点击后轮询计时，实测值写进 `after_wait`

点击区域后不再固定等 1 秒，而是按 `Poll Interval` 轮询取帧：
| 轮询结果 | 判定 | 后续动作 |
|---|---|---|
| 识别到别的已知场景 | 跳转完成 | 记录边，实测耗时写入 `after_wait` |
| 画面变化但识别不出 | 可能是新画面 | 交给 `_register_new_scene` 落草稿 |
| 连续稳定且仍在原场景（已过 `click_settle` 兜底） | 没有跳转 | 按 `no_jump_retries` 重试点击 |
| 到 `Settle Timeout` 仍无结论 | 放弃本轮 | 记事件，继续下一个区域 |

**为什么用实测值**：不同跳转的过场时间差别很大——瞬时切页与战斗加载可能差十几秒。
统一写 1.0 秒，前者白等、后者不够等；而这条边的真实需求只有点一次才知道。

两个参数持久化在库根的 `library.json`（`probe_interval` / `settle_timeout`），
随库走而不是随机器走。旧库缺字段时按 0.2s / 5.0s 读取，不报错。

### 配置页对齐模板页签：卡片网格，而不是画布 + 下拉框

原来的配置页是「场景下拉框 + 一块只读画布」。场景到几十个后，下拉框里只能看到一串
名字，想知道每个场景长什么样必须逐个切换；而画布占满整页，实际只用来「看一眼」。

改为上游模板页签（`ok/ui/qt/tasks/TemplateTab.py`）的形态：标题 + 计数 + 搜索框 +
操作按钮，下面是卡片流式网格。一屏能看到所有场景，选中的那张才能操作。

| 控件 | 对齐上游 |
|---|---|
| 标题 + 计数 | `display` + `caption`，同「模板 1」 |
| 搜索框 | 300px 固定宽、放大镜图标，按场景名过滤 |
| 删除 / 编辑 | 选中后才出现（上游的 Delete / Markup 也是如此） |
| 保存 / 截图 | 常驻。截图 = 后台取帧后自动建卡片 |

**卡片只显示缩略图、场景名与场景 id**，不显示特征数、区域数、边数，也不在缩略图上叠画区域框。
理由：卡片是「找到那个场景」的入口，不是信息面板。信息密度高的内容放进编辑弹窗——
那里有画布、有列表、有完整属性。

### 卡片继承上游 ImageCard，而不是复制一份

新增 `pages/scene_card.py` 的 `SceneImageCard(ImageCard)`，只改三件事：

| 项 | 父类 | 子类 |
|---|---|---|
| 名称来源 | 文件名（`splitext(basename(image_path))`） | `scene.json` 的 `name` 字段，右侧跟灰色小字 id |
| 信号载荷 | 图片路径 | 场景 id（`scene-0001`） |
| 副文本 | `features_text` | 固定空串（id 不占这一行） |

**为什么继承而不是复制**：卡片的样式走 QSS 的 `QFrame#templateCard` 与
`QLabel#templateThumb` 选择器，尺寸常量是 `CARD_WIDTH` / `CARD_PADDING`。复制一份
等于把这两套约定抄进本能力，上游一改样式这里就与模板页签不一致，而这种不一致没有
任何检查能发现。继承则自动跟着走。

**副文本为什么传空串**：父类在 `_features_text_full` 为空时会把 `features_label`
隐藏，并相应减少卡片高度。

**场景 id 为什么放名称行而不是副文本行**：副文本是独立的一行，会让卡片固定高出一个
行高（实测 131 → 151px），而 id 与名称是同一件事的两个标识，放同一行读起来是一句
「主页界面 scene-0001」。用富文本让 id 小一号、次要色，视觉上从属于名称；名称过长时
两者能一起自然换行、卡片按需增高（`set_card_width` 走 `heightForWidth`），不会截断。

**名称必须 HTML 转义**：名称是用户输入，含 `<` 或 `&` 时会被当作标签解析，表现为名称
被吞掉一段，而界面上看不出是「名字里有尖括号」还是「渲染坏了」。

**为什么重写鼠标事件**：父类 emit 的是 `self.image_path`，而本页需要场景 id 来定位
`ok_scenes/<id>/`。在同一位置换成 id，调用方不必再反查。

**名称替换后必须重算高度**：父类用文件名算名称行高，换成「场景名 + id」后文字长度变了，
不调 `set_card_width()` 重算会让内容被截断。

### 子页签切换：显式的 key → 控件映射，不靠下标对齐

`tab.py` 用 `TabStrip` + `QStackedWidget` 自组合四个子页签。`_add_page(key, text, widget)`
在加页签的同时把 `key → widget` 记进 `self._pages`，`_on_tab_changed(key)` 先
`setCurrentWidget(self._pages[key])`，再按 key 做该页的 reload。

**为什么不用「页签条下标 == 堆栈下标」的隐式对应**：调试页按 `is_debug_mode()` 决定
是否创建。一旦有人调整创建顺序或加条件页，两边的下标就错位，而错位的表现是「点 A 页签
显示 B 的内容」——不报错，也没人会发现是下标问题。显式映射把「哪个 key 对应哪个控件」
写死在一个地方，加条件页时不需要重新数下标。

**为什么先切控件再 reload**：反过来的话，任一页的 reload 抛异常都会让点击彻底没反应，
用户看到的是「页签点了不切换」，与真正的接线缺失（本轮修掉的缺陷）无法区分。先切过去
则异常只影响该页内容的新旧。

历史缺陷：`_on_tab_changed` 早期版本只做了 reload，**从未调用 `setCurrentWidget`**。
页签高亮会变、数据也会刷新，只有内容永远停在第一页——验收里加 `TestSceneManagerTab`
逐个真点 + 断言当前控件，专门覆盖这一类。

### 滚动边界：外层页签永不滚，配置页只滚卡片列表

`SceneManagerTab` 继承的 `Tab` 本身是 QScrollArea；配置页内部还有一个装卡片的
`QScrollArea`。两层滚动区并存时，「谁响应滚轮」取决于外层有没有滚动余量，而外层的
余量来自 `QStackedWidget` 报出的最大高度——只要不主动钉住，卡片一多就会先让整页
产生滚动范围，用户抓到的是最右侧那根整页滚动条：标题、搜索框与状态行跟着一起滚出
视口，卡片列表自己反而不滚。

因此 `_sync_outer_height()` 在**所有子页**下都把外层 `view` 的最大高度钉在
`viewport().height()`，页签本身不出现上下滚动条。滚动只发生在各页自己的容器里：

| 子页 | 唯一滚动区 |
|---|---|
| 场景配置 | 卡片列表（`ConfigPage.scroll_area`） |
| 场景路由 / 探索 | 画布（自绘，平移靠中键 / Alt+左键，不使用滚动条） |
| 草稿确认 | 表格自身的滚动条 |

**配置页的固定部分不得参与滚动**：工具栏与底部状态行在页面的根布局里，卡片列表
用 stretch 吃满剩余高度。滚到列表底部时页面固定部分的坐标必须不变——这是测试里
「只有列表在滚」的可观测判据；只断言外层滚动范围为 0 不足以排除「内层滚动带动
外层布局」。

**共享堆栈会把任一页的最小宽度并给所有页**：`QStackedWidget` 的最小尺寸取所有
子页的最大值，而横向滚动条是关闭的——任一页出现一条不换行的长文案，其余页（尤其
配置页的卡片网格）都会被推得比窗口还宽，右侧直接裁掉且无法横向滚过去。因此页面里
的说明性长文本一律 `word_wrap=True`：草稿页的整段说明、配置页空态提示都属于这一类。
同一环境下实测草稿页的最小宽度从 772px 降到 376px。

### 新建场景不弹窗，直接落成卡片

点「截图」在后台取帧，完成后自动分配 id 与名称（`场景 N`），插一张卡片；导入图片
同理。用户看到卡片后才决定是否双击进编辑。

**为什么不建完就弹窗**：上游模板页签的「截图」也是直接落一张卡片。弹窗是「我要配这
个场景」的明确动作，与「我先把画面抓下来」不是同一件事——先抓后配更符合实际操作
顺序（常常一次抓好几张再逐个配）。

**序号不复用**：id 由库级计数器 `next_scene_seq` 分配，只增不减。删掉 `scene-0003`
后再新建得到 `scene-0004` 而不是 `scene-0003`，避免边指向被复用的编号。

**名称的序号从 id 派生**（`scene-0005` → `场景 5`），不另起一套计数器。

历史缺陷：名称原先按「现有 `场景 N` 的最大 N + 1」算，与 id 计数器相互独立。库里
一旦出现用户自定义名的场景，两套就分叉——实测库里有 `scene-0002`「靶场入口」、
`scene-0003`「关卡选择」，名称从 1 数起，于是 `scene-0004` 被叫成「场景 1」、
`scene-0005` 叫「场景 2」。用户看到的是「id 是 5、名称却是 2」，而号一旦错开就
再也追不回来。

派生而非双计数器：id 是唯一权威来源，名称跟着它走才不会分叉。前缀固定中文、不走
`tr()`——名称要落进 `scene.json`，是持久化数据，随界面语言变化会让同一场景在不同
语言下叫不同名字。

### 特征与区域的默认名：默认不带前缀，可开关打开场景名前缀

新建特征或交互区域时，属性对话框里的默认名默认是 `特征1`、`区域1`；编辑器顶部的
「名称带场景前缀」开关打开后变成 `靶场入口-特征1`、`靶场入口-区域1`。编号从 1 起、
跳过已占用的。

**为什么默认关闭**：同一场景里连续画十几个框时，`特征1` 比 `主页-特征1` 短，
在 280px 的右侧列表里不容易折行；而且 `feature` 与 `area` 本来就在各自分区里，
归属由分区已经表达清楚了。只有确实需要跨场景对照名称时才打开开关。

**开关状态持久化在库元数据**（`LibraryMeta.name_with_scene_prefix`），与「自动保存」
同口径：它是编辑器偏好，跟着库走，换机器时保持上次的选择；不写进场景文件，避免每个
场景各存一份互相矛盾。

**编号紧贴前缀、不加分隔符**（`主页-特征1` 而非 `主页-特征-1`）：场景名本身可能含
`-`，再加一个会让 `特征-1` 与 `特征1` 两种形态混在库里，用户分不清哪个是自动生成的。

**场景名为空时用 id 兜底**：`Scene.__post_init__` 本会把空名填成 id，但导入的旧数据
可能真的有空名。用 `scene-0009-特征1` 比 `特征1` 好——后者看不出属于哪个场景。

**前缀取名称输入框的当前文本**而不是已保存的 `scene.name`：用户常常先改名再画框，
而改名要保存才落盘，取已保存的名字会生成旧名前缀，与界面显示的当前名称对不上。

### 布尔字段一律用开关，不用「是/否」下拉

属性对话框里的布尔项统一用 `TOGGLE_FIELD`（开关）形态：

| 字段 | 所在弹窗 | 默认 |
|---|---|---|
| 必须（`Feature.mandatory`） | 新建 / 编辑识别特征 | 开 |
| 允许探索探测（`Area.explore_probe`） | 新建 / 编辑交互区域 | 关 |
| 探索返回区域（`Area.explore_return`） | 新建 / 编辑交互区域 | 关 |

**为什么不用两选下拉**：两个选项的下拉要先点开、再选一项，一次判断变成两次操作；
开关直接呈现当前状态，点一下就切换。**新建与编辑必须同形**——同一个布尔项在两个
弹窗里形态不同，用户会以为它们是不同的东西。此前「探索返回区域」只加在编辑弹窗里，
新建完区域找不到入口标返回，只能再双击进一次编辑弹窗。

### 属性对话框的动态参数区：参数行直接插进主表单

对话框里有两类「按条件出现」的字段，共用同一套机制：

| 对话框 | 控制器 | 动态字段 | 锚点 |
|---|---|---|---|
| 识别特征 | 识别方式 | 模板匹配无、OCR 有「期望文本」 | 阈值（不是控制器本身） |
| 交互区域 | 探索动作 | 长按有按住时长、滑动有距离与方向 | 控制器本身 |

**识别特征为什么也要按需显示**：模板匹配的判定路径 `match_template(...)` 根本不读
`feature.text`，保存时也直接写 `text if kind == KIND_OCR else ""`。摆一个填了不生效
的输入框，用户会反复试而结果永远不变——这类「显示了但不生效」比缺字段更误导。

**锚点可以不是控制器**：「期望文本」要排在「阈值」之后（两者合起来构成匹配参数），
而控制它显隐的是更上方的「识别方式」。若一律紧贴控制器插入，它就会插到「必需」前面，
与阈值脱节。因此 `dynamic_params` 支持可选的第三个元素指定锚点字段。

「探索动作」下面要显示该动作的参数（长按的按住时长、滑动的距离与方向）。这类字段的
数量与种类取决于另一个下拉字段的取值，不能像普通字段那样在打开时静态生成一次。

**两轮历史缺陷**：

1. 初版把参数与动作一起静态生成——新建区域默认单击、单击没有参数，于是**切到长按
   也看不到「按住时长」输入框**。
2. 改成「参数固定平铺」后仍有问题：平铺的是打开时那个动作的参数，切到别的动作照样
   缺字段。

**做法**：`PropertyDialog` 支持 `dynamic_params = (controller_key, provider)`。
控制器（下拉字段）的取值变化时调 `provider(value)` 拿到该动作的参数字段，**逐行插进
主 `QFormLayout`**。

| 要点 | 做法 | 为什么 |
|---|---|---|
| 插入位置 | 插在**控制器所在行之后**，不是表单末尾 | 否则参数排到「操作后等待」下面，看着像那条的子项 |
| 插入方式 | `insertRow(row, label, editor)` 插进主表单 | **另建容器 + 独立 QFormLayout 时标签列宽由容器自己算，与主表单对不齐**——实测「双击间隔（秒）」的标签明显更靠左 |
| 无参数时 | **插 0 行**，不显示任何提示 | 用户明确要求「没有参数的时候直接不显示那个提示」 |
| 高度固定 | 首次显示后逐值量高、取最大、`setFixedHeight` | 无参数不留行会让高度随动作变（177/221/265），按钮跟着移动最多 88px |
| **标签列定宽** | 逐值量出最宽标签，给所有标签 `setFixedWidth` | 高度固定**解决不了**这一条：列宽由该列最长标签决定，多一行长标签会把整列撑宽，其余输入框被推着右移并变窄 |
| **标签显式右对齐** | 定宽时同时 `setAlignment(AlignRight)` | `QFormLayout.setLabelAlignment` 只对未定宽的标签生效；一旦 `setFixedWidth`，标签按默认左对齐渲染，表现为「所有标签挤到最左边」 |
| 切走再切回 | 跨动作记住已填的值 | 填了 2.5 秒切去看滑动再切回来，不该退回默认的 1 |
| 移除旧行 | `removeRow(row)`（会立即销毁控件） | 只 `removeWidget` 时旧控件要等事件循环回收，期间仍渲染在原位，表现为「新旧标签叠在一起」 |
| 编辑已有区域 | `set_dynamic_values` 灌初值 | 否则编辑一个填过 3.5 秒的长按区域会显示默认的 1，用户以为值被改了 |

**「切换不跳」需要固定两样东西，不止高度**：

| 项 | 不固定时的现象 | 实测 |
|---|---|---|
| 高度 | 底部按钮上下移动 | 单击 177 / 双击长按 221 / 滑动 265 |
| 标签列宽 | **所有输入框左边界右移、宽度变窄** | 阈值框 x 92→140、宽 337→289 |

第二项容易被漏掉：它不改变对话框外框尺寸，只看高度发现不了。因此 `_measure_and_freeze`
在逐值循环里同时记录 `height()` 与最宽标签宽度，循环结束后一起固定。

**三条要求能同时成立的完整链路**：

| 要求 | 靠什么 |
|---|---|
| 标签与输入框共两列 | 参数行插进主 QFormLayout，与普通字段共用同一组列 |
| 无参数不留提示 | 无参数时插 0 行 |
| 切换动作按钮不跳 | 对话框固定为「所有取值里的最大自然高度」 |
| 切换动作输入框不挪 | 标签列固定为「所有取值里的最宽标签」 |

**标签列定宽为什么不能靠 `setColumnMinimumWidth`**：那个接口只设下限，遇到更宽的标签
仍会把列撑开。必须逐个 `setFixedWidth` 才真的锁定。动态行插入时也要按已定的列宽设置，
否则新标签又会把列撑宽。

**高度固定为什么必须靠「逐值实测」**：`sizeHint()` 在 `insertRow` / `removeRow` 之后
不会自己失效，实测五个动作的行数从 3 变到 5、`sizeHint` 却始终是 177；只调
`invalidate()` + `activate()` 也不够。可靠的做法是每轮 `resize(width, 2000)` 撑高、
`adjustSize()` 收回、**再跑一次 `QApplication.processEvents()`** 让 Qt 完成尺寸计算，
最后取各轮 `height()` 的最大值。少了 `processEvents` 那一句，量出的永远是第一轮的数。

**为什么不在构造时量**：布局未激活时 `sizeHint()` 是「最小可接受尺寸」而非真实尺寸
（实测 265 而实际需要 353），据此固定会压扁内容；强行 `show()` 测量又会让窗口闪一下。
因此测量排在首次 `showEvent` 的下一轮事件循环里。

**多余空间落在按钮上方**：根布局在表单与按钮之间有一个 stretch，固定高度后多出的空间
被它吃掉，集中在按钮上方——而不是把字段之间的间距拉开（后者看着像「少了一块内容」）。

**注意「用测试里的 processEvents 掩盖测量缺陷」**：完整 `show()` 流程的用例自带若干次
`processEvents`，会把布局提前稳定，导致去掉测量里的 `processEvents` 后仍通过。因此另有
`test_measure_picks_tallest_not_first` 专门守「测量取的是最大值而非第一个取值」。

**灌初值时必须跳过「回读现有输入」**：`_render_dynamic` 默认会先把当前输入框的内容
记进 `_dynamic_values` 再重建。灌初值时这个回读会把刚写进去的值覆盖成旧值，表现为
「灌了 3.5 还是显示 1」。因此 `set_dynamic_values` 传 `keep_inputs=False`。

### 自动保存是可选开关，默认仍然手动落盘

编辑器顶部新增「自动保存」开关（默认关），打开后改动停止约 0.8 秒自动写入编辑区。
三个约束：

| 约束 | 做法 | 理由 |
|---|---|---|
| 只对已落盘场景生效 | 新建场景先手动保存一次 | 否则拖一个框就会以「新场景」的名字直接入库，用户还没命名 |
| 防抖 800ms | 手停下来再写 | 一次拖动触发几十次改动，逐次落盘要反复重算模板与掩码 |
| 切场景/关窗前补写 | 先 `_write_scene`，写不进去就不切 | 最后一次改动可能还在防抖里，直接切走会丢 |

开关状态存在库元数据 `library.json` 的 `auto_save` 里，随库走；下次打开窗口恢复
上次的选择。自动保存只写编辑区，产物区仍由配置页的「保存到 assets」一次性导出
——两者不能合并，否则每次拖动都会把未确认的内容推到运行期。

### 画布完全按标注编辑器的源码重写

`pages/canvas.py` 的 `SceneCanvas` **完全按上游 `AnnotationCanvas`
（`MarkUpWindow.py`）的源码实现重写**，不再保留此前自研的任何结构。只换三处业务
边界，其余逐项对应：

| 项 | 上游 | 本项目 |
|---|---|---|
| 数据结构 | `annotations: list[dict]` + 下标 | `_items: dict[key, CanvasItem]` + `_order` 列表 |
| 选中/悬停 | 下标 `selected_ann_index` / `hovered_ann_index` | 稳定 key |
| 新建完成 | 直接在画布里弹 `BBoxDialog` | 发 `rect_created`，由调用方弹属性框 |
| 删除/复制 | 画布内直接改 `annotations` | 发 `delete_requested` / `copy_requested` |

#### 逐项对齐清单

| 能力 | 实现口径（与源码一致） |
|---|---|
| 缩放 | 滚轮 1.1 倍/格；下限夹到 `fit_scale`（适配视口），上限 50 |
| 缩放锚点 | 记下锚点处图像坐标，改比例后反算偏移，使该坐标仍落在锚点 |
| 适配比例 | `min(view_w/img_w, view_h/img_h)`，允许放大 |
| 平移边界 | 图像小于视口时居中，大于时夹到 `[total-size, 0]`，两侧不留黑边 |
| 平移触发 | 仅当图像超出视口时可拖；光标开手掌/闭手掌 |
| 手柄判定 | `detect_handle`：距任一边 ≤ 8px 即命中，角优先于边 |
| 手柄前置条件 | **不要求该项已选中**——离边 8px 就能拖 |
| 手柄光标 | 四角对角箭头、四边水平/垂直箭头 |
| 悬停手势 | 手柄 → 调整光标；框体 → 四向箭头；空白 → 开手掌/箭头 |
| 调整算法 | 位移相对起点换算一次；最小 5px；夹到图像边界 |
| 绘制预览 | 绿色虚线 + 30 alpha 填充 |
| 新建门槛 | 宽或高 < 3px 不生成 |
| 三档视觉 | 选中：accent + 50 alpha；悬停：warning + 30 alpha；普通：高对比色 + 40 alpha |
| 悬停手柄高亮 | 加粗对应边；角手柄画 5px 圆点 |
| 配色 | 黄金分割比取色相、避开红蓝区间、按序号缓存 |
| 画布底色 | 跟随主题 `sidebar`（浅色主题下 `#efeff1`），不写死深灰；主题不可用时退到同色兜底 |
| 标签 | 框内左上，9pt 加粗，深色底 + 白字 |
| 取色采样 | 每次移动发 `color_sampled(abs, rel, color)`，越界时 color 为 None |
| 右键菜单 | 命中框时发 `context_action`，由调用方弹「复制 / 编辑 / 删除」 |
| 缩放下限 | 适配视口，不是固定小比例 |
| 位移算法 | 相对起点换算一次，不做增量累加（逐步取整会在放大后表现为拖不动） |

#### 三处业务边界差异

| 差异 | 为什么不照抄 |
|---|---|
| 新建后不在画布里弹对话框 | 本项目的属性对话框要读写 `Scene`/`shape` 模型，弹窗职责在 `scene_editor`，画布只管几何 |
| 删除/复制发信号而非直接改数据 | 数据在 `store` 里，画布不持有库；且删除要确认框、复制要保证名字唯一 |
| 多了 `set_mask_rect` | 场景库要提示「特征落在遮罩区」，那是本能力独有的信息 |

#### 一处刻意保留的差异

**允许矩形翻转**：拖过对边时按排序纠正。上游是「钉住对边 + 最小 5px」，继续拖不会
再有变化——用户容易以为卡住了。翻转后仍是合法矩形，行为更自然。

### 删除只作用于编辑区

与模板页签一致：删的是编辑区（`ok_scenes/`），产物区（`assets/scenes/`）等下次
「保存」才同步。保留「保存」作为唯一的导出动作，不做双向同步——两个方向都能改产物
区时，「产物区的内容是哪来的」就没有唯一答案了。

## 结论

**选 A：纯逻辑类 + 薄壳 Task**。

- 识别与单步点击落在 `recognize.py` / `navigate.py`，可被流转图页与离线测试直接调用；
- `SceneGotoTask` 与 `SceneExploreTask` 只做「执行器集成 + 独占 + 参数注入」，逻辑不超过十余行；
- 页签四子页签用 `TabStrip` + `QStackedWidget`（框架无现成嵌套页签容器）；
- 流转图用 networkx 算布局与最短路、QGraphicsView 自绘（`ok-pyside-minimal` 已验证具备三件套）。

实测数据推翻了探索记录中「搜索区域只是鲁棒性措施」的定位，升级为「无搜索区域的特征不予保存」——
这一条已记入实施偏差记录，不原地回改探索记录。

## 未解问题

设计阶段无法确定、需要实施中验证的点。这些会进实施偏差记录。

| 未解问题 | 为什么设计阶段定不了 |
|---|---|
| 识别缓存「上次场景」在什么时候失效 | 用户可能在导航之外手动操作游戏，缓存就过期了。可用「连续 N 次不匹配才放弃缓存」但 N 值需实测 |
| 探索时 `acquire_exclusive` 与任务队列的交互 | 独占会停掉当前任务并禁用一次性任务；探索本身就是一个任务，独占自己是否为非法操作需实测验证（可能需改为在 Task 内不重复独占） |
| 图布局算法选型 | `spring_layout` 稳定但需固定随机种子；`shell_layout` 或分层布局在图大时更好读。无真实图数据前无法判断 |
| 差分提候选框的最小/最大框尺寸 | 太小（几个像素）无意义，太大（半个屏幕）等于没提。需真实探索产出后定 |
| 一个场景的模板图数量与总体积 | 每场景 1 张 preview + N 张模板，全为 PNG。上百场景时的仓库体积需实测评估 |

**实施后的状态**（结论以 `deviation.md` 为准，此处只记哪些已落地）：

| 未解问题 | 实施结果 |
|---|---|
| 识别缓存失效 | 缓存只在**单次导航内**有效（`recognize()` 的 `cached_scene_id` 由调用方逐轮传入），跨任务不复用。因此「用户在导航之外手动操作」不会让缓存过期——调用方每轮都重新识别 |
| `acquire_exclusive` 与任务队列交互 | 两个任务各自 `acquire` / `release`，owner 不同（`scene-manager-goto` / `scene-manager-explore`）。被他人占用时**降级为不独占**而非失败——用户可能只想快速试一次 |
| 图布局算法 | 定 `spring_layout` + 固定种子 17。理由：布局稳定可复现，用户能靠「那个场景在右上角」形成空间记忆 |
| 差分候选框尺寸 | 定：面积占比 < 0.1% 判过小、> 50% 判过大，两者都不给候选框；差异像素占比 > 30% 判背景有动画。三个阈值都在 `ExploreOptions` 里可调 |
| 模板图数量与体积 | 未验证（需真实游戏数据）。当前一场景一目录、模板按特征裁小图，理论上可控 |
