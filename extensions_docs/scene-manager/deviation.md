## #1 特征搜索区域从「鲁棒性措施」升级为「不满足即拒存」

| 字段 | 值 |
|---|---|
| 日期 | 2026-11-11 |
| 类型 | 前提失效 |

**触发场景**：写设计文档时实测模板匹配性能，确认「识别开销靠缓存+短路能压住」这个前提是否成立。

**原计划**：探索记录中「特征支持模板图 + OCR 文本」「特征搜索区域存相对比例」两条的
**理由都只是鲁棒性**——「分辨率归一化后仍可能因窗口边框、黑边、裁剪偏移不同而错位，
相对比例对这种差异更鲁棒」。搜索区域被视为一个可选的质量提升项，一条特征即使不配区域
也能工作（全图匹配）。

**实际做法**：搜索区域改为**硬性要求**——没有搜索区域的特征不允许保存，配置界面在
未框选搜索区域时禁用保存按钮。

**原因**：实测数据显示全图匹配与限定区域匹配差 **18 倍**，差距不在模板尺寸而在搜索面积：

```text
# 环境：Windows 10 / Python 3.12 (.venv) / ok-script 3.0.0b3
# 样本：assets/images/0.png（3840×2160），模板 200×80 从该图裁出

fs.find_feature(img, None, template=tpl, threshold=0.8)                           → 3.5s
fs.find_feature(img, None, template=tpl, threshold=0.8, limit=1)                  → 0.470s
fs.find_feature(img, None, template=tpl, threshold=0.8, x=0,y=0,to_x=.25,to_y=.25, limit=1) → 0.0265s
fs.find_feature(img, None, template=tpl, threshold=0.8, box=Box(0,0,960,540), limit=1)      → 0.0260s

模板尺寸影响（限 30% 区域）：60×40=30ms / 120×80=42ms / 240×160=30ms / 400×300=28ms
多场景全扫估算（1920×1080、每场景 1 必需特征、限 30% 区域）：30 场景 = 0.270s（9ms/场景）
```

无 `limit` 时的 3.5s 还有个额外发现：post 阶段耗时 3051ms，源于全图匹配产出上千个
`1.00` 置信度候选（样本图大面积同色）后做 NMS。这说明**除区域限定外，`limit` 也必须传**
——两者都写进实现。

按 9ms/场景推算，若允许无区域特征，30 个场景的一轮判断约 14s。导航每轮都要判断当前场景，
这个量级无法接受；而「缓存当前场景 + 短路」只能在**命中**时省开销，首次判断与缓存失效后
仍必须全扫，压不住这个量级。

**影响**：
- 影响批次三（识别）与批次八（配置页）：识别侧把「无区域特征」视为配置错误并跳过该特征；
  配置页未框选搜索区域时禁用保存并给出说明。
- 不影响 `model.py` 的数据结构（字段本就有），只影响其**必填校验**与界面可用性。
- 引入的新风险：使用者配置每个特征都要多框一次区域，配置成本上升。缓解方式——特征框选时
  自动以外扩一定比例生成同名搜索区域，用户只在该默认区域不合适时才手动改。
- 探索记录不改：这条按「采纳后不回改」的约定留在此处。探索记录里那两条的原文仍然成立
  （相对比例确实更鲁棒），只是**理由不再充分**——真实原因多了性能这一层，且分量更重。

## #2 实施计划从「按技术层次分批」改为「按可独立验证的数据流分批」

| 字段 | 值 |
|---|---|
| 日期 | 2026-11-11 |
| 类型 | 更优路径 |

**触发场景**：把设计落到 `plan.md` 的批次划分时。

**原计划**：无。骨架里的批次表为空，由设计完成后再填。

**实际做法**：按「先能存 → 再能认 → 再能走 → 再能探 → 最后做界面」划分为 13 批，
前六批严格串行（每批只依赖前批产物），界面批次按子页签各占一批。

**原因**：这个能力的核心风险集中在**数据模型与换算**，而非界面。若先做界面，会先写出一批
「看起来能用」的页面，而底层模型在界面压力下反复变形，界面跟着改两三轮。按数据流分批后，
批次一至六每批都能用纯逻辑测试验证（不装 GUI、不接设备），风险在成本最低的阶段暴露。

**影响**：
- 界面工作集中在批次八至十一，届时数据契约已冻结，返工面小。
- 引入的新风险：全部界面在后期才出现，整体可演示时间推迟。可接受——需求方要的是能用的
  导航接口，不是先看到界面。
- 不需要新写决策记录（未推翻任何已定决策）。

## #4 缺陷修复：零方差模板必须拒绝

| 字段 | 值 |
|---|---|
| 日期 | 2026-11-11 |
| 类型 | 前提失效 |

**触发场景**：批次三测试里多个场景互相误识别。

**原计划**：模板匹配直接用 `cv2.matchTemplate(TM_CCOEFF_NORMED)`，置信度过阈值即命中。

**实际做法**：新增 `template_has_texture`（标准差下限 1.0），零方差模板判未命中，
并把该行为固化为回归用例。

**原因**：`TM_CCOEFF_NORMED` 算的是相关系数，模板方差为 0 时分母为 0，OpenCV 返回
全 1.0。实测：

```text
# 200x200 黑帧，10..50 区域涂白
白模板 40x40：max=1.0000  （即使在完全不含白色的区域也 1.0000）
黑模板 40x40：max=1.0000
```

若不拦，用户框一块纯色区域当特征，该场景就会**永远命中**，表现是「总是识别成这个
场景」，比识别不到更难排查。

**影响**：
- 影响 `recognize.py`。
- 引入的新风险：纹理极弱但确实可用的模板（如单像素边框）会被误拒。阈值 1.0 是
  灰度标准差，正常 UI 元素远高于此。

## #5 缺陷修复：编号不能按「最大 id + 1」分配

| 字段 | 值 |
|---|---|
| 日期 | 2026-11-11 |
| 类型 | 前提失效 |

**触发场景**：批次一测试「新 id 取现有最大值加一，删除后不复用」。

**原计划**：`next_scene_id()` 扫描现有目录取最大值加一。

**实际做法**：`LibraryMeta` 增加 `next_scene_seq` / `next_draft_seq` 两个单调递增
计数器，与现有最大值取较大者。

**原因**：删掉最大 id 后，该编号会被**重新分配**。而指向被删场景的边就成了悬空引用
——它不报错，只是静默指向一个完全不同的新场景。

**影响**：
- 影响 `model.py`（`LibraryMeta`）与 `store.py`（id 分配）。
- 库文件 `library.json` 新增两个字段；旧库读取时默认 1，无需迁移。
- 引入的新风险：计数器在「分配 id 后、保存前」崩溃时该编号会丢失。可接受——重新
  分配一个未落盘的编号不会造成悬空引用。

## #6 缺陷修复：重试点击未计入上限

| 字段 | 值 |
|---|---|
| 日期 | 2026-11-11 |
| 类型 | 前提失效 |

**触发场景**：批次六测试「单场景点击次数达上限即停」。

**原计划**：按「区域数」计单场景上限（每个区域点一次）。

**实际做法**：计数改为由主循环与 `_probe` 共享同一个字典，重试也累加。

上限按区域数计就失效。实测：上限设 3，实际点了 6 次。

**影响**：
- 影响 `explore.py` 的 `run` 与 `_probe`。
- 引入的新风险：上限在重试时可能提前耗尽，导致某场景的区域未全部探完。这是安全
  方向的取舍（宁可少探，不可多点）。

## #7 缺陷修复：步内中止被当成失败

|---|---|
| 日期 | 2026-11-11 |
| 类型 | 前提失效 |

**触发场景**：批次五测试「走完第一步后中止」。

**原计划**：中止检查只放在每步开始前。

**实际做法**：在 `_execute_step` 之后**再判一次** `should_stop`，为真则直接返回

**影响**：

## #8 缺陷修复：`x or []` 真值陷阱

| 字段 | 值 |
|---|---|
| 日期 | 2026-11-11 |
| 类型 | 前提失效 |

**触发场景**：批次六测试里「点击抛异常应记为事件」一直失败。

**原计划**：结果类用 `self.events = events or []` 作为「未传就用空列表」的简写。

**实际做法**：全部改为 `[] if events is None else events`，涉及 `ExploreResult`
（5 个字段）、`NavigationResult`（2 个）、`MatchResult`（2 个）。

**原因**：空列表是假值，`or` 会把它替换成**新列表**。调用方传自己的列表进去、之后
append 到自己的那份，而结果对象里永远是那个新建的空列表——事件、边、候选全部丢失。
这类缺陷不报错，只表现为「数据莫名其妙是空的」。

**影响**：
- 影响 `explore.py` / `navigate.py` / `recognize.py` 三个结果类。

## #9 缺陷修复：能力之间不得互相 import

| 字段 | 值 |
|---|---|
| 日期 | 2026-11-11 |
| 类型 | 前提失效 |

**触发场景**：批次七完成后跑 `extension_capability_guard.py audit`。

**原计划**：`runtime.py` 里 `from extensions.capabilities.screenshot_mask import geometry`
复用遮罩的几何计算，以「保证两处口径一致」。

**实际做法**：改为在 `runtime.py` 内自己实现同一套几何（锚点 + 百分比 + 截断取整），
并加一条用例逐值比对两处结果。

**原因**：体检报「能力隔离」错误两条：

```text
[错误] 能力隔离：extensions/capabilities/scene_manager/runtime.py:66 引用了其他能力
       extensions.capabilities.screenshot_mask——能力之间不得互相 import，
       共享代码应上升为装配基础设施
```

规则的理由是「被依赖的能力无法单独删除或迁移，而这条依赖在目录结构上完全看不见」。
而我原先的理由（口径一致）可以用**测试**达成，不必用 import。遮罩的锚点与百分比
换算属于**全局配置契约**（`config['global_configs']` 里的 `Screenshot Mask` 项），
不是那个能力包的私有实现。

**影响**：
- 影响 `runtime.py` 与 `TestSceneManagerTasks.py`。
- 逐值比对用例覆盖三种分辨率，任一处改成 round 就会失败——这条用例是防漂移的关键。

## #10 缺陷修复：翻译门禁按能力包拆开

| 字段 | 值 |
|---|---|
| 日期 | 2026-11-11 |
| 类型 | 前提失效 |

**触发场景**：批次十三（本地化）跑 H1 的翻译一致性门禁。

**原计划**：`plan.md` 批次十三写「`task_i18n_helper.py gate` 通过」，沿用 H1 现有命令
`gate --i18n extensions/capabilities --path extensions/capabilities`。

**实际做法**：新增 `.codebuddy.project/tools/i18n_gate_per_capability.py`，按能力包逐个
调用门禁，并把 H1 的第 2 步命令改为调用该脚本。

**原因**：上游 gate 的语义是「扫描给定路径的全部文案，要求**每个** locale 的 catalog
都覆盖它们」，且它把 `--i18n` 根下所有 po 按 locale 名合并
（`cmd_check_missing` 里的 `catalogs.setdefault(locale, set()).update(...)`）。

只有一个带 i18n 的能力包时，这两种语义等价。加入第二个包后，`screenshot_mask` 的
catalog 会因缺少 `scene_manager` 的 14 条任务配置文案而报错——而它本来就不该包含
那个包的文案。实测输出：

```text
语言 screenshot_mask 缺 14 条：
  「沿场景流转图跳转到指定场景」
  「Target Scene」
  ...
EXIT=1
```

本项目的能力包按**能力隔离**、各自自带 catalog，因此按包逐个校验才是正确口径。

**影响**：
- 影响批次十三，以及 H1 门禁命令（`.codebuddy.project/configs/skills/vcs/vcs-git-commit/project-config.md`）。
- 不改上游脚本：`ok-script` 是 vendored 包，改它会被后续同步覆盖；也不改包结构
  （把两个能力的 catalog 合并会破坏能力隔离）。
- 引入的新风险：包装脚本自身若有缺陷，会让门禁静默放行。缓解：脚本失败时以非零
  退出，且实测两条能力包都跑过。

## #11 缺陷修复：探索回退未真正实现（需求缺口）

| 字段 | 值 |
|---|---|
| 日期 | 2026-11-11 |
| 类型 | 前提失效 |

**触发场景**：首轮交付自检时发现，`explore.SceneExplorer._go_to` 只做「确认当前
是否已在目标场景」，并没有接入 `graph.return_step` 做实际回退。

**原计划**：`plan.md` 批次六写「探索器：BFS、白名单过滤、稳定帧判达、两点无跳转
判无效、差分提候选框、草稿产出」，设计文档写「探索回退 = 场景级返回区域（可配）+
入边反推」。

**实际做法**：`_go_to` 改为三级策略——已在目标则直接返回；图上有正向路径则走过去；
否则反复用 `graph.return_step` 逐层回退直到出现正向路径。同时：

- 区域循环内每次点击前调 `_ensure_at`，确保点击发生时确实在该场景；
- `_probe` 增加「点击前校验当前场景」，防止在错误画面上误点；
- 草稿落盘后经 `on_draft_saved` 重建识别器——不重建则认不出新画面，回退与后续
  展开全部失效；
- 草稿在差分给不出候选框时退化为整帧特征，保证它至少可被识别。

**原因**：原实现里 BFS 点进 B 之后无法回到 A，A 的其余区域被 `continue` 跳过。
需求「自动点击可点击区域、构建各场景之间的路由流转图」在多级图上不成立——只有
单级（起点没有分支）时才能跑通，而单级正是原测试桩唯一覆盖的情形。

原测试用的是「识别直接返回 `world.current`」的桩：它让识别变成作弊，掩盖了
「点进没有特征的画面后认不出来」这个真实约束。改为「按帧内容查表识别」后，
该缺口立即暴露——这也是本次修复的验证手段。

**影响**：
- 影响 `explore.py`（回退与点击前校验）、`runtime.py`（图与识别器刷新）。
- 新增 5 条用例（`TestRollbackAcrossLevels`），其中
  `test_waits_for_returned_scene_before_clicking` 断言点击序列必须是
  `a1→回退→a2→回退→a3`，直接证明回退被真正执行。

## #14 特征改为「形状 + 掩码」，场景库拆成编辑区与产物区

| 字段 | 值 |
|---|---|
| 日期 | 2026-11-12 |
| 类型 | 概念修正 + 结构调整 |

**触发场景**：用户要求「只存小图，加上参考项目的 mask 处理，方便处理异形图片，
如圆形、三角形」，并追问「是不是就需要考虑编辑的时候怎么配置与编辑 mask 区域」。

**原做法**：特征只有一个 `region` 矩形；一个特征一张裁图；场景库只有
`assets/scenes/` 一处，编辑与产物混在同一目录。

**改后做法**：

- 特征 = 一个形状（`rect` / `circle` / `sector` / `polygon`）+ 一张模板 + 一张掩码。
  新增 `shapes.py` 承担几何、掩码生成与命中测试。
- 搜索区域由形状派生，**删掉独立的 `region` 字段**。另存一个 region 会与形状分叉，
  改了形状忘了改 region，模板与搜索区对不上，表现是「这个特征从来匹配不到」。
- 场景库拆两区：`ok_scenes/`（编辑区，不入库，留 `raw.png`）与 `assets/scenes/`
  （产物区，入库，无原始帧）。配置页新增「保存到 assets」按钮经 `export_to` 导出。
- 旧的 `region` 格式不兼容，`SCHEMA_VERSION` 升到 2。读旧库直接报错，不按全画面
  矩形兜底——兜底会让模板按整帧裁剪，3840×2160 下一个特征就 23.7MB，启动即卡住，
  而表现是「打开很慢」而非「格式不对」。

**过程中的两个实测修正**：

1. **圆的半径必须按帧宽折算**。首版按相对包围盒裁图，1920×1080 下「相对半径 0.1
   的圆」被裁成 384×216 的椭圆，掩码覆盖率 94.4%（真圆应为 78.5%）——圆被上下
   切掉了一截。改为在像素空间完成全部几何计算后，覆盖率 78.52%（理论 78.54%）。
2. **搜索区域必须比模板大**。原实现用 `feature.region` 既裁模板又当搜索区，两者
   尺寸相同，`cv2.matchTemplate` 的结果退化成 1×1——实测画面平移 1px，得分从
   1.0000 掉到 0.0028。改为搜索区向外扩 8px 后，1–8px 位移都能命中。

**「旋转」的口径**：用户要的是**形状可倾斜**（给矩形/多边形设角度，模板按该角度
裁真实像素），不是**模板旋转匹配**。后者实测需要 24 个角度的模板库，单次匹配从
17ms 涨到 688ms、每特征占 2.8MB，而游戏 UI 的元素角度是固定的。

**参考资料**：`ZenlessZoneZero-OneDragon` 的 `TemplateInfo`（`template_shape` +
`point_list` → `mask.png`）与 `ScreenArea`（`pc_rect` 定搜索范围）确认了
「掩码表达形状」这一口径，与上游 `ok_templates` → `assets/templates` 的两区分离
同构。

**未做**：编辑端的形状绘制交互（画圆、拖顶点、角度控件）与掩码三态视图属第二批；
第一批只保证矩形可用，非矩形形状可通过 `scene.json` 直接写。

## #15 调查遮罩的框架口径，确认「输出脱敏」；原始帧仍不落盘

**已知限制**：若将来要求「运行期也拿不到 UID」，只能在框架的 `next_frame` 处统一
施加，属改上游文件，需登记 `divergence.yaml`。本能力不自行引入该分歧。

**新增用例**（`TestSceneManagerTasks.TestCaptureFrame`，5 项）：取帧返回原始像素

## #16 缺陷修复：改框后画布缩放与位置被重置

| 字段 | 值 |
|---|---|
| 日期 | 2026-11-12 |
| 类型 | 缺陷修复（用户指出） |

**触发场景**：用户反馈「框选区域后在弹窗点确认保存特征，编辑器区域的图像缩放会被
调整为适应模式，改变了之前滚轮调整的缩放大小与位置」。

**原因**：`SceneCanvas.set_image()` 每次都会把视图设为「整幅进视口」
（`_scale = self._fit_scale()`），而 `SceneEditorDialog._refresh_canvas()` 每改完
一个框都会调它。于是「用滚轮调好位置 → 点确认 → 画面弹回适应窗口」反复发生。

**为什么原实现看起来合理**：`set_image` 的语义是「载入一张新底图」，首次载入确实
应该取景为整幅可见。问题在于刷新框时底图并没有换（还是同一张 `preview.png`），
却复用了同一个方法。

**改法**：`set_image` 增加 `keep_view` 参数，保留缩放与平移（仍夹一次偏移——换了
不同尺寸的截图时旧偏移可能越界）。`_refresh_canvas` 增加 `reset_view` 参数：

| 调用场景 | `reset_view` | 理由 |
|---|---|---|
| 新增/修改/删除框后刷新 | `False` | 底图没变，没有理由重置 |
| 抓图、导入图片、载入已有场景 | `True` | 底图换了，旧视图不再对应同一画面 |

**新增用例**（2 项）：改框后缩放与偏移逐值保持；`reset_view=True` 时回到
`_fit_scale()`。

## #19 缺陷修复：点子页签内容不切换，始终显示场景配置

| 字段 | 值 |
|---|---|
| 日期 | 2026-11-13 |
| 类型 | 缺陷修复（接线缺失） |

**触发场景**：用户点「界面流转」「草稿确认」页签，内容区始终是场景配置页。

**根因**：`tab.py` 的 `_on_tab_changed(key)` 只做了「按 key 刷新数据」，
**从未调用 `self.stack.setCurrentWidget(...)`**。`QStackedWidget` 默认停在索引 0，
所以内容永远是 `ConfigPage`。

**为什么长期没被发现**：页签高亮由 `TabStrip` 自己维护（`QButtonGroup` 互斥），
切换时按钮确实会亮；数据也真的 reload 了。三个可见信号里只有「内容」是错的，
其余两个都正常——肉眼看不出是哪一层没接上，也没有任何异常。

**改法**：

1. `_add_page` 增加 `self._pages[key] = widget`，显式记录 key → 控件的映射。
   **不用「页签下标 == 堆栈下标」**：调试页按 `is_debug_mode()` 条件创建，一旦有人
   调整创建顺序或插入条件页，两边下标就错位，表现是「点 A 显示 B」——同样不报错。
2. `_on_tab_changed` 先 `setCurrentWidget(self._pages[key])`，再按 key reload。
   **顺序不能反**：先 reload 的话，任一页 reload 抛异常（场景库损坏、图的节点数据
   异常）都会让点击彻底没反应，用户看到的现象与「接线缺失」完全一样，排查会被误导。

**新增用例** 5 项（`TestSceneManagerTab`）：初始页是配置页、点流转切到流转页、

## #20 场景卡片名称后显示场景 id

| 字段 | 值 |
|---|---|
| 日期 | 2026-11-13 |
| 类型 | 交互改进（用户要求） |

**触发场景**：用户要求「在场景配置页签中的场景卡片名称后面显示一下场景 ID」。

**为什么要显示 id**：编辑区是 `ok_scenes/<id>/` 的目录结构，排查问题、对照 `scene.json`、
看清场库导出日志时都要靠 id 定位。原先卡片只有名称，用户必须进编辑弹窗或翻目录才知道
某个场景的 id。

**做法**：名称行改成富文本——`场景名` + 两个不断行空格 + `<span style="...">id</span>`，
id 用小一号（11px）的次要色 `#8a8a92`。

**为什么放名称行而不是副文本行**（试过副文本，实测 131 → 151px）：副文本是独立的一行，
会让每张卡片固定高出一个行高，而 id 与名称是同一件事的两个标识，放同一行读起来是
一句「主页界面 scene-0001」。名称过长时两者一起自然换行，卡片按需增高
（`set_card_width` 走 `heightForWidth`），不会截断。

**名称必须 `escape`**：名称是用户输入。不转义时 `a<b>c` 会被当标签解析、整段消失，
而界面上看不出是「名字里有尖括号」还是「渲染坏了」。实测 `a<b>c & d` 转义后按字面
显示正常。

**两个不断行空格**：单个半角空格在换行时容易被拆开，导致 id 单独掉到下一行；用
`&nbsp;&nbsp;` 保证「名称 + id」作为一个整体换行。

**新增用例** 2 项：名称行同时含名称与 id 且带 `<span>` 片段、名称含尖括号与 `&` 时
按字面显示。

## #21 缺陷修复：基准分辨率不随画面更新，三道判断拦截

| 字段 | 值 |
|---|---|
| 日期 | 2026-11-13 |
| 类型 | 缺陷修复（静默错位） |

**触发场景**：用户报「点击场景配置中的保存按钮后，library.json 的分辨率没有跟随
最新的场景图片大小更新」，并给出识别失败信息「画面宽高比与场景库不一致：
当前 1280x720(1.7778)，库基准 1918x997 (1.9238)」。

**根因**：基准只在「库里还没有分辨率」时写入一次。这条分支只在库为空时成立，之后
换窗口尺寸、换采集分辨率都不会更新基准。

实测本机数据：

| 项 | 值 | 宽高比 |
|---|---|---|
| `ok_scenes/library.json` | 1918×997 | 1.9238 |
| `scene-0002/preview.png` | 1280×720 | 1.7778 |
| `scene-0003/preview.png` | 1280×720 | 1.7778 |

**为什么画布上看不出异常**：编辑器存相对坐标时用基准做分母
（`_pixels_to_ratio(..., meta.base_width, meta.base_height)`），画框时又用同一个基准
换算回来。两个错误互相抵消，界面上完全正常；只有运行期把帧缩放到基准后，框才错位。
我按两种口径各裁一次图验证过：按基准换算裁到的是错位后的一块，看不到完整文字。

**改法（用户指定的三道判断）**：

| 时机 | 判断 | 不通过时 |
|---|---|---|
| 库里还没有场景 | 用当前帧立基准 | — |
| 已有场景，准备截图 | 宽高比与基准一致 | 弹窗说明并拒绝写入 |
| 点「保存」同步到产物区 | 逐个场景核对 `preview.png` 尺寸 | 弹窗列出问题场景并中止导出 |

新增 `resolution.py` 集中三条判定，界面只负责询问。宽高比与尺寸分开处理：比例不同
是硬错误（坐标不可信）；比例相同、尺寸不同只提示（识别会等比缩放，结果正确）。

**新增能力**：`store.image_size` 只读 PNG 的 IHDR 取尺寸，不解码整幅图；并要求签名
与 `IHDR` 都在场——扩展名被改成 `.png` 的其它格式会读出一对垃圾宽高，那种「看起来
有尺寸」的误判比读不出来更危险。`store.resolution_problems` 用它逐场景核对。

**顺手删掉的死代码**：`scene_editor._ensure_base_resolution` 从未被调用（基准写入早已
移到配置页的建场景路径），留着会让后来者以为「打开弹窗时也会设基准」。

**软提示被覆盖的缺陷（本轮自查发现）**：初版先写「尺寸不同会被缩放」再写「已创建」，
后者把前者盖掉了——用户永远看不到「这次是缩放过的」，而那正是解释「为什么识别得分
略低」的唯一线索。改为两条一起显示。

**新增用例**：`TestSceneManagerResolution` 20 项（判定分支、格式、库级检查、非 PNG
拒绝）+ `TestConfigPageResolutionGuard` 8 项（空库立基准、不一致被拦且不落盘、一致
放行、缩放放行并提示、截图按钮同样被拦、仅空库可改基准、保存前拦下、一致时放行）。

**测试期踩的坑**：补丁 `kit.dialogs.Dialog` 无效——两处调用点写的都是
`from ok.ui.qt.kit import Dialog`，解析的是包模块属性。补丁错层时真实对话框会弹出来
阻塞在 `exec()`，测试不是失败而是挂住（表现为无输出、不结束）。已在用例的
`_patch_dialog` 里写明这条，避免后来者重踩。

## #22 缺陷修复：点「识别当前画面」后界面卡死

| 字段 | 值 |
|---|---|
| 日期 | 2026-11-13 |
| 类型 | 缺陷修复（线程死锁） |

**触发场景**：用户在调试页点「识别当前画面」，整个界面卡死（日志停在
`TaskExecutor:get_task_by_class ...`，之后再无输出）。

**根因（四环相扣）**：

| 环节 | 事实 |
|---|---|
| 执行器初始状态 | `TaskExecutor.__init__` 里 `self.paused = True` |
| `task.ocr` 的前置检查 | 第一行就是 `if self.blocked_by_pause(): self.executor.sleep(1)` |
| 暂停判定的线程语义 | `blocked_by_pause` 只在「执行器线程 + job 有 ignore_pause」时返回 False |
| `executor.sleep` 的形态 | 暂停态下是 `while True`，只在暂停解除时退出 |

GUI 线程调 `task.ocr` → 判定暂停 → 进 `sleep` 死循环 → 等暂停解除 → 而解除要执行器
线程推进，GUI 又占住了事件循环 → **双方互等，只能杀进程**。

**影响面比报告的更大**：不只是 OCR。`task.click`、`task.sleep` 同样以
`check_enabled` 开头，所以调试页的「单步试走」「完整跳转」与流转页的「试走一步」
**全都会卡死**，只是用户先点到了识别。

**改法**：新增 `TaskBridge.run_on_executor(fn, timeout)`，把会碰任务的代码
`executor.submit` 到执行器线程并等结果。job 默认 `ignore_pause=True`，暂停态下照常
执行。三个界面入口全部改为经它调用：

| 入口 | 原来 | 现在 |
|---|---|---|
| 调试页识别 / 实时刷新 | GUI 线程直接 `capture_frame + matcher` | `bridge.identify_blocking()` |
| 调试页单步试走 | GUI 线程 `activate_area + wait + identify_once` | `bridge.click_and_identify()` |
| 调试页完整跳转 | GUI 线程 `navigator.goto` | `bridge.goto_blocking()` |
| 流转页试走一步 | GUI 线程 `activate_area + identify_once` | `bridge.click_and_identify()` |

**为什么整段一起派发**：点击 → 等待 → 识别要在一个 job 内完成。拆成多次派发会打断
「点完立刻识别」的时序，中间还可能插进别的 job。

**为什么目标函数不碰 Qt 控件**：它跑在执行器线程，改控件会崩。结果经返回值带回
GUI 线程再更新。

**顺带修正**：调试页原先「取不到画面」有专门的中文提示，改走 bridge 后该分支消失，
统一由 `run_on_executor` 抛出可读原因（「取不到帧」/「执行器忙」/「操作未完成」），
界面上仍是同一行文字。

**新增用例** 13 项（`TestSceneManagerExecutorThread`）：四个构成死锁的框架契约断言
（执行器默认暂停、暂停判定分线程、`sleep` 是 while True、`ocr` 先查暂停）+ 派发契约
（跨线程执行、等结果、异常转 RuntimeError、超时取消 job、执行器缺失、被独占）+ 三个
入口的执行顺序。契约断言的作用是：哪条前提将来被框架改掉，这里立刻失败并提示
「本缺陷的根因已消失」，避免一段无用的防御代码长期留着。

## #23 识别结果显示耗时（手动与实时刷新都显示）

| 字段 | 值 |
|---|---|
| 日期 | 2026-11-13 |
| 类型 | 交互改进（用户要求） |

**触发场景**：用户要求「右侧点击识别后，加一个耗时显示」，随后补充「实时刷新也需要显示」。

**做法**：`recognize()` 内用 `time.perf_counter()` 计时，填进 `MatchResult.duration`；
界面显示成「识别为 scene-0003（耗时 64 ms，帧缩放：否）」。

**计时边界只到「归一化 + 扫描」**，不含取帧与线程排队。界面拿这个数字要回答的是
「识别本身快不快」；把设备往返与执行器排队算进来，同一台机器上会随负载大幅抖动，
看不出任何优化效果。实测 20 场景 / 40 特征：纯扫描 64ms、归一化 23ms，合并计时才有
量级意义。

**`duration == 0` 显示「未实际识别」**：库为空或缺基准时 `make_matcher` 返回恒未命中的
兜底函数，它从不真正扫描。显示「耗时 0 ms」会被读成「快到不需要时间」，与事实相反。

**小于 10ms 保留一位小数**：取整会得到「耗时 0 ms」，与「未实际识别」在界面上无法
区分。

**实时刷新为什么不需要单独实现**：它与按钮共用 `_on_identify`。但顺带发现一个并发
问题——刷新间隔 800ms 可能短于一次识别（场景多或执行器排队时），上一次还没返回就
会再发一次，两次结果各写一遍，耗时与当前画面不同步。加 `_identifying` 互斥，触发被
**丢弃**而不是排队（排队会积压，放开后连跑好几次）。标记用 `try/finally` 复位，
否则一次异常会让后续点击全部静默失效。

**顺带修正文案**：原先把归一做进标签里写成「耗时归一化：是/否」，与新加的「耗时 64 ms」
并列时两个「耗时」重复，读起来别扭。改为「帧缩放：是/否」。

**新增用例** 14 项（`TestSceneManagerTiming`）：`MatchResult.duration` 默认值与透传、
格式化四档（0 / 亚 10ms / 常规 / 秒级）、真实识别耗时为正、未命中也有耗时、归一化
计入耗时、命中与未命中界面都显示耗时、实时刷新走同一路径、识别中不重入、异常后标记
复位。

## #24 识别结果表只读、按相似度排序并显示相似度

| 字段 | 值 |
|---|---|
| 日期 | 2026-11-13 |
| 类型 | 交互改进（用户要求） |

**触发场景**：用户要求「下面的识别结果列表现在可以编辑，调整为不可编辑，然后顺序
调整下，按照识别的相似度进行排序，识别结果有相似度之类的参数么，有的话也添加上显示」。

**相似度的来源**：原先 `evaluate_scene` 把每个特征的 `confidence` 算完就丢
（`hit, _confidence = ...`），`score` 只是排序用的合成值——命中固定 1.0 加可选加成、
未命中固定 0.0。没有现成的相似度参数可显示，需要先把置信度带出来。

**核心问题：短路让相似度不可比**。`evaluate_scene` 在首个必需特征不中时立即返回，
于是「已评估特征的均值」在不同场景上平均了不同数量的样本。实测一组能让排序**完全
反转**的数据：

| 场景 | 特征数 | 短路相似度 | 全量相似度 |
|---|---|---|---|
| A | 1（命中一半） | 0.617 | 0.617 |
| B | 4（首个不中，其余全中） | 0.009 | 0.752 |

按短路值排 B 掉到最后，按全量值排 B 应排在 A 前面——B 其实有一半以上特征很像。

**改法：两套路径分开**。

| 路径 | 用哪个 | 依据 |
|---|---|---|
| 运行期识别 | `evaluate_scene`（保留短路） | 实测 50 场景 × 2 特征：短路 4ms、全量 189ms，差 47 倍。导航每轮判断，不能为显示慢两个数量级 |
| 调试页 | 新增 `diagnose_scene`（全量）+ `TaskBridge.diagnose_blocking` | 人点一下等半秒无所谓，换可比的相似度 |

`diagnose_blocking` 在同一帧上先跑正式识别（保证「命中哪个」与运行期一致），再全量
评估每个场景，结果放 `MatchResult.diagnostics`。`details_by_similarity` 优先用它，
没有时才退回 `details`。

**一帧两用的必要性**：诊断若另取一帧，画面可能已经变了，展示的相似度与状态行的命中
结论就会互相矛盾。

**表格只读的两个层次**：控件级 `setEditTriggers(NoEditTriggers)` 覆盖不到 F2 与部分
平台的右键菜单，所以每个 item 再执行 `flags() & ~ItemIsEditable`。用例逐格断言，
确保没有遗漏某行某列。

**顺带调整**：新增「相似度」列并把它放在场景名右侧（原第二列是「必需命中」），
垂直表头隐藏（排序后行号与「第几个场景」无关，留着会误导）。

**兼容处理**：`detail` 是元组协议，历史调用点可能只给 5 项。排序时缺第 6 项按 `-1`
处理（排最后），界面显示 `—` 而不是 `0%`——0 是「算出来全是 0 置信度」，与「没有
这个数据」是两回事。

**新增用例** 16 项（`TestSceneManagerDetailTable`）：detail 6 元组与相似度取值、
短路失败时相似度为该特征置信度、降序排序、平局保持扫描顺序、优先用 diagnostics
（含排序反转的回归）、旧格式 5 项兼容、`diagnose_scene` 评估全部特征、相似度文本
四档、表格逐格不可编辑、按相似度排序、相似度列存在、旧格式显示破折号、垂直表头隐藏。

## #25 缺陷修复：OCR 特征识别不到——裁剪未外扩 + 检测器向下吸附

| 字段 | 值 |
|---|---|
| 日期 | 2026-11-13 |
| 类型 | 缺陷修复（OCR 检测失效） |

**触发场景**：`ok_scenes/scene-0002` 的「靶场入口」场景无法识别。用户指出同一张
`preview.png` 单独做 OCR 却能看到这段文字，并明确质疑「框明明完整包住了文字，
是不是坐标偏移」。

**第一轮归因错了，被用户驳回两次**，两次都记在这里以免重犯：

1. 先猜「OCR 引擎依赖缺失（onnxruntime 未装）」——错。项目配 `use_openvino=True`，
   走 OpenVINO 分支，根本不需要 onnxruntime。
2. 再猜「特征框比文字紧，切掉了字边」——错。用 OCR 检测框 `(244,75)-(411,126)` 当
   「文字真实范围」去比特征框，得出「上下各切 4px」。但检测框是**宽松估计**，不是
   墨迹边界。用像素阈值直接量墨迹：`(251,82)-(406,120)`，特征框四边各留 3~5px 余量，
   **完整包裹**。用户贴图指出这一点，说得对。

**真正的成因有两层，各自独立**。

第一层：文字离裁剪边界不足 4px 就失效。固定宽度、只改上边界：

| 裁剪上边界 | 文字上方留空 | 结果 |
|---|---|---|
| y=82 | 0px | `'五'`、`'分'`（碎片） |
| y=80 | 2px | 空结果 |
| y=79（特征框原样） | 3px | `'TT'` |
| y=78 | 4px | `'靶场入口'` 0.998 |
| y=74 | 8px | `'靶场入口'` 0.999 |

DB 检测器把文字区域 `unclip`（向外扩张）后作为识别输入，扩张后的框超出裁剪边界就
被裁掉，文字区域不完整导致检测失败。所以**特征框画得再准也没用**。

第二层：检测器把输入边长吸附到 32 的倍数，且用 `round`
（`resize_h = max(round(resize_h / 32) * 32, 32)`）。`round` 一半情况**向下**取整：

| 原高 | 吸附后 | 变化 |
|---|---|---|
| 40 | 32 | 压缩 20% |
| 46 | 32 | 压缩 30% |
| 47 | 32 | 压缩 32% |
| 48 | 64 | 放大 |

压缩后笔画糊在一起，识别直接失效。**这与 `pad` 互相独立**：原框高 49 外扩到 65，
`round(65/32)=2` 仍压到 64；原框高 25 外扩到 41 会压到 32（压缩 22%）。实测 `round`
在 468 个高度里 **232 个（50%）会压缩**——靠调 `pad` 只是碰运气。

**用户指出了关键**：「这个我认为不能走四舍五入，应该走向上取整才对，否则你这个扩
边界的方式，总会遇到扩了还是导致了向下取整，产生问题。」这个判断是对的。

**改法（两道都在 `match_text` 里）**：

1. 裁剪时四边外扩 `TEXT_PAD = 8`，与 `match_template` 的搜索区外扩一致；
2. 补齐到 `OCR_SIDE_MULTIPLE = 32` 的倍数，按 `ceil`。补齐后检测器的吸附变成**恒等**
   （验证 1..499 零例外），压缩从结构上不可能发生。代价是平均放大 1.18 倍、最坏
   1.94 倍。用 `BORDER_REPLICATE` 补边缘而非缩放——缩放会拉伸文字变形。

**回滚掉的中间方案**：上一版提交 `fdc085d` 在 `OcrAdapter` 里「放大 2 倍」。它能同时

## #27 缺陷修复：新建场景的名称与 id 不对应

| 字段 | 值 |
|---|---|
| 日期 | 2026-11-13 |
| 类型 | 缺陷修复（双计数器分叉） |

**触发场景**：用户指出「新建场景的名称没有与场景 id 对上，需要 id 是 5 场景那边名称
也要是场景五」。截图里 `scene-0004` 叫「场景 1」、`scene-0005` 叫「场景 2」、
`scene-0006` 叫「场景 3」。

**根因：id 与名称各有一套计数器**。

| 项 | 来源 | 表现 |
|---|---|---|
| id | 库级 `next_scene_seq` 单调递增 | `scene-0004`、`scene-0005`、`scene-0006` |
| 名称 | 「现有 `场景 N` 的最大 N + 1」 | 从 1 数起 → `场景 1`、`场景 2`、`场景 3` |

库里有 `scene-0002`「靶场入口」、`scene-0003`「关卡选择」这类用户自定义名，它们不匹配
`场景 N` 格式，不参与名称计数。于是 id 已经到 6、名称还停在 3。

**为什么双计数器必然分叉**：id 与名称的「消耗」时机不同——用户改一次名，名称就从计数
序列里消失了；而 id 永远不回退。两套数字一旦错开就再也追不回来，而且没有任何机制会
发现。

**改法：名称的序号从 id 派生**，`scene-0005` → `场景 5`。新增
`model.id_sequence(scene_id)` 取 id 里的数字，`store.scene_default_name(scene_id)` 拼
名称；`new_scene` 在不显式传名时用它。配置页删掉自己的 `_next_scene_name` 与
`_SCENE_NAME_PREFIX`。

**id 是唯一权威来源**：名称跟着它走才不会分叉。这比「保持两套计数器同步」可靠——
同步要求每次改名、删除、导入都两边一起改，漏一处就重新分叉。

**用户选择**：数字用阿拉伯（`场景 5`）而非中文（`场景五`），与现有显示风格一致，
序号变大也不会变长；已有的错位场景（`scene-0004` 叫「场景 1」）**只改新建的**，旧的
保持原样由用户自行处理，不做批量改名。

**前缀固定中文、不走 `tr()`**：名称要落进 `scene.json`，是持久化数据。随界面语言变化
会让同一场景在不同语言下叫不同名字，序号也会跟着乱。

**草稿转正不受影响**：`promote_draft` 沿用草稿名（草稿可能已有意义的名字），只在
`name` 为空时才需要默认值。

**新增用例** 11 项：`TestSceneDefaultName` 3（序号跟随 id、草稿 id、非法 id 退回）、
`TestIdSequence` 2（正式/草稿、5 种非法输入返回 0）、`TestStoreNewSceneName` 2（已有
自定义名时名称仍与 id 一致、显式名不被覆盖）、配置页 2（连续新建名称跟随 id、显式名
保留），另改 2 项既有断言（`test_next_scene_name_increments` → `test_new_scene_name_follows_id`，
截图建场景的名称断言改为按 id 推导）。

## #28 调试页改为全量匹配；特征/区域默认名带场景名

| 字段 | 值 |
|---|---|
| 日期 | 2026-11-13 |
| 类型 | 缺陷修复 + 交互改进（用户要求） |

### 一、调试页命中第一个场景就停了

**触发场景**：用户点「识别当前画面」后，表格里只出现一个场景。

**根因**：`diagnose_blocking` 对每个场景都算出了全量相似度并放进 `diagnostics`，但
汇总那次 `recognize()` 仍用默认 `MatchOptions(stop_on_first=True)`。命中第一个场景
循环就 break，`details` 里只有一条；而表格按 `len(result.details)` 建行，于是整张表
只显示一个场景。`diagnostics` 本来是完整的，只是没被用上。

**改法**：汇总识别传 `stop_on_first=False`。运行期 `make_matcher` 保持默认 True——
那里每轮都要判断，不能为完整性牺牲速度（实测 50 场景 × 2 特征：短路 4ms、全量 189ms）。

**新增用例** 3 项：`diagnose_blocking` 源码含 `stop_on_first=False`、`make_matcher`
不含该开关、全量模式 details 覆盖 4 个场景而首中即停只有 1 条。

### 二、特征/区域默认名带场景名

**触发场景**：用户要求默认名改为 `<当前场景名称>-特征<数字递增编号>` /
`<当前场景名称>-区域<数字递增编号>`。

**改法**：新增 `scene_editor._name_prefix(scene, kind)` 拼前缀，`_next_name` 改为
「前缀 + 编号」直连。

| 项 | 改前 | 改后 |
|---|---|---|
| 特征默认名 | `feature-1` | `靶场入口-特征1` |
| 区域默认名 | `area-1` | `靶场入口-区域1` |
| 编号分隔 | `feature-1`（带连字符） | `靶场入口-特征1`（紧贴） |

**为什么带场景名**：右侧列表与属性对话框只显示名称，光看 `特征1` 分不清属于哪个
场景，用户在多个场景间切换时容易配错——而配错的代价是那个场景识别不到。

**为什么编号不隔连字符**：场景名本身可能含 `-`，再加一个会让 `特征-1` 与 `特征1`
两种形态混在库里，用户分不清哪个是自动生成的。

**场景名为空时**：用 id 兜底（`scene-0009-特征1`）。`Scene.__post_init__` 本会把空名
填成 id，但导入的旧数据可能真的有空名；用 id 比只用 `特征1` 好，至少能定位到目录。

**不动的部分**：复制特征/区域仍用 `<原名>_copy`——那是「复制某一份」，与新建的编号
语义不同，加场景名反而会让名字过长。

**新增用例** 5 项：前缀含场景名、编号跳过已占用、空名退回 id、框选特征默认名、框选
区域默认名。

## #29 探索动作可配：单击/双击/长按/滑动/右键

| 字段 | 值 |
|---|---|
| 日期 | 2026-11-13 |
| 类型 | 功能新增（用户要求） |

**触发场景**：用户问「场景自动探索功能，现在是不是只有单击按钮进行探索，且区域没有
配置按钮的探索操作方式，你看下是不是需要进行功能新增」，随后补充「动作会有操作参数，
如长按时间、滑动距离方向等」。

**确认的现状**：探索确实固定单击（`activate_area` → `click_point_of` →
`task.click`），区域只有 `explore_probe` 一个布尔开关，没有动作配置。

**为什么必须加**：设计文档原有一条「区域不绑定动作类型」，理由是动作种类可扩展、写进
数据结构要迁移旧库。这条判断对**业务动作**仍然成立（导航与外部调用方自己实现），但
对**探索**不成立——探索是唯一「自己动手」的使用方，它必须知道怎么触发。实测三类区域
用单击探测全都会出错，且都不报错：

| 区域类型 | 单击的后果 |
|---|---|
| 滑动列表、轮播、地图 | 画面不变 → 判「无效区域」，连两次永久跳过 |
| 需要长按蓄力的按钮 | 单击不触发 → 同上，被误杀 |
| 右键菜单 | 单击打开另一个功能 → 写出的边是错的 |

**改法**：`Area` 加两个字段，**都带 `explore_` 前缀**以表明探索专用、不参与识别与
寻路：

| 字段 | 内容 |
|---|---|
| `explore_action` | 单击（默认）/ 双击 / 长按 / 滑动 / 右键单击 |
| `explore_params` | 该动作的参数，按动作校验并补默认值 |

参数规格：

| 动作 | 参数 |
|---|---|
| `double_click` | `interval` 两击间隔，默认 0.08s，范围 [0.01, 1] |
| `long_press` | `duration` 按住时长，默认 1.0s，范围 [0.1, 10] |
| `swipe` | `direction` 四方向（默认 up）、`distance` 帧短边比例（默认 0.3，范围 [0.05, 0.9]） |

**参数放在独立字典而不是给每种动作加字段**：动作会继续扩展（拖拽、滚轮），每加一种
就往 `Area` 上添字段会让结构无限膨胀，而取值又必须各自校验。用「动作 → 参数规格」
两张表（`ACTION_NUMERIC_PARAMS` / `ACTION_ENUM_PARAMS`），新增动作只改表。

**切换动作时丢弃旧参数**：长按切到滑动时 `duration` 若留着，会跟着落盘、下次读出来
看着像「滑动也有个 duration」。多余键丢弃不报错（用户改动作不该被拦下），已知参数取值
非法才报错（通常意味着配置被手改坏）。

**滑动距离用帧短边比例而非像素**：换分辨率后手势幅度不变，否则同一份配置在 4K 上会
滑出画面。

**执行方式挑上游现成接口**：

| 动作 | 实现 | 为什么不自己拼 |
|---|---|---|
| 长按 | `click(down_time=duration)` | 手动 mouse_down/mouse_up 在异常路径上可能留下没松开的按键 |
| 双击 | 两次 `click` + `wait(interval)` | 上游没有跨设备一致的双击接口 |
| 右键 | `click(key="right")` | 同上 |
| 滑动 | `swipe(x, y, end_x, end_y)` | 上游现成手势，终点夹在画面内 |

**界面上参数字段固定平铺、不按动作显隐**：这个对话框此前试过「按条件显隐行」，切一次
动作布局就上下跳一次、按钮跑位，已回滚过一次。平铺不会污染数据——保存时由
`normalize_action_params` 丢弃不属于当前动作的参数。标签里注明适用动作
（`Long Press Duration (s)`）。

**翻译收集规则顺带补了两个缺口**：动作名与参数标签放在元组/字典表里，调用处是
`tr(label)` 传变量，原脚本抓不到——表现为界面上这几项一直英文，而门禁查不出来（它
对照的正是同一份 catalog，两边一起缺就一致了）。新增 `LABEL_TABLE_BLOCK` 限定只在
这三张表定义块内收集，避免误收 `_MASK_ANCHOR_SIDES` 这类内部映射（第一版用裸规则把
`bottom_right`、`center` 收进了 catalog）。

**新增用例** 20 项：`TestExploreAction` 11（默认单击、五种动作、未知动作报错、默认
参数、无参数动作、范围校验、非数字、方向校验、旧参数丢弃、序列化往返、规格供界面用）
+ `TestSceneManagerExploreAction` 9（五种动作的分派形态、滑动四方向、终点夹边、
`click_point_of` 不受动作影响）。

## #30 缺陷修复：探索动作的参数不显示

| 字段 | 值 |
|---|---|
| 日期 | 2026-11-13 |
| 类型 | 缺陷修复（动态字段未接） |

**触发场景**：用户指出「探索动作的参数没有对应的参数呢，例如长按时间、双击间隔等」。

**根因**：参数字段在**打开对话框时**按当时的动作静态生成一次。新建区域默认单击、
单击没有参数，于是切到长按也看不到「按住时长」输入框。

上一版（#29）为避开「切换动作时布局跳动」，把参数做成「固定平铺」——但平铺的是
打开时那个动作的参数，切换后仍然缺字段。这是个设计矛盾：既要不跳，又要随动作变。

**改法**：`PropertyDialog` 新增动态参数区，`dynamic_params = (controller_key,
provider)`。控制器取值变化时调 `provider(value)` 重建内容。

| 要点 | 做法 | 为什么 |
|---|---|---|
| 插入位置 | 插在控制器行之后 | 否则参数排到「操作后等待」下面，看着像那条的子项 |
| 布局稳定 | 预热所有取值取最高者作为 `minimumHeight` | 参数数量不同（滑动两行、长按一行、单击零行），不设下限时底部按钮会上下跑 |
| 无参数时 | 显示「该动作没有额外参数」 | 固定高度会空出一块，看着像少了什么 |
| 切走再切回 | 跨动作记住已填的值 | 填了 2.5 秒切去看滑动再切回，不该退回 1 |
| 旧控件移除 | `removeWidget` + `setParent(None)` + `deleteLater` | 只调前两者时旧控件等事件循环回收，期间仍渲染在原位——实测出「新旧标签叠在一起」 |
| 编辑已有区域 | `set_dynamic_values` 灌初值 | 否则编辑填过 3.5 秒的长按区域会显示默认的 1 |

**为什么用 `minimumHeight` 而不是 `fixedHeight`**：固定高度要求测得的最大值精确，而
预热阶段布局还没完成几何计算，量出来偏小——滑动动作的方向下拉框被压成一条边（实测
`440x281` 里放不下两行 36px 控件）。设下限则内容更高时能撑开。

**灌初值时跳过「回读现有输入」**：`_render_dynamic` 默认先记下当前输入框内容再重建，
灌初值时这个回读会把刚写的值覆盖成旧值——实测「灌了 3.5 仍显示 1」。因此
`set_dynamic_values` 与预热都传 `keep_inputs=False`。

**顺带补的翻译**：「该动作没有额外参数」这句提示漏了译文，界面上一直是英文。

**新增用例** 9 项（`TestPropertyDialogDynamic`）：切动作出现参数、滑动有两个参数、
切回保留已填值、灌初值优先于默认、切换动作按钮位置不变、参数区插在控制器下方、控制器
不存在报错、控制器是文本框报错、参数字段随动作变化。

**反向验证**：把 `currentIndexChanged.connect(...)` 换成 `pass` 后，8 项里有 3 项失败

## #31 缺陷修复：参数行与主表单不对齐、无参数时留空白

|---|---|
| 日期 | 2026-11-13 |

**两个问题的根因是同一个**：参数行装在独立容器里，容器内是另一个 `QFormLayout`。

| 问题 | 成因 |
|---|---|
| 参数标签错位 | 容器的 QFormLayout 自己算标签列宽，与主表单的两列宽度不同——实测「双击间隔（秒）」的标签比其他标签更靠左 |
| 无参数时空白 | 为了让高度稳定，先给容器设了 `minimumHeight`（预热所有动作取最高），再在里面塞一行「该动作没有额外参数」占位 |

**改法**：不再建容器，**参数行直接 `insertRow` 进主 `QFormLayout`**。

这一改同时解决两件事：共用同一个表单 → 标签列宽天然一致；无参数时插 0 行 → 自然没有
空白。提示文字与 `minimumHeight` 预热一并删掉，旧译文也从 catalog 里移除。

**已知代价**：切换动作时对话框高度会变（单击 177、双击/长按 221、滑动 265），底部
按钮跟着移动 44~88px。这是与「无参数不留空白」直接冲突的取舍——早先固定高度能保证
按钮不动，但代价是每次都有空白加提示。用户明确选择不留空白，接受高度变化。

**为什么不用「另建容器但手动对齐列宽」**：那要把主表单的标签列宽同步给容器内的表单，
并在每次文案变化后重算——两套布局靠代码维持一致，改文案或换语言就会重新错位。

**新增/改写用例**：`test_no_placeholder_row_when_action_has_no_params`（无参数时插 0
行）、`test_dynamic_rows_follow_controller_row`（行号紧跟控制器）、
`test_labels_share_one_column`（所有标签右边界一致，直接测「共用表单」的可观测结果）。
原 `test_height_stable_across_actions` 删除——它断言的「按钮位置固定」已被本轮取舍

## #32 三条布局要求同时满足：固定高度 + 不留占位 + 共用表单

**新增用例**：`test_height_frozen_at_tallest_variant`、`test_measure_picks_tallest_not_first`。

## #34 缺陷修复：切换识别方式时标签列变宽、输入框被推着变窄

|---|---|
| 日期 | 2026-11-13 |

**根因与高度无关**：`QFormLayout` 的标签列宽度由该列**最长的标签**决定。切到 OCR 时

|---|---|---|---|

| 文本（OCR） | 121 | 140 | 289 |

**改法**：在 `_measure_and_freeze` 的逐值循环里同时记录**最宽标签宽度**，循环结束后

- 逐个标签 `setFixedWidth(最宽值)`——`setColumnMinimumWidth` 只设下限，遇到更宽的

  与原先观感完全不同（本轮实测踩到）；
- 动态行插入时按已定的列宽与对齐设置新标签，否则新标签又会把列撑宽。

**测试盲区（已补）**：`test_input_geometry_stable_across_kinds` 用短标签测试桩，两列

`test_label_column_width_fixed` 直接断言「所有标签宽度一致」与「`_label_width` 已记录」，
注入缺陷后立刻失败。

**结果**：标签列宽固定 121，阈值框 x 恒 140、宽恒 289，高度恒 265；来回切换完全不变。

**新增用例** 3 项：输入框位置与宽度稳定、标签列宽已锁定、标签仍右对齐。

## #35 缺陷修复：点「点击并观察」整个界面卡死

| 字段 | 值 |
|---|---|
| 日期 | 2026-11-13 |
| 类型 | 缺陷修复（`task.sleep` 不返回） |

**触发场景**：用户点调试页「单步试走」里的「点击并观察」后，整个界面卡死。

**已排除了上一条（#22）的成因**：`_on_step` 确实经 `bridge.click_and_identify()` 派发到
执行器线程，job 的 `ignore_pause=True` 也生效——`blocked_by_pause()` 那层死循环不存在。

**真正的阻塞源是另一个分支**。`TaskExecutor.sleep` 只有一个正常出口，且被
`should_capture()` 挡在外面：

```python
if not (self.blocked_by_pause() or (self.current_task is not None
        and self.current_task.paused) or self.interaction is None
        or not self.interaction.should_capture()):
    to_sleep = self.pause_end_time - time.time()
    if to_sleep <= 0:
        return              # ← 唯一出口
else:
    self._wait_for_activity(0.1)
```

`should_capture()` 在 `Pynput` / `PyDirect` / `ForegroundPostMessage` 里返回
`hwnd_window.is_foreground()`。**用户点按钮时焦点在调试页**，游戏窗口不在前台 → 判断
恒为 False → 永远进不到 return → 每 0.1 秒空转一次。

`click_and_identify` 的流程正是 `activate_area` → **`wait(after_wait)`** → `identify_once`，
而 `wait` 内部调 `task.sleep`。因此卡在第二步。

**改法**：`TaskBridge.wait()` 改用 `time.sleep`，不再经过 `task.sleep`。

**为什么这不是「绕过框架」**：`sleep` 的设计意图是「等用户把窗口切回前台再继续」；而
这里的语义是「点击后等画面稳定」的固定时长——卡死比多等两秒糟得多，且此时画面本来也
没在被操作。执行器线程只跑这一个 job，直接阻塞不影响 GUI；GUI 在
`future.result(timeout)` 上等，超时后仍能拿回控制权。

**覆盖范围**：所有等待都汇到 `TaskBridge.wait`（`click_and_identify`、`goto_blocking`、
导航与探索的 `hooks.wait` 共 9 处调用点），一处修改全覆盖。

**新增用例** 3 项（`TestBridgeWait`）：`wait` 不调用 `task.sleep`（假任务提供 `sleep`
也不许用）、非正时长立即返回、任务没有 `sleep` 时同样可用。

**反向验证**：把实现退回「优先 `task.sleep`」，`test_wait_does_not_use_task_sleep`
立刻失败。

**这条与 #22 是两处独立的死循环**，都必须处理：`blocked_by_pause` 那层靠「派发到执行器
线程 + `ignore_pause`」，`should_capture` 这层靠「不用 `task.sleep`」。

## #36 结构调整：路由从区域搬到独立的 routes.json

| 字段 | 值 |
|---|---|
| 状态 | 已实施 |
| 关联能力 | scene-manager |

**触发场景**：用户提出「流转信息的路由图是一个新功能，那么场景编辑中的交互区域配置中的

只需要存储识别特征、可交互区域的定义，以及探索信息，不应该有额外的信息」。

- 流转图上有一条边，点下去到不了；
- 探索探到了，流转图上却看不见。

4. 全库只有 `promote_draft` 会写 `SOURCE_CONFIRMED`，**没有任何路径能确认一条入边**，

- 新增 `routes.py`：`Route` + `RouteTable`，落库根 `routes.json`，键为
  `(场景 id, 区域名)`；
- `Area` 删掉四个跳转字段，只留 `name` / `rect` / `explore_*`；
- `graph.SceneGraph.build(scenes, routes, include_pending=False)` 改为读路由表；
  流转页传 `include_pending=True` 以画出待确认边，寻路仍只读 `routable_routes()`；
- `navigate` 的等待从 `RouteStep` 取、回退等待从图上取；
- 场景编辑器的区域对话框删掉「目标场景」「操作后等待」两项；
- 流转页承接边维护：确认 / 改目标 / 改等待 / 删除，表格同时列出待确认边；
- `promote_draft` 三步迁移：改写指向旧 id 的边 → 出边与入边升 `confirmed` →
  清空指向其它草稿的边并计数；
- `load_library` 首次运行时把旧库挂在区域上的边迁进路由表（幂等、不覆盖已有条目）；
- 删除场景、删除区域、区域改名三处补上路由联动。

**为什么键同步必须显式做**：路由与场景之间只剩 `(场景 id, 区域名)` 一条纽带。四类操作
漏任一处，故障都是静默的——改名后边无故消失、删区域留下点不到的边、删场景让流转图打不开、

删场景不清路由 → 1 条失败。

操作完的，然后得到了所有结果，那么就能够生成场景与场景之间的路由图，如果存在场景不可达
的情况，那么就可能是配置出现了问题或者一些其他情况」。

**判定**：这是**代码问题**，不是配置问题。返回区域已经标好了，探索却没探它。

**实测复现**（5 场景串联，每层都有「返回」，路由表初始为空）：

    clicks: [('scene-0002','开始按钮')]
    visited: ['scene-0002', 'scene-0003']
    edges:   [('scene-0002','开始按钮','scene-0003')]
    events:  warn  scene-0003  该场景没有返回区域也没有入边，无法回退
             skip  scene-0002  已离开该场景且无法回来，跳过它的剩余区域

一次点击就结束。根因链：回退依赖「返回边已存在」→ 返回边要靠探索才能知道 → 探索在
回退失败时直接放弃。

**五个独立缺陷，逐个修**：

1. **跳到已有场景不入队**。`RESULT_JUMPED` 分支直接 `continue`，于是「点进 B」之后
   B 的区域一个都不探。改为入队展开。
2. **回退失败即放弃**。加 `_discover_exit`：在回退失败时挑一个「还没有结论」的区域
   探一下，把返回关系发现出来，再回循环顶部重判位置。
3. **`expanded` 语义错**。原先「进队列就标记」，导致半途中断的场景被永久锁死、无法
   重试。改为「区域全走完才标记」，并加每场景最多 3 次的重排队上限。
4. **回退阶段仍走正向路径**。`_walk_to` 会把人送回刚离开的场景，形成
   「进 B → 退到 A → 又沿 A→B 走到 B」的往复，实测烧光 20 次点击。回退循环里不再
   尝试正向走。
5. **探索内部路由表不更新**。`_remember_edge` 只更新规划图，而「区域有没有结论」读
   路由表——刚探到的区域仍被当作没结论，下轮重探。补上 `set_target`，并用
   `_owns_routes` 避免写入模块级共享的占位空表（会让边漏到别的实例）。

顺带修了一处判据：跳过已探区域时原先用「目标场景已知」，它对 `invalid_areas` 无效
（判无效的区域不在路由表，永远不跳过）。改为统一的 `_area_resolved`。

**验证**（同一份 5 场景数据）：修前 1 次点击 / 1 条边 → 修后 5 场景全部访问、
8 条边（含全部 4 条返回边）、`stop_reason=completed`，点击序列无重复：

    a1(开始按钮) → 区域1 → 区域1 → 区域1 → 确定 → 设置按钮 → 帮助按钮
    → 开始按钮 → 返回 → 开始按钮 → 区域1 → 返回 → 区域1 → 区域1
    → 返回 → 区域1 → 区域1 → 确定

**测试**：新增 `TestExitDiscovery`（5 项）：探出返回边、多级场景 8 条边全齐、跳到已有
场景要展开、边不重复、无出口时如实停止。反向验证：把探路与入队两处同时注掉 → 2 条失败
（单点注入不失败，因为两条路径互为兜底，这是有意的防御）。

场景管理器全量 791 项通过。

## #81 页签外层不再滚动，配置页只让卡片列表滚

| 字段 | 值 |
|---|---|
| 状态 | 已实施 |
| 关联能力 | scene-manager |
| 创建日期 | 2026-11-23 |

**触发场景**：用户反馈「场景配置页签的滚动方式做的有问题，滚动区只应该在场景卡片
列表部分进行滚动，不能是整个配置页签页面」。

**根因**：`_sync_outer_height()` 只对「场景路由 / 探索」两页把外层 view 的最大高度
钉在视口高度，配置页走 `16777215` 分支。配置页内部本来就有卡片列表的 `QScrollArea`，
于是同一个滚轮有两层候选滚动区：外层一旦有滚动余量（卡片多、页面被撑高），滚动的
就是整页——标题、搜索框与状态行一起滚出视口，卡片列表自己反而不滚。设计文档原先
把这条写成「配置页内容超高，切回时恢复上限照常滚动」，即把这个行为当成了预期。

**改动**：

1. `SceneManagerTab._sync_outer_height()` 改为**所有子页**都把外层 `view` 的最大
   高度钉在 `viewport().height()`；`_current_key` 随之不再需要记录（删掉）。
2. 页面内部改为唯一滚动区：配置页是卡片列表，草稿页是表格，路由/探索页是画布
   （平移不靠滚动条）。配置页的工具栏与状态行留在根布局，卡片列表 stretch 吃满
   剩余高度。
3. 顺带修掉两处撑宽共享堆栈的长文案：`DraftsPage` 的整段说明与 `ConfigPage` 空态
   提示改为 `word_wrap=True`。`QStackedWidget` 的最小宽度取所有子页的最大值，任一页
   不换行的长句都会让配置页比窗口还宽；横向滚动条是关闭的，右侧会被直接裁掉。

**验证**：新增「配置页外层无滚动范围」「卡片溢出时只滚列表且固定部分不移动」
「空态提示换行」「草稿说明换行」4 项用例；`TestSceneManagerEditor` 187 项、
`TestSceneManagerToasts` 77 项通过。真实 `SceneManagerTab`（1560×820）实测：
外层 `view` 最大高度 724 = 视口高度、外层滚动范围 0，卡片列表滚动范围随卡片数增长；
同一环境下草稿页最小宽度由 772px 降到 376px。

### 原偏差 R1 停窗口后追加 `kill_exe` 兜底

| 字段 | 值 |
|---|---|
| 日期 | 2026-11-19 |
| 类型 | 前提失效 |

**触发场景**：设计阶段把「`stop_hwnd()` 在窗口未绑定时杀不掉目标」列为未解问题。
实施时确认：探索一开始就取不到画面时，`device_manager.hwnd_window` 可能尚未建立，
`stop_hwnd()` 没有可杀对象。

**原计划**：先 `stop_hwnd()`，再启动目标。

**实际做法**：`stop_hwnd()` 之后无条件调用 `kill_exe(abs_path=path)` 兜底，
其中 `path` 来自 `get_exe_path()`；`kill_exe` 会跳过当前进程与父进程。

**原因**：只靠 `stop_hwnd()` 会在最需要重启的场景（一开始就取不到画面）失效，
而失败表现是「重启后仍是旧进程」，比直接报错更难查。

**影响**：
- 计划第一批（目标探测/重启）受影响，已按兜底实现
- 新风险：`kill_exe` 按 exe 路径杀全部同名进程；仅对 Windows 目标生效，
  且目标路径由用户配置，不接受任意输入
- 未推翻任何已确认决定，不需要新决策记录

### 原偏差 R2 探索结果增加重启次数，摘要带出

| 字段 | 值 |
|---|---|
| 日期 | 2026-11-19 |
| 类型 | 范围变更 |

**触发场景**：任务层重试循环完成后，界面与日志只能看到最终的 `stop_reason`，
无法判断「这次结果是重启后得到的」还是「一次跑成」。

**原计划**：计划只写「次数耗尽保留原停止原因」，没有要求把重启次数带回结果。

**实际做法**：`ExploreResult` 增加 `restarts` 字段，`summary()` 在非零时追加
「，重启目标 N 次」，`to_dict()` 同步输出。

**原因**：重启是后台自动执行的破坏性操作，用户需要在不翻日志的情况下知道
「结果是在杀掉目标之后得到的」。摘要与横幅本来就承担这件事。

**影响**：
- 计划第三批（任务重试）与第四批（界面）范围略增
- 不引入新风险：字段默认 0，旧调用方不受影响

## #83 结论性说明：真机验证的环境阻断

| 字段 | 值 |
|---|---|
| 日期 | 2026-11-11 |
| 类型 | 范围变更 |

**触发场景**：按 `testing.md` 的已知盲区要求做真机端到端验证。

**原计划**：用测试子页签跑「实时识别 / 单步试走 / 完整跳转」三段并登记结论。

**实际做法**：改为「记录阻断原因 + 提供可复现的检查命令 + 明确恢复步骤」，
并在测试子页签改进取帧失败提示。

**原因**：当前环境不具备条件，不是省略：

```text
$ .venv/Scripts/python.exe -c "from ok import OK; ok = OK(cfg); print(ok.device_manager.capture_method)"
device_manager: DeviceManager
capture_method: None
```

`capture_method` 为 `None` 表示没有匹配到游戏窗口。本项目是**模板项目**，
`src/config.py` 的 `windows.exe` 按上游形态被注释，因此没有可截图的窗口。
这不是代码缺陷，也无法通过写代码绕过——真机验证必须先把目标游戏接上。

**影响**：
- `testing.md` 增加「未做真机验证的阻断原因」与「真机验收记录（待填）」两节，
  写明需要三步才能恢复（填 exe / 用 main_debug 启动 / 跑三段并登记）。
- 测试子页签在取不到帧时明确提示「请确认已连接设备，且 `src/config.py` 的
  windows/adb 配置能匹配到游戏窗口」，而不是笼统报「取不到画面」——否则使用者
  会以为是识别功能本身坏了。
- 真实风险仍在：识别阈值、点击坐标、稳定帧判据在真实游戏上的表现未经校验。
  这一条不能因为「有理由」就当作不存在，它留在 `testing.md` 的已知盲区里第一行。
