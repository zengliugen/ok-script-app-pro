## #3 门禁在「无 catalog」时错误地以退出码 3 中止

| 字段 | 值 |
|---|---|
| 日期 | 2026-11-03 |
| 类型 | 前提失效 |

**触发场景**：把 gate 接进 H1 后实跑，扩展目录下没有任何 `i18n/`，脚本报
「环境不可用：未找到任何 .po：extensions/capabilities」并退出 3。

**原计划**：计划里把 `check-mo` 的「未找到任何 .po」定为退出码 3（沿用原 `compile` 的处理）。

**实际做法**：`check-mo` 在**没有任何 catalog** 时改为打印一行说明并以 0 通过；
只有「代码里有界面文案、但扩展根下一条 `.po` 都没有」的 `check-missing` 才以 3 中止。

**原因**：退出码 3 在门禁语义里表示「检查没跑完」，会让 H1 阻断每一次提交。
而「这个能力本来就没有界面文案」是**合法的常态**，不是环境故障。
实测该分支会被现有两个能力（`log_noise_filter`、`update_check_guard`）稳定命中。

**影响**：
- 批次五（H1 接入）从「会阻断所有提交」变为可用
- 退出码语义更准：3 只留给真正的配置/环境故障
- 未引入新风险：真的缺译文时 `check-missing` 仍以 1 失败

## #2 包结构检查把 `i18n/` 资源目录当成缺失 `__init__.py` 的包

| 字段 | 值 |
|---|---|
| 日期 | 2026-11-03 |
| 类型 | 前提失效 |

**触发场景**：设计阶段实测 `check_package_structure`，对
`capabilities/demo/i18n/zh_CN/LC_MESSAGES` 报「缺少 __init__.py，会退化为命名空间包」。

**原计划**：设计文档的「未解问题」里已预判这条，但未定判据。

**实际做法**：新增 `_is_catalog_dir`，按「路径同时含 `capabilities` 与 `i18n` 段，
且 `i18n` 位于 `capabilities` 之后」豁免；`extensions/i18n/` 这种顶层目录不豁免
（顶层白名单会单独报错）。

**原因**：资源目录不是 Python 包，要求 `__init__.py` 只会逼人往译文目录放空文件。

**影响**：
- 批次三的范围增加一项
- 判据取窄：不影响能力包自身的 `__init__.py` 检查
- 无新增风险

## #1 按钮文案收集把元数据键当成待翻译串

| 字段 | 值 |
|---|---|
| 日期 | 2026-11-03 |
| 类型 | 更优路径 |

**触发场景**：脚本重写后对 `src/tasks` 跑 `gate`，报 `en_US` / `zh_CN` 各缺 2 条：
「text」「callback」。这两个是 `config_type` 里按钮项的**字段名**，不是界面文案。

**原计划**：沿用原 `_collect_config_type_value`，对 `options` 与 `buttons` 都递归取值。

**实际做法**：`buttons` 单独走 `_collect_button_strings`，只取每项的 `text` 值；
`options_available` 与 `options` 同等处理。

**原因**：按钮项形如 `{"text": "Show Config Values", "callback": ...}`，递归会把键名
`text`、`callback` 一起收进去，产生假缺失。实测原实现在 45 条真实文案里多报 2 条。

**影响**：
- 批次一的范围包含此项修正
- 修复后 `gate` 对 `src/tasks` 通过（两语言各 45 条）
- 无新增风险
