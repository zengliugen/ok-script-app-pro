# archive/ —— 已完成能力归档

## 放什么

已完成能力的文档整包归档：该能力的 design、plan、deviation、testing 四份文档随能力目录一起移入。

```
archive/
└── <能力名>/
    ├── design.md
    ├── plan.md
    ├── deviation.md
    └── testing.md
```

活跃区与归档区**同构**（都是「一能力一目录 + 固定文件名」），因此归档是一次目录搬迁，
不需要改名；四份文档的文件名与在活跃区时完全一致，引用它们的相对路径只需替换前缀。

## 为什么不删除

归档的价值不是保存结论（结论已进代码与规则），而是保存**当时不知道什么**。
半年后要判断「这个能力能不能改」时，知道当初有哪些盲区、哪些方案被排除过，比知道最终选了什么更有用。

## 与 decisions/ 的边界

ADR **不进归档**，永远留在 `decisions/`。原因：决策链靠编号顺序连续，移动会打断追溯。

## 归档动作

用 `archive <能力名>` 完成，**不要手工移动文件**：

```bash
python .codebuddy/lib/devflow/skills/devflow-guard/scripts/devflow_guard.py archive <能力名>
```

它一次做完三件事，并绑成一个整体：

1. 四类文档移入 `archive/<能力名>/`
2. 总览表各列路径更新为归档位置
3. **状态保持不变**——归档是存放位置，不是生命周期阶段，二者正交。

总览表的合法状态只有五个（草稿 / 评审中 / 已定 / 已实施 / 已废弃），**没有「已归档」**。
手工把它改成「已归档」会被 `audit` 判为错误（状态取值不在允许集合内）。
归档事实靠**路径**表达：该能力各列指向 `archive/<能力名>/` 下的文件即为已归档。

不要删除归档内容。

## 已归档的能力要怎么改

归档文档是那次工程的**冻结快照**，不是当前事实的载体。按改动性质分四类：

| 改动性质 | 动归档？ | 做法 |
|---|---|---|
| 纠错（错别字、失效链接、笔误） | **可以** | 直接编辑，不产生新事实 |
| 补充认知（归档后发现的新情况、新盲区） | **不改** | 记进当前工作的偏差记录，或新写 ADR 指向原决策 |
| **实现缺陷**（代码与该能力归档文档写的设计不符） | **不改** | **直接修代码**，不走流程、不立新能力 |
| **设计失效**（原设计的判断前提不成立，或要让能力做当初明确不做的事） | **不改** | **立新能力**：`new <新名> --rework-from <旧名>`，旧文档一字不动 |

**后两类的分界只有一条：归档文档记载的判断是否还成立。**

| 自问 | 能 |
|---|---|
| 把代码改成与设计一致就能解决吗？ | 能 → 实现缺陷，直接修 |
| 修完后，归档里的设计推理仍然成立吗？ | 成立 → 实现缺陷，直接修；不成立 → 设计失效，立新能力 |

改动量不构成判据——改一百行仍可能只是实现缺陷，改一行也可能推翻原结论。判错两个方向的
代价不对称：把实现缺陷判成立新能力，文档体系被琐碎改动稀释；把设计失效判成直接修，
归档里的推理悄悄过期，半年后有人照它再否决一次正确方案。

完整判据见 `.codebuddy/lib/devflow/skills/devflow-guard/references/guide.md` 的
「已归档的能力怎么改」。

## 为什么目录名不带日期

`archive/<能力名>/` 不带日期后缀，这是有意的：

- 能力名在总览表内唯一，`new` 遇到同名直接拒绝，不存在「两个同名能力需要靠日期区分」；
- 能力名同时是代码包名（`snake_case`）、`registry.py` 清单条目、文档目录名（`kebab-case`）
  与总览表「能力」列，四处必须机械对应。加日期就得让代码目录一起带日期，`audit` 的命名核对会断；
- 时间信息已由文件头的「创建日期 / 更新日期」与 git 历史承载。

同一能力多轮返工时用**语义区分**的新名字（`cache-policy` → `cache-policy-ttl`），
并用 `new <新名> --rework-from <旧名>` 建立指向关系。
