## 要解决的问题

具体现象或缺口。不要写「想加个功能」——那句话通常意味着问题还没界定。

- 现象：窗口最大化后关闭，再启动时界面错乱——标题栏区域出现**两组**最小化/最大化/关闭按钮，
  内容整体下移、布局出现偏差（用户截图 `ScreenShot_2026-11-04_103050_675.png`）。首次启动
  （窗口非最大化）不出现；只有配置里 `window_maximized: true` 时才出现。

- 根因（实测确认，非推测）：上游 `ok/ui/qt/MainWindow.py:452` 的 `bring_to_front()`
  在 Windows 分支**无条件**执行 `win32gui.ShowWindow(hwnd, SW_RESTORE)`。启动时窗口已按配置
  处于原生最大化，`SW_RESTORE` 把它降级为普通窗口，但 Qt 侧 `isMaximized()` 仍为 `True`。
  `ok/ui/qt/kit/window.py` 的 `WM_NCCALCSIZE` 处理按 `self.isMaximized()` 决定客户区内缩，
  状态错位后系统标题栏（`WS_CAPTION` 仍在）与 kit 标题栏同时可见、客户区被多缩 16px。

- 实测证据（同一 `1100x700` 测试窗口，`repro5/repro7/repro8.py`）：

  | 场景 | Qt isMaximized | 原生 IsZoomed | 窗口 | 客户区 |
  |---|---|---|---|---|
  | 最大化显示后 | True | True | 2576x1416 | 2560x1400 |
  | 调用 `SW_RESTORE` 后 | False | False | 1100x700 | 1084x684（内缩 16px，双标题栏） |
  | 跳过 `SW_RESTORE` | True | True | 2576x1416 | 2560x1400 |
  | 改用 `SWP_FRAMECHANGED` | False | False | 1100x700 | 1100x700（可自愈） |

- 不做的后果：所有把窗口最大化后关闭的用户，每次重启都会看到双标题栏与错位布局，且无法通过
  拖动/最大化恢复正常外观，只能手动还原窗口再最大化。这是启动即坏的第一屏，用户会直接判定应用有问题。

## 已确认的决定

每轮提问与回答的落点。每行一条决定，必须写清「凭什么这么定」——
理由缺失的决定，等于把问题原样推给后来者。

| 决定 | 为什么这么定 | 成立前提 |
|---|---|---|
| 走路径 3（`on_show_main_window` 钩子），不动上游 `MainWindow.py` | 上游文件改动要登记 `divergence.yaml` 且每次合并上游都可能冲突；钩子在 `set_window_size()` 之后、`show()` 之前执行，正好卡在窗口状态已定、用户可见之前 | `ok/__init__.py:521-523` 在 `my_app` 上派发 `on_show_main_window`，且此时 `main_window` 已 `set_window_size` |
| 只做「最小改动」：把实例的 `bring_to_front` 换成安全版 | 用户明确选择；根因只有一处多余的系统调用，替换后最大化状态不再被降级，无需额外补偿逻辑 | 替换实例方法能覆盖全部调用点——已核实三处：`showEvent` 的 `QTimer.singleShot(0, ...)`（`MainWindow.py:513`）、`ok/__init__.py:468`（`do_show_main`）、`ok/__init__.py:499`（语言切换重建窗口） |
| 安全版只在 `IsIconic()` 为真时才 `SW_RESTORE` | 最小化恢复确实需要 `SW_RESTORE`；最大化与普通窗口都不需要，调了就会降级 | 无 |
| 不做 `windowStateChanged` 自愈守卫、不做事后 `showMaximized` 补偿 | 用户选择最小改动；自愈守卫属另一条行为面（DPI 变化、系统吸附加），事后补偿会产生可见闪烁 | 若后续出现非启动路径的同类错位，再单独立项 |
| 断言目标方法存在，缺失即崩溃并指名 | 遵循扩展能力底线 4；上游若删掉/重命名 `bring_to_front`，静默跳过会让问题以「偶发界面错乱」的形式回归 | 无 |

## 已排除

考虑过但明确不做的方向，以及在什么前提下它会重新变得可行。
只写「不行」会让后来者无法判断当初的否决是否仍然成立。

| 方向 | 排除理由 | 重新可行的前提 |
|---|---|---|
| 直接改上游 `ok/ui/qt/MainWindow.py` 的 `bring_to_front` | 上游文件，改动需登记且每次合并冲突；本项目规则要求零改动优先 | 上游自己修复了该 bug，本项目可撤掉能力 |
| 保留 `SW_RESTORE`，事后 `showMaximized()` + `SWP_FRAMECHANGED` 补偿 | 实测可行（`repro8.py`），但启动时窗口会先缩小再最大化，产生可见闪烁 | 若发现不调 `SW_RESTORE` 会导致置前失败，且闪烁不可接受时重新评估 |
| 启动时忽略 `window_maximized` 配置，一律以普通窗口启动 | 会让「记住最大化状态」这个既有功能失效，属功能倒退 | 无 |
| 自己实现完整的 `bring_to_front` 语义（含前台锁突破） | 超出「修这个 bug」的范围，属重写上游行为 | 出现置前相关的独立问题时 |
| 用 `windowStateChanged` 自愈守卫统一兜底 | 用户明确选最小改动；该守卫覆盖的是另一类触发条件 | 出现非启动路径的同类错位时单独立项 |

## 结论

一句话说清做什么、不做什么。**结论为空时不允许建立能力文档**——那意味着还没有确认任何东西。

- 做：新增扩展能力 `window-restore-guard`，在 `on_show_main_window` 钩子里把主窗口实例的
  `bring_to_front` 替换为安全版——仅在窗口确实最小化时才调用 `SW_RESTORE`，其余情况跳过，
  从而不再把已最大化的启动窗口降级；断言目标方法存在，缺失即崩溃。

- 不做：不改上游文件；不加 `windowStateChanged` 自愈守卫；不做事后 `showMaximized` 补偿；
  不接管 `bring_to_front` 的全部前台锁语义。
