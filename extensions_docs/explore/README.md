# 需求探索目录

## 放什么

能力动手**之前**的需求确认记录：要解决什么、有哪些已知约束、哪些点还没定、最后确认了什么。

## 不放什么

- 能力的设计推演 → 需求确认后由 `new` 建立，进 `design`
- 已拍板的决策 → `decisions`

## 为什么单独一个阶段

`new` 生成的是「**承诺做这件事**」的文档。需求未确认就落盘，会留下一份看起来推演过、
实际什么都没说的骨架——而体检只查契约、查不出内容为空。探索阶段把这些判断放在前面，
并由 `new --from-explore` 强制引用，使「先确认再承诺」成为**结构**而不是纪律。

## 生命周期

| 状态 | 含义 | 能否被 `new` 引用 |
|---|---|---|
| 初始档 | 还在讨论 | 否 |
| 其余任一档 | 「结论」与「已确认的决定」均已填写 | 是 |

**采纳不靠状态表达，靠「## 采纳」一节**：`new --from-explore` 成功时自动追加一行
`- 采纳于：design/<能力名>.md（日期）`。它由工具写、不靠人工填，因为「是否被采纳、
被谁采纳」必须当场留痕；人工写等于让人事后自证。

**采纳后不原地回改**：实施中发现某个已确认的决定不成立，写进偏差记录并注明推翻的是哪一条，
不回改探索记录——与设计文档同一条规则。纠错（错别字、失效链接）可直接改。

**为什么不用状态表达采纳**：状态只能表达「有没有被采纳」，无法表达「被哪个能力采纳」；
而后者才是双向校验的依据。多一个状态值还会让状态集合与能力状态混在一起，语义漂移。

**放弃探索不删除**：把状态留在初始档即可。它与决策记录里的否决方案同价——
记录了「想过但没做」，而这类信息在别处无处可查。
