## 要解决的问题

具体现象或缺口。不要写「想加个功能」——那句话通常意味着问题还没界定。

- 现象：本项目是 ok-script 模板项目，业务代码要在「进入某个画面之后才能做某事」这件事上
  反复手写等待与重试。使用者每接一个新游戏，都要自己写「先回主界面、再点菜单、再点二级页」的
  一串坐标点击，路径一变全部失效，且没有任何可视化手段知道「现在到底在哪个画面」。
  参考实现 `ZenlessZoneZero-OneDragon` 用 79 个场景 / 699 个区域 / 75 条跳转边解决了这个问题
  （`assets/game_data/screen_info/`），但它的场景库与业务代码强耦合，且**没有**自动探索
  （全仓 grep `auto_explore|自动探索|自动建图|state_graph` 无命中），跳转靠人工填 `goto_list`。

- 不做的后果：使用者的每个任务都要各自实现「识别当前在哪 → 决定怎么走 → 点击 → 验证到没到」，
  同一套逻辑在不同任务里重复且互不兼容；换分辨率或游戏更新后，散落在各处的坐标需要逐个改。

- 本能力要提供的：一套**与业务解耦**的场景库（画面状态 + 可点击区域 + 跳转边），
  一个「跳到指定场景」的稳定接口，以及一个能自动把跳转边探出来的探索器。

## 已确认的决定

每轮提问与回答的落点。每行一条决定，必须写清「凭什么这么定」——
理由缺失的决定，等于把问题原样推给后来者。

| 决定 | 为什么这么定 | 成立前提 |
|---|---|---|
| 一次做全：配置 + 流转 + 自动探索 + 跳转接口 + 测试页，不分期 | 用户明确要求首版交付全部五项。分期的好处是早点验证场景模型够不够用，但既然配置与流转已先行明确，冒的风险是探索撑不住拖住整体 | 探索的不确定项（停机判据、边采样、回退策略）可在实施中按已定规则收敛，不出现需要推翻场景模型的新事实 |
| 场景库全部当**项目资产入库**，落 `assets/scenes/` | `configs/` 被 `.gitignore` 的 `/configs` 忽略（用户数据不进仓库），而场景库需要随仓库分发、可分享、可评审，属开发者资产。项目已有先例：`assets/coco_annotations.json` 与 `assets/images/` 都入库 | 入库图必须是脱敏后的图（见下两行） |
| 基准图存**遮罩版**：截图走已生效的全局 `screenshot_processor`，入库图不含 UID | 项目已有 `screenshot-mask` 能力把 UID 区域涂成纯色，任何落盘截图都会经过它（`ok/core/screenshot.py:207-210`、`ok/ui/qt/tasks/TemplateTab.py:176-177`）。入库图与真实帧只在矩形内有差异，矩形外的像素完全一致 | 遮罩矩形内不含需要识别的特征；相交时必须提示用户（见下一条） |
| 不做双图（原图 + 遮罩图），只存一张遮罩版 | 双图要维护两份生命周期、导入导出还得区分，成本大于收益。而遮罩默认只是右下角 13%×2.5% 的小块，UI 特征极少落在那里 | 特征框与遮罩矩形相交时给出明确提示，让用户调整位置或缩小特征 |
| 特征框与遮罩矩形相交 → **提示并展示交集**，不静默接受、不做特殊裁切 | 裁切本身永远可行，问题只在于裁出的模板像素在交集内是纯色块，匹配会失败。矩形求交可机械计算，能精确定位问题 | 遮罩配置（锚点/宽高/偏移）可从 `Screenshot Mask` 全局配置读取，见 `geometry.resolve_rect` |
| 场景扁平化，关系只由「区域 → 目标场景」的边表达 | 参考项目的 79 个场景同样是扁平的（`app_id` 只是作用域，不是父子层级）。层级可以用命名前缀（如 `设置-音效`）自行组织，不必进数据模型 | 无 |
| 场景主键用**稳定 id + 可改显示名**，所有边引用 id | 参考项目用名字当主键，改名必须同步所有 `goto_list`，漏一处即断边。用 id 后重命名只改一处 | 导入导出时保留 id；id 一旦分配不复用 |
| 配置**一场景一 JSON**（`assets/scenes/<场景目录>/scene.json`） | diff 友好、单场景损坏不连坐、与项目其余配置的 JSON 习惯一致；不引入 YAML 这个新格式 | 场景目录名用稳定 id，显示名只在 JSON 里 |
| 资产目录布局：`assets/scenes/<场景 id>/` 下放 `scene.json` + `preview.png` + `templates/<特征名>.png` | 一场景一目录，删场景即删目录，模板与预览图不会成为孤儿。分三处存放的方案删场景时要清三处，易漏 | 无 |
| 识别判据 = **必需特征全中 + 可选特征打分** | 必需特征防误判（参考项目正是「所有 id_mark 区域全中」，`screen_utils.py:462-473`），可选特征区分相似画面。纯评分制要逐场景调阈值，场景多时维护成本高；纯必需全中则无法区分相似画面 | 每个场景至少有一个必需特征；无必需特征的场景视为配置错误 |
| 识别不到任何场景时返回**疑似场景与分值** | 能区分「真的不在任何场景」与「在过渡动画里」。与参考项目的 `top_n` 模糊候选同源（`screen_match.py:226-234`） | 疑似结果只用于诊断与回退决策，不用于寻路 |
| 特征支持两种手段：**模板图 + OCR 文本** | 两者都已验证可用：模板走 `find_feature(template=<ndarray>, box=<Box>)`（`FeatureSet.py:236`），OCR 走 `task.ocr()`（`task.py:742`）。颜色范围在参考项目里只作 OCR 前置过滤，不单独立项 | 无 |
| 特征搜索区域存**相对比例**（0-1），不存绝对像素 | 分辨率归一化后仍可能因窗口边框、黑边、裁剪偏移不同而错位，相对比例对这种差异更鲁棒 | 无 |
| 分辨率不一致时把**帧等比缩放到基准分辨率再匹配**，点击坐标乘回当前分辨率 | 一次 resize 复用给多次匹配，模板只需存一份不必缩放（缩放模板会反复插值、失真累积）。与参考项目一致——它就把帧 resize 到标准的 1920×1080 再识别（`pc_screenshot_controller.py:76-77`） | 场景库记录采集时的基准分辨率；空库首次采集时以当时帧尺寸为基准 |
| 场景库记录**基准分辨率**，导入到不同分辨率的机器上按上一行归一化 | 无基准分辨率就无法换算，库要么锁定一个分辨率不可迁移，要么无法使用 | import 时检测并提示分辨率差异 |
| 可点击区域参数：名称、坐标、是否允许探索点击、目标场景（可空）、点击后额外等待秒数 | 游戏有动画，固定延时不够用，而等待参数放区域上最直观。目标场景可空 = 只点不记边（如关闭弹窗），这是真实存在的用法 | 无 |
| 自动探索默认只点**白名单区域**（`可探索` 标记），且运行前弹窗列出本次将点击的区域数让人确认 | 误点可能花资源、进战斗、消耗次数，且不可逆。黑名单无法穷尽（「充值」「删除」「退出」之外还有游戏自定义的危险按钮） | 区域默认 `可探索=false`，用户显式打开 |
| 探索停机 = 三重上限（状态数 / 总时长 / 单状态步数）+ 手动中断 | 状态空间可能无限（同一画面因进度不同差分出新状态），不可能靠「自然跑完」收尾。只设时长会在小图跑得慢、大图中途截断；只靠「无边可探」在存在可点击区域时永不触发 | 三个上限均有默认值且可在任务配置里改 |
| 探索按 **BFS 逐层展开**：先把当前场景所有允许区域试一遍，再进新场景 | 每层只需一次回退，边采集效率高，先得到广度上的全貌。DFS 回退次数多且先深挖一条支线，整体拓扑很晚才成形 | 无 |
| 探索回退 = **场景级返回区域**（可配）+ 入边反推（无配置时） | 探索是树状展开，不会回退就只能跑一条直线。只用入边反推在入边多时试错成本高且可能越退越深；固定回根场景则每步都要走完整路径，极慢 | 无返回区域且无入边的场景（起点）不回退，直接终止该分支 |
| 点完区域后判定到达画面 = **等画面稳定（连续两帧一致）** 再识别 | 动画/过渡中识别必错。固定延时是写死参数：快画面白等、慢画面误判。轮询识别直到命中则可能在过渡动画中误命中中间态场景 | 稳定判据用帧差阈值，阈值与最长等待可配 |
| 探索发现的新画面自动存为「待确认」草稿，落 `assets/scenes/_drafts/`，与正式场景同构 | 探索无人值守，停下来问会打断长跑。草稿与正式场景结构一致，确认只需一次目录移动，不易漏字段。只存内存则中途关闭全白做；直接写正式目录会让寻路走到未验证节点 | 寻路与识别只读正式目录，不读 `_drafts/` |
| 新画面的候选特征 = **与父场景帧做逐像素差分取最大差异区域**，给出候选框供用户确认 | 自动框选难以准确，但给出候选框后人工微调成本极低。固定区域截取命中率低易误匹配；完全不提则探索发现 50 个画面就要手工框 50 次 | 差分只在两帧尺寸一致时有效；尺寸不一致时退化为「不提供候选框，全手工」 |
| 探索产生的边先落**草稿**，人工确认后才进正式路由图 | 误判一条边就可能让导航点错地方，而探索是无人值守跑出来的。直接写入正式图会让下次导航就跑错 | 草稿确认动作在「草案」子页签里，支持逐条与批量 |
| 边带 `source`（manual / explored / confirmed）与观测次数；寻路**只走 manual 与 confirmed** | 分不清哪条是人配的、哪条是机器猜的，出问题难追溯。explored 未经确认就参与寻路，等于把探索误差直接变成导航误差 | 用户可一键把 explored 升级为 confirmed |
| 图算法用 **networkx**（最短路、连通性、spring 布局坐标），渲染用 **QGraphicsView 自绘** | 项目当前无任何图库（`requirements.txt` 与 `.venv` 均无 networkx/graphviz/pyqtgraph/matplotlib）。networkx 是纯 Python 无原生依赖、可打包；而交互式节点画布（拖动、点选看详情、高亮路径）必须自绘才可控 | networkx 写进 `pyproject.toml` 的 `[project].dependencies`（基础依赖，不归 qt extra），因为寻路是运行期核心逻辑 |
| 结论驱动形态：**纯逻辑类 `SceneNavigator` + 薄壳 `SceneGotoTask`** | 纯逻辑类可被流转图页的「试走一步」、离线测试复用；薄壳 Task 让它能进任务列表、被 `run_task_by_class` 同步调用、继承执行器的暂停/停止语义。全写在 Task 里则内部模块无法复用；只做普通函数则不继承暂停/停止语义 | 框架支持任务嵌套：`BaseTask.run_task_by_class`（`task.py:1046-1056`）与 `TaskExecutor.submit`（`TaskExecutor.py:522-543`）均已核实可用 |
| 外部调用传参：`go(scene_name)` 方法内设属性再执行；无参 `run()` 读任务配置里的默认目标 | 一个方法同时服务代码调用与 UI 点击，调用方不会忘传参。走任务配置项则每次跳转都要改配置、多写一次盘且污染用户配置 | 任务注册时 `visible=False` 以免占用任务列表 |
| `goto_scene` 返回**结果对象**（是否成功、实际路径、每步耗时、失败原因），失败不抛异常 | 调用方多是任务流程，要根据结果决定后续分支；异常会让整条流程中断。只返 bool 则失败时无法知道卡在哪步 | 参数错误（场景不存在、图为空）仍抛异常，属编程错误不属运行失败 |
| 跳转失败恢复 = 重试 N 次 → 尝试回退到已知场景 → 仍失败则报错退出并保留现场截图 | 游戏会有动画、弹窗、加载中，单次识别失败是常态。失败即退出则一个临时弹窗就能让整个流程失败；失败后 BFS 重规划在本版复杂度高，且失败边可能只是偶发 | 重试次数与超时可配 |
| 识别开销控制 = **缓存当前场景 + 短路**：先试上次场景，不中再全量扫描，每场景内必需特征按区分度排序、失败即短路 | 模板匹配是 CPU 密集，几十个场景全扫一次可能几秒。每次全量扫描在导航多轮时明显卡顿；分组扫描要多一层人工配置负担 | 缓存只在同一次导航内有效，跨任务不复用（画面可能已被用户改动） |
| 探索与导航都 `acquire_exclusive(owner)` 独占执行器，结束 `release` | 两者都在控制游戏，若别的任务或触发任务同时点击，路径会乱。框架已提供该机制并在 MCP 里用过（`TaskExecutor.py:560-585`、`mcp_runner.py:204`） | 独占被别人持有时导航返回失败，不排队等待 |
| 自动探索做成**独立 BaseTask**（`SceneExploreTask`），任务页和页签按钮双入口 | 探索是长跑，必须受执行器的暂停/停止/独占保护，任务框架已自带。只在页签内 `submit` 跑则用户看不到进度条与停止按钮 | 两个入口启动的是同一个任务实现，不写两套 |
| 页签内部 **四个子页签**：配置 / 流转 / 草稿 / 测试 | 草稿是探索产物、需要批量确认，节奏与手工配置完全不同。并入流转页则图与草稿列表争空间；探索独立成页则只剩一个启动按钮与进度，不值一页 | `TabStrip` + `QStackedWidget` 组合（`kit/tabs.py:74`，范例 `ui/qt/tasks/tasks_page.py:509-527`），框架无现成嵌套页签组件 |
| 测试子页签**只在 debug 模式创建** | 与需求一致；避免普通用户误点导致游戏被动操作。debug 值可取 `og.config['debug']`（`__init__.py:719`）或 `og.app.debug`（`:331`） | 用 `main_debug.py` 启动时可见 |
| 测试子页签三段：实时识别结果 / 单步走一步 / 完整跳转 | 三段分别定位「识别错」「边错」「寻路错」。只做完整跳转则失败时分不清是哪一环 | 批量回归（跑全库基准图识别）不放在这里，属测试代码，落 `extensions_tests/` |
| 基准图来源：**实时截图 + 导入本地图片**双支持 | 导入能降低「必须开着游戏才能配置」的门槛，也方便用已有截图搭库。只实时截图则无游戏时完全不能配置；只导入则每次都要先去别处截图 | 导入的图片须为支持的格式，且不在遮罩区内含隐私内容（导入图不经过 processor） |
| 场景库**导出/导入**（单场景 + 整库 zip） | 换机器、分享配置、备份都需要，成本很低，还能当探索前的安全网 | 导出前做脱敏体检（见下一条） |
| 导出前做**脱敏体检**：基准图是否已遮罩、模板与遮罩区是否相交、OCR 文本是否含长数字串，有问题列出清单让用户确认 | 导出是不可逆的外发动作，用户很可能把含 UID 的包发出去。不检查则风险完全靠用户自觉 | 检查结果只提示不阻断，最终由用户确认 |
| 界面文案**中英两份 gettext**（`i18n/zh_CN`、`i18n/en_US` 的 `ok_ext` 域） | 项目规则强制要求用户可见文案可本地化，体检的本地化项会报错；只做中文则日后补英文要改全部文案 | catalog 放能力包内 `i18n/<locale>/LC_MESSAGES/ok_ext.{po,mo}`，两者都入库 |
| 场景库开箱为空，不预置任何具体游戏的场景 | 本项目是模板项目，仓库里没有具体游戏（README 已声明）。预置需要先有目标游戏与关键画面信息 | 若日后要预置，需先确认目标游戏 |
| 画面稳定的帧差判据**复用框架 `patches_changed` 的阈值**：单像素差 > 8 计为变化，`mean(diff) > 3.0` 或变化像素占比 > 0.1 判为仍在变；叠「连续两帧都判稳定」才算稳定 | 这套阈值不是猜的：框架用它在 `ok/util/blur.py:104-115` 做 overlay 的 patch 变化检测，已在本框架的真实截图上验证过。自定一套更严的值要重新调参，且与框架口径不一致会让「同一帧在图上是稳定、在探索里是不稳定」这种矛盾出现 | 两个阈值作为任务配置项暴露，默认值即框架值 |
| 探索「单状态步数上限」**只计有效点击次数，不计回退** | 回退本身由「场景级返回区域 + 入边反推」控制，而 BFS 的已访问集合保证每个场景只展开一次，不存在靠回退反复旋转的情形；另有时长上限兜底。把回退计入会让回退频繁的分支提前耗尽上限，未探完就停 | 若实测出现回退路径导致的死循环（已访问集合失效），再改为计数含回退 |
| 点击后没离开原场景的区域：**连续两次无跳转**才判为无效区域，写入探索报告且不建边 | 一次可能是卡顿、冷却或动画未结束（有些按钮第二次点才生效）；两次仍无变化基本可判定。一次即判会让冷却类按钮被误判并永远不再尝试 | 「无跳转」的判定同样走稳定帧判据，避免在动画中误判 |
| 单个场景的必需特征 > 3 个时**在配置页给提示，不阻断保存** | 必需特征是 AND 关系，加越多越容易整场景漏识别；3 个是经验上限。硬限 3 个会逼复杂画面降低区分度，而不提示则用户容易堆一堆特征再抱怨「识别不到」 | 提示文案需说明「必需特征越多越容易漏识别」 |
| 差分提候选框时，若差异像素占比 > 30%，判定背景有动画，**不给候选框**，退化为全手工框选 | 动态背景（飘动特效、粒子）的差分结果是一片噪声，取最大差异区域毫无意义。给一个错误候选框比不给更糟——用户会以为自动结果可信 | 30% 作为任务配置项，可调 |
| 导入的图片与场景库基准分辨率不一致时**比对宽高比**：比例一致（容差 1%，同框架 `check_frame_and_resolution`）则按缩放处理并提示；比例不一致则拒绝并要求重截 | 单张图无法区分「只是裁剪差异」与「真的换了分辨率」，但宽高比可以：比例相同说明是缩放关系可换算，比例不同说明画面构成已变，换算出来也是错的 | 容差取值与框架的 1% 保持一致 |
| `preview.png` 缺失时显示占位图 + 提示「重新截图」，**不报错** | 预览图只用于展示与缩略图，不参与识别与导航，缺它不影响功能。报错会让「用户手动删了一张展示图」变成阻断性问题 | 占位图不能影响该场景的识别与寻路 |

## 结论

一句话说清做什么、不做什么。**结论为空时不允许建立能力文档**——那意味着还没有确认任何东西。

- 做：在 `extensions/capabilities/scene_manager/` 新建「场景管理」能力，提供一套与业务解耦的
  场景库（场景 = 必需/可选特征 + 可点击区域，一场景一 JSON，落 `assets/scenes/<id>/`）与
  四子页签界面（配置 / 流转 / 草稿 / 测试，测试页仅 debug 可见）。核心能力三项：
  ① 按「必需全中 + 可选打分」识别当前场景，帧归一化到库基准分辨率后匹配；
  ② 提供 `SceneNavigator` 纯逻辑类 + 薄壳 `SceneGotoTask`，支持 `goto_scene(name, timeout)`
  沿 networkx 最短路逐层跳转并返回结果对象，失败按「重试 → 回退 → 报错」恢复；
  ③ 提供独立 `SceneExploreTask`，BFS 逐层点击白名单区域、等稳定帧判到达、
  自动发现新画面存草稿、边先落草稿待人工确认。附场景库导入导出与导出前脱敏体检。

- 不做：不改上游文件（除既有 `pyproject.toml` 依赖条目需要更新）、不预置任何具体游戏的场景、
  不做双图存储、不做 MCP/HTTP 外部接口、不引入 graphviz/pyqtgraph、不用数据库、
  不把场景库放 `configs/`、不让探索产物直接进正式路由图。

## 补充探索：探索未完成时重启目标（2026-11-19）

> 原独立探索记录 `explore/scene-target-restart.md` 已并入本节（2026-11-23）。
> 它是同一个能力下的子问题，不单独立项。

### 要解决的问题

- 现象：场景探索依赖目标程序持续在线。目标崩溃、掉线或被关闭后，探索只能以
  `no_start_scene`（取不到画面 / 识别不到起点）或取帧、点击异常结束；当前没有任何
  恢复手段，用户必须手动重开目标，再回探索页重新点一次。
- 不做的后果：长时间探索中任何一次目标异常都会让整轮进度停住，夜间或无人值守时
  尤其明显；已采集的边虽然落盘，但剩余区域不会被接着探，用户也很难判断是目标挂了
  还是探索逻辑有问题。

### 已确认的决定

| 决定 | 为什么这么定 | 成立前提 |
|---|---|---|
| 只在探索**未完成**时重启：`no_start_scene` 与取帧/点击异常触发；`completed`、`max_scenes`、`max_seconds`、`max_clicks_per_scene`、`cancelled` 都不重启 | 后几类是用户设定的正常截止或主动取消，重启只会把「按上限结束」误判成故障，白杀一次目标 | 用户把「未完成」理解为异常中断，而不是「没探满所有区域」 |
| 只对 Windows 目标生效，ADB 模拟器与真机暂不支持 | 杀模拟器会关闭多开实例、改变串口，恢复链路比 Windows 复杂得多；真机也无法由主应用重启 | 目标通过 `windows.exe` 或已绑定 hwnd 启动 |
| 「自动启动目标」与「未完成时重启」两个开关**默认关闭** | 两者都有副作用：一个会拉起进程，一个会杀进程。默认关闭让用户显式授权后才生效 | 用户已确认默认关闭 |
| 配置放探索页参数区，写入 `LibraryMeta`（随场景库走） | 与点击间隔、稳定超时、探索顺序同类，都是探索行为参数；写入主窗口设置会产生上游差异，也不随库迁移 | 探索页保留参数区 |
| 默认最多重启 1 次（可配 0–3），启动后等待窗口稳定上限 8 秒（可配），随后轮询取帧并识别，直到命中任一场景 | 一次重启能覆盖大多数崩溃/掉线；次数过多会在登录画面等无法自动通过的场景上反复杀进程 | 目标重启后能回到某个已建场景 |
| 重启后**从头再跑一轮**，保留已采集的草稿与边；已有可寻路路由的区域会被 `_area_resolved` 跳过 | 目标进程重启后 BFS 队列与当前画面上下文已经丢失，从断点继续不现实；按路由表跳过已解决区域等价于「从已探部分继续」 | 第二轮能重新识别起点 |
| 重启流程用框架现有能力：`device_manager.stop_hwnd()` 杀已绑定目标 → `execute()` 拉起 → `do_refresh(True)` → 轮询取帧 | 不新写杀进程与启动逻辑，复用框架对 `windows.launch_arguments`、管理员权限与启动方式的既有处理 | 框架版本仍提供这三个接口 |

### 未定项

| 未定项 | 为什么当时定不了 | 收敛结果 |
|---|---|---|
| `stop_hwnd()` 在窗口尚未绑定（探索一开始就取不到画面）时杀不掉目标 | 取决于异常发生时 `hwnd_window` 是否已建立 | 已补 `get_exe_path()` + `kill_exe()` 兜底（偏差 #82 子节 R1） |
| 重启后 `device_manager` 重连耗时与识别轮询的超时取值 | 与目标启动速度、截图方式有关，8 秒只是起点 | 由 `restart_wait` 控制，默认 8 秒，可调 |
| 目标重启后停在登录 / 公告画面时轮询会一直识别不到 | 这类画面不在场景库里，自动流程无法通过 | 列为已知盲区；次数耗尽后保留 `no_start_scene` |

### 已排除

| 方向 | 排除理由 | 重新可行的前提 |
|---|---|---|
| 探索完成后也重启目标（恢复到初始状态） | 用户明确只要「未完成」触发；完成后重启没有恢复价值，反而会让用户以为程序异常 | 有「每次探索后重置目标」的明确需求 |
| 支持 ADB 模拟器 / 真机重启 | 杀模拟器影响多开与串口，真机无法由主应用重启；风险远高于收益 | 有模拟器专用重启接口，且能保证多开实例隔离 |
| 只做「探索前自动启动」，不做中途重启 | 解决不了探索进行中目标崩溃/掉线的主要场景 | 目标稳定性足够，崩溃只发生在启动阶段 |
| 重启后从原 BFS 队列断点继续 | 进程重启后当前画面、回退路径与队列上下文全部失效，继续点会作用在错误画面上 | 目标支持进程内断点恢复 |

### 结论

- 做：为 Windows 目标增加「探索前自动启动」与「探索未完成时重启并重跑」两个可选
  开关，默认关闭；配置随场景库保存，重启次数与等待时间可调。
- 不做：不做 ADB / 真机重启，不在探索正常完成或用户取消时重启，不从原队列断点继续。
